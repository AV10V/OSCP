01

Reconnaissance

Port scan and service fingerprint

Goal: confirm the host is reachable, enumerate every open TCP port, fingerprint the services, and then — because TCP came back sparse — check UDP as well.

1.1 Connectivity

command
ping -c 2 -W 2 192.168.245.149
output
PING 192.168.245.149 (192.168.245.149) 56(84) bytes of data.
64 bytes from 192.168.245.149: icmp_seq=1 ttl=61 time=64.5 ms
64 bytes from 192.168.245.149: icmp_seq=2 ttl=61 time=64.3 ms

Reading it: TTL 61 means the packet started at 64 and crossed three hops, which on this lab subnet means a Linux kernel with the default net.ipv4.ip_default_ttl=64 sitting behind a couple of routers. Already a hint the box is Linux before a single port is touched. The ~64 ms RTT confirms it is reachable over the VPN tunnel rather than on-link.

1.2 Full TCP port scan

Scan all 65535 ports first — never trust a "top 1000" scan on an exam box.

mkdir -p /tmp/box149 && cd /tmp/box149
nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt 192.168.245.149
output

Nmap scan report for 192.168.245.149

Reading it:

  • 65532 closed tcp ports (reset) — the host answers with RST rather than dropping, so there is no packet filter in front of it. Every port result here is trustworthy.
  • Only three services. That is a deliberately small attack surface, which usually means the intended path is a service misconfiguration rather than a memory-corruption exploit.
  • 23 seconds for a full sweep is the payoff from --min-rate 3000 on a LAN-speed target.

A TCP-only scan finds three well-patched services and the box looks like a wall. UDP is where OSCP boxes hide their easiest wins, and SNMP is the usual reason.

02

Web enumeration

The dead end, justified with four negatives

Port 80 is the obvious target on a box with only three services, so it deserves a real attempt — but a bounded one. The skill being practised here is knowing when to stop, and being able to justify the stop with evidence rather than a hunch.

Spoiler: there is nothing here. The value of this chapter is the four independent negative results, because together they justify walking away.

2.2 Cheap probes before brute force

Always do the short list first — it costs one loop and occasionally saves the whole chapter.

command
for p in robots.txt sitemap.xml index.php index.html .git/ .htaccess \
         server-status manual/ phpinfo.php info.php; do
  code=$(curl -s -o /dev/null -w "%{http_code} %{size_download}" --max-time 5 \
    "http://192.168.245.149/$p")
  echo "$code  /$p"
done
output
404 277  /robots.txt
404 277  /sitemap.xml
404 277  /index.php
200 10918  /index.html
404 277  /.git/
403 280  /.htaccess
403 280  /server-status
404 277  /manual/
404 277  /phpinfo.php
404 277  /info.php

Reading it:

  • Every 404 returns the same 277 bytes — a consistent Apache error document, which gives us a reliable size filter for the brute-force step.
  • There is no PHP: /index.php 404s and /phpinfo.php 404s. Combined with Content-Type: text/html on the index, this is a static-only Apache. No mod_php, so no webshell path even after a file-write.
  • .htaccess → 403 means the file exists as a protected file rather than being served. Normal hardening, not a finding.
  • /server-status → 403 means mod_status is loaded but restricted to localhost. Worth a note; not exploitable from here.

2.6 Checking the one plausible CVE

Apache 2.4.41 is old. The famous 2021 path-traversal pair targets 2.4.49 and 2.4.50, so this is technically out of range — but Ubuntu backports, and the check is cheap. --path-as-is is mandatory: without it curl normalises %2e%2e for you and the test silently does nothing.

command

curl -s --path-as-is "http://192.168.245.149/icons/.%2e/.%2e/.%2e/.%2e/etc/passwd"

## CVE-2021-41773 via cgi-bin
curl -s --path-as-is "http://192.168.245.149/cgi-bin/.%2e/.%2e/.%2e/.%2e/etc/passwd"

## CVE-2021-42013 double-encoding variant
curl -s --path-as-is \
  "http://192.168.245.149/cgi-bin/%%32%65%%32%65/%%32%65%%32%65/%%32%65%%32%65/%%32%65%%32%65/etc/passwd"

## from the document root
curl -s --path-as-is "http://192.168.245.149/.%2e/.%2e/.%2e/.%2e/etc/passwd"

All four:

<!DOCTYPE HTML PUBLIC "-//IETF//DTD HTML 2.0//EN">
<html><head>
<title>400 Bad Request</title>
</head><body>
<h1>Bad Request</h1>

Reading it: 400 Bad Request rather than 403 or 404 is the patched behaviour. The apache2-bin package version recorded in the SNMP software list confirms it: apache2_2.4.41-4ubuntu3.23_amd64 — the 3.23 revision includes the traversal fix backport. Also note /cgi-bin/ 404s from section 2.2, so the alias this exploit depends on does not even exist.

Conclusion — do not spend more time on port 80

Four independent lines of evidence:

  1. Byte-identical stock page, timestamped to image build time, no PHP and no redirects.
  2. Two wordlists (raft-medium, DirBuster 2.3 medium with 10 extensions) → only the stock page and stock icon; soft-404 filtered.
  3. No vhosts across 5000 candidate names in two resolutions.
  4. The only plausible CVE is patched (400, and the vulnerable package revision is confirmed from the installed-software list).

This is enough to write the service off and go where the evidence points: UDP/161 SNMP, which the TCP-only view never showed.

03

SNMP

The leak that hands over credentials

161/udp was the only unambiguous UDP result from chapter 01. This chapter turns it into a username and a password policy statement.

3.1 Why SNMP first

SNMP on a Linux host is almost always net-snmp/snmpd, and it is almost always misconfigured in the same two ways on lab boxes: the default community string public is left in place, and somebody has added a custom extend entry that runs a host command. The extend mechanism is attractive for admins because it lets you expose arbitrary script output as an OID — and disastrous when the description of that extend is itself sensitive.

Decoding the index

The OID suffix 5.82.69.83.69.84 is not opaque. The first component is the string length, the rest are ASCII character codes:

Component Meaning
5 length of the extend name
82 R
69 E
83 S
69 E
84 T

So the extend is named RESET. Decoding these by hand is worth doing once — it makes tables where the key carries the meaning readable at a glance:

command
## generic decoder for an nsExtend index suffix
python3 -c "
s='82.69.83.69.84'.split('.')
print(''.join(chr(int(x)) for x in s[1:]))"

What each column tells us

Column Value Meaning
...2.1.2 ./home/john/RESET_PASSWD the command the agent executes
...2.1.3 / .4 "" no stdin, no arguments
...2.1.5 INTEGER: 5 cache timeout type (5 = cache for a set period)
...2.1.6 INTEGER: 1 output type: run the command through a shell
...2.1.20 / .21 4, 1 exec error codes — clean run
...3.1.1 "Resetting password of kiero to the default value" the MIB description string
...3.1.4 INTEGER: 0 exit status 0 — the command succeeded

Three separate pieces of intelligence, all without credentials:

  1. A username: kiero. Confirmed twice over — the description names it, and the hostname ...-kiero-... independently suggested it.
  2. A password policy statement: "the default value". Not a hint, a specification. This converts the password from "unknown, brute force everything" to "try the obvious defaults for this specific account".
  3. A privileged binary: /home/john/RESET_PASSWD. Something on this host exists whose job is to reset kiero's password, which means it runs as root. That is a privilege-escalation candidate for later — logged and set aside for chapter 06.

Two-for-one. This single OID range supplied the entry point and foreshadowed the privesc. That is why nsExtendTable is always worth a walk.

A note on the extend output

The executed output (...4.1.2.<index>.1) contains only the description text, not a password. The cached value is what the script printed, and the script prints a status line. There is no credential to harvest directly from the extend — the value is purely the hint.

6.4 Why this is exploitable

system(3) is documented as running the command via /bin/sh -c. The shell therefore performs a PATH lookup for chpasswd, and PATH is inherited from the calling process — which the attacker controls.

The usual protection against setuid programs being abused this way is that sh drops privileges when the real and effective UIDs differ, so system() inside a setuid binary would run as the real user. That protection does not help here, and the reason is the first two instructions:

output
setuid(0);   /* ruid = euid = suid = 0  */
setgid(0);   /* rgid = egid = sgid = 0  */

setuid(0) called with euid==0 (which we have, thanks to the setuid bit) sets all three UIDs — real, effective and saved — to 0. After that call, ruid == euid == 0, so /bin/sh sees no mismatch, does not drop anything, and executes our binary with full root. The program disables its own safety net.

So the attack is: put a program called chpasswd in a directory, prepend that directory to PATH, run the SUID binary. The binary sets itself to root, then asks the shell to run the first chpasswd it finds on PATH — which is ours.

Any payload works. This one proves root non-destructively by capturing identity and reading the root-only proof file, rather than spawning an interactive shell.

Two points worth being precise about:

  • The real password reset never happens. The first system() call would have run the genuine chpasswd, but we replaced it. This exploit therefore does not change kiero's password — a detail worth knowing on an exam, where you must not silently break accounts you have finished with.
  • Ordering. system() returns only after the child exits, so both calls run sequentially and the second banner is not evidence about the first.

6.7 Why this is the intended path

  • The binary is named in the SNMP extend that also leaked the account name — the box hands you the privesc pointer during initial access.
  • It is setuid and setgid, world-executable, and sits in the unprivileged user's home directory. All three are deliberate choices.
  • It calls setuid(0) then system() with an unqualified command — a textbook CWE-426 (Untrusted Search Path) pattern that no amount of patching elsewhere would fix.
  • Every other vector was dead (chapter 05), so the box is unambiguous.

6.8 Fix, for the record

output

/* fixed — no shell, no PATH lookup, fixed environment */
execl("/usr/sbin/chpasswd", "chpasswd", (char *)NULL);

or better, drop the shell entirely and write to the shadow database through the PAM/libc API as root. Also: remove the setuid bit (the task needs root, but it does not need to be reachable by users), change file mode from 6775 to 4755 at minimum, and never install a setuid helper inside a user-writable home directory.

7.3 What made this box easy

Honest accounting, because "easy box" write-ups that skip the reasoning teach nothing:

  1. The UDP scan decided the box. The entire TCP surface was three patched services with no exploitable version. nmap -sU --top-ports 30 found 161/udp, and that single result produced the entry point. Skipping UDP would have left this box looking unsolvable.
  2. The SNMP extend did the reconnaissance for me. nsExtendTable handed over a username and an explicit statement that the password is a default value. That is not a lucky guess — it is information the host volunteers. Always walk 1.3.6.1.4.1.8072.1.3.2.
  3. The privesc was pre-announced. The same extend named /home/john/RESET_PASSWD, and once I had a shell, ls -la in the home directory confirmed a setuid+setgid root binary that was world executable. No hunting through cron, capabilities, or the kernel was needed.
  4. No mitigation defence was needed. Full RELRO and PIE meant memory corruption was off the table — but the logic bug (system() + attacker-controlled PATH) is unaffected by binary hardening. Hardening does not fix a design flaw.

7.5 The transferable lessons

Scan UDP on every box. Ten seconds of --top-ports 30 reorders the whole engagement. SNMP, TFTP, and NTP are the usual suspects, and SNMP is by far the most valuable.

Walk nsExtendTable, not just system. 1.3.6.1.4.1.8072.1.3.2 exposes the commands the agent runs and the human-written description of each. Descriptions are written by admins for admins, which means they assume an internal audience — exactly the wrong assumption. Decode the index: it is length.ascii.ascii….

Treat "default password" as a specification, not a hint. It narrows the candidate set enormously: try the account name, the hostname, and the box name first, in both cases. kiero:kiero was the answer, and it took a 19-entry list to find, not a wordlist.

A setuid binary is a design review, not a brute-force target. Read it before attacking it: file, strings, then objdump -d on main. system() with a bare command name is instantly exploitable; system() with an absolute path is not. Check whether setuid()/seteuid() is called before the dangerous call — that is what removes the shell's built-in privilege drop.

Hardening is not a fix. Full RELRO, PIE, NX, stack canaries — all present here and all irrelevant. The bug is that root executes a command resolved through PATH.

Clean up, and say what you did not change. Documenting "I replaced the chpasswd call, so the intended password reset never ran" is the difference between a report and a guess.

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.
